# Cell 模式评估：合理性、扩容判据、管理成本与业界对照

**结论先行：① Cell 模式合理**——它是 AWS Builder's Library 验证过的 cell-based architecture 同款模式（故障域=部署域=灰度域），且在"Hindsight 引擎不改核心"的约束下是唯一可落地的组织方式（主文档 §2 的 ADR 结论）。**② 管理成本的真实来源不是"三层伸缩互相牵连"**——引擎扩容与 PG 扩容在运行期几乎解耦（前者被 PgBouncer 吸收，后者对引擎只是断线重连），真实成本 = 每 Cell 一套同构操作 × Cell 数（线性项）+ 规划期预算核算（一次性算术）。**③ 压成本的答案是"少而大的共享 Cell + Cell 即代码"**——扩 Cell 判据（万级索引/schema）保证共享 Cell 能装很多租户；在租户总量 ≲10 万、地域×维度组合有限的规模假设下 Cell 数为个位数到十位数（推断前提与"只增不减"问题见 §5.1 的取舍说明），模板化后新增 Cell 的边际人力接近常数（定性估计，未实测）。**④ 业界对照**：本架构与 Supabase 同属"引擎零改动+独立实例分组"阵营；DynamoDB/Aurora/Neon 式动态池化需要五条引擎级前提，是数据库内核工程，无法靠编排层补齐——但存在低风险演化台阶（cell 内多库+连接代理 → 存算分离引擎托管）。

本文是 [`huawei-cloud-serverless.md`](huawei-cloud-serverless.md)（下称"主文档"）的专题评估，回答五个问题：Cell 合理吗 / 何时扩 Cell / 三层伸缩管理成本高吗 / 其他云怎么做 / 有没有更好的管理方式。**术语速查**（详见主文档 §0）：bank=租户内的业务记忆分区；请求角色/任务角色=hindsight-api/hindsight-worker 两种进程；TEI=开源推理服务（embedding+重排）；expand-contract=加列先行、删列滞后的发布契约。凡"§n"指本文节，"主文档 §n"带前缀。**外部云断言均为【模型知识·待核实】**（本环境网络不可用，知识截止约 2025；具体数字不确证的不给）；本架构侧断言均落主文档节号或引擎源码。

## 1. Cell 模式合理性判定

| 判据 | 结论 | 依据 |
|---|---|---|
| 业界是否有同款模式 | **是**【模型知识·待核实】 | AWS Builder's Library《Cell-Based Architecture》《Shuffle Sharding》：cell = 服务一组租户的独立全栈单元，故障爆炸半径=1/N cell，部署域=故障域，cell 交错发布（新版本逐 cell 滚动灰度、坏版本快速回滚）。与"shuffle sharding"（共享池内每租户随机抽取实例组合，**主旨是故障隔离**——使任意两租户几乎不共享基础设施，噪声邻居抑制只是附带收益）互补——前者粗粒度分组，后者细粒度交错 |
| 为什么我们必须用 | 引擎硬约束 | 主文档 §2 ADR：`DATABASE_URL` 进程级静态（C2）、`TenantContext` 只返回 schema 名（C1）、跨租户例程单库语义（C5）——不改引擎核心时，"独立 PG 实例分组"是唯一可落地的多租户组织方式 |
| 与 AWS cell 的差距（诚实） | 两点 | ① AWS 托管服务内部 cell 的数据层是高可用集群/多副本，我们是**单 RDS 实例（HA 主备）**——可用性依赖 RDS HA 而非 cell 内多副本；② AWS 的 cell 对客户**完全透明**（客户只见端点），我们的 cell 由自建平台管理——这正是"自研平台=扮演云厂商托管层"的含义 |
| cell 带来的额外红利 | 灰度与版本隔离 | cell = 天然的发布灰度单元（交错发布）、embedding 维度/引擎版本的隔离单元（维度冻结约束的解法）、强隔离租户的专属单元（`plan=dedicated`）——这些红利在"单一共享池"模式里没有安放处 |

**判定：合理，且在约束下别无选择；需要补齐的是"托管化"（把 cell 管理自动化到客户/运维无感知），而不是换模式。**

## 2. 何时需要扩 Cell：决策表

扩 Cell 是**分片动作**（容量/隔离的结构性变化），不是常规伸缩——常规负载波动全部在 Cell 内消化。判据表（阈值方向为"到这个方向就该考虑"，具体数值待压测标定）：

| 指标 | 阈值方向 | Cell 内可否吸收 | 吸收手段 |
|---|---|---|---|
| 向量索引数（活跃 bank×3+全局） | → 万级 | 惰性创建可延缓（引擎按行数阈值建索引），**超限只能加 Cell** | 主文档 §3.2/§7.2 |
| 租户 schema 数 | → 万级 | 升配内存暂时扛；根治=加 Cell | §7.2 |
| 连接预算（两条线） | 需求 > 预算 | **先 Cell 内吸收**：升配 RDS / 调低每实例池 / 调大 PgBouncer max_client_conn；全调满仍不够才加 Cell | §7.3 |
| recall 读吞吐 | QPS 高 | 加请求实例（预算内）；预算耗尽后加 Cell。**注意：只读副本救不了 recall**（异步复制破坏写后立读，Day-1 不配副本，§5.2） | §5.2/§7.1 |
| 单个大 bank 任务慢 | retain/consolidation 排队 | **拆 bank**（同 bank 串行化谓词，加实例无效；recall 不受影响） | §7.2 |
| 合规/大客户隔离 | `plan=dedicated` | **无条件加 Cell** | §6.1 |
| 换 embedding 维度/新引擎 | 维度冻结 | **必须新 Cell + 源重放**（pgvector 列宽硬约束） | §9 |

**关键澄清（对"PG 也能横向扩"的误解）**：本架构里 PG 的"横向扩"（只读副本）**只服务分析/导出负载**，不参与 recall 主路径——所以 Cell 内真正能横向扩的只有引擎 ECS；存储容量的横向扩展就是加 Cell 本身。**两层不对称：引擎横向、存储纵向（升配）+分片（加 Cell）。**

## 3. 管理成本的真实解剖

### 3.1 三层伸缩的耦合性质：规划期静态耦合，不是运行期动态耦合

用户质疑"Cell 里 PG 和 Hindsight 资源都能横向扩，管理成本会不会高"。解剖结果（全部落主文档/源码）：

| 层 | 伸缩动作 | 触发 | 对其他层的影响 |
|---|---|---|---|
| 引擎 ECS | AS 加/减实例 | 并发占用率>70% / 有活 bank 数 | **零配置联动**——无需任何 PG 侧配置变更；服务端连接数不随实例数涨（PgBouncer 后端池固定）。但存在三条运行期**负载**联动（自愈型，见下） |
| PgBouncer | 调池参数（reload） | 预算重算时 | RDS 升配后同步调大 default_pool_size（一次性） |
| RDS PG | 升配 / 加分析副本 | 连接/IO/内存饱和 | 对引擎=断线重连（重连窗口 ~10s，§8-F4）；迁移锁走直连不受影响 |
| Cell | 新建 | §2 决策表 | 平台注册 + 租户放置策略更新 |

**耦合点全部是部署期算术**：①②两条连接预算公式 + query_timeout≥600s 对齐 + 多进程乘数（主文档 §7.3）——每 Cell 算一次。**不存在"每次扩容要跨系统联动改配置"的运行期耦合**；但运行期仍有三条**负载联动**（非配置联动，自愈型）：① 引擎到 PgBouncer 的**客户端连接随实例数线性增长**（预算②式）——这正是 AS max 实例数被两条预算反推的原因，扩容受预算硬约束而非零影响；② 新实例的注册表缓存冷启动（miss 查平台，TTL 5min）与任务角色的轮询扫描加入；③ 每实例直连 Cell 内共享 TEI——主文档未设 TEI 连接预算线，实例数增长直接传导 TEI（F7 单点）。用户担心的"两层伸缩互相牵连"在配置层面不成立；成立的代价是规划期一次算对 + 上述三条负载联动的容量预留。

### 3.2 Cell 底座清单（与租户数无关的固定占用）

开一个空 Cell ≈ **6 个常驻 ECS 实例 + 1 个 HA RDS + 1 个 ELB + 2 个 AS 组**：ELB×1、请求角色 min 2 + 任务角色 min 1、PgBouncer×2、TEI×1（+共享面分摊的 APIG/L2/平台库/采集器；运维跳板机若常驻则另计）。共享 Cell 只装少量租户时，底座成本**主导**——这直接证成"少而大"策略：**Cell 要装满才有经济性**。

### 3.3 Cell 间差异面与"Cell 即代码"可行性

**必须不同的约 15 个参数**：三个数据库 URL（进程级静态，`config.py:153-157`）、每 Cell 独立 DB 账号与 OBS 桶凭据（主文档 §6.1 中间态强化）、`HS_PLATFORM_CELL_ID/REGISTRY_URL/METERING_URL`、ELB/PgBouncer 端点与池参数、AS min/max（两角色各自，预算反推）、TEI 端点+embedding 模型与维度、引擎镜像版本（灰度差异项）；**Cell 按地域分布时**（§5.1）VPC/子网/安全组 ID/KMS 密钥也必然 per-cell。
**基本相同的占绝大多数**：容器镜像、平台扩展包与槽位配置、禁项清单（MCP stateless/无本地模型/WORKER_ENABLED=false）、安全组规则模板（同地域共享 VPC 前提下）、user-data 脚本结构（仅实例 ID 插值）、告警规则定义。
**评估：一份参数化模板 + 每 Cell 一份 values 文件可覆盖绝大多数（定性估计）**；剩余差异是"故意要不同"的（版本、维度——Cell 存在的意义）。差异面小是隐性优点。

### 3.4 升级与监控的线性项

- **升级**：Cell 内=请求角色滚动（零风险）+ 任务角色滚动（worker_id 释放协议，30s 排空，源码 `shutdown_graceful`）+ schema 迁移（直连+expand-contract，镜像可回滚、**schema 回退仅限可逆版本**——数据迁移的 downgrade 多为故意空操作，主文档 §8-F10）。跨 Cell=按金丝雀→批次推进，**单步操作同构、人力随 Cell 数线性；版本共存/兼容矩阵的管理成本随 Cell 数变多**（主文档 §2.3 自认的版本碎片成本）——适合控制器循环执行（主图 CTRL 已含"版本升级"职责）。
- **监控**：每 Cell 约 8-10 条告警（F 表逐项 + 计量丢弃计数 + 连接预算用量），规则定义同构可模板化，实例数线性；统一 Cell 规格可消除阈值差异。

### 3.5 成本曲线（定性结论）

| 运营方式 | 对租户数 | 对 Cell 数 |
|---|---|---|
| 不模板化（每 Cell 手工 ~6 实例+2 AS 组+监控栈） | 线性（随放置动作） | **大斜率线性** |
| **模板化 + 少而大**（本方案要求） | **常数**（大 Cell 内先纵向/参数吸收） | 小斜率线性（apply 模板+注册+冒烟 ≈ 常数级人力，定性估计） |

残余线性项只有跨 Cell 版本灰度批次（实践近似 log 批次）与跨 Cell 聚合分析（§2.3 已列）。**由于扩 Cell 判据（万级索引/schema）保证共享 Cell 可以很大，合理运营下 Cell 数是个位数到十位数——管理成本整体可控。**

## 4. 业界对照（全部【模型知识·待核实】）

| 产品 | 隔离单元 | 伸缩单元 | 租户→资源映射 | cell/分片对客户可见 | 关键技术前提 |
|---|---|---|---|---|---|
| AWS 托管服务内部 cell | cell（全栈） | cell 容量/数量 | 租户组→cell | 不可见 | 自建控制面+路由+故障自动化 |
| Lambda | Firecracker microVM | 并发环境数（执行环境保活复用） | 函数→动态调度 | 不可见 | microVM+执行环境复用+秒级调度 |
| Aurora Serverless v2 | 集群（共享卷+实例；**集群属单账户**，多库共享是账户内而非跨租户） | ACU 秒级**纵向**热调 | 多库共享一集群 | 库可见 | 存算分离+改造引擎 |
| DynamoDB | 内部 partition | partition 自动分裂 | 表→分区 | **完全透明** | 自研引擎+请求路由 |
| PolarDB Serverless | 集群 | 计算单元秒级 | 多库共享实例 | 库可见 | 存算分离 |
| Snowflake | 虚拟仓库 | size+cluster 数 | 租户→仓库+共享存储 | 仓库可见 | 存算分离+自研引擎 |
| **Neon** | 每租户一个 PG compute | 纵向/scale-to-zero | 租户→1 compute+共享 pageserver | 实例可见 | **存储引擎剥离重构**（pageserver/safekeeper） |
| Supabase | 项目（专用 PG 实例） | 实例规格 | 租户→项目→实例 | 实例可见 | SaaS 实例运维自动化 |
| PlanetScale/Vitess | shard | 节点数/在线 reshard | 租户→keyspace→shard | 需理解分片键 | VTGate 中间件+十余年重分片工程 |
| **本架构 Cell** | cell=ECS 组+独立 PG | cell 容量/数量 | 租户组→cell→独享 PG | 可见（自建） | 路由层+cell 生命周期自动化 |

两个阵营的分界与**动态池化的技术前提**（DynamoDB/Aurora/PolarDB/Neon/Lambda 各自满足其中数条）：①存算分离（持久状态移出计算单元——Neon 缩零与 Aurora 秒调的本质；对 Lambda 平凡真，对 DynamoDB 实为分区复制组而非共享卷）；②快启动（microVM/执行环境保活复用/快照恢复；**Aurora 的对应物是运行中实例的 ACU 热调**，非单元快启）；③自建控制面（健康/故障转移/放置/计量）；④引擎内多租安全；⑤细粒度计量作为产品形态。另有两条常被低估的工程量：**数据面代理/请求路由**（把单元生死与位置对客户端藏起来——Neon 连接代理、VTGate；这是常驻热路径组件，不是控制面）与**存储层自身的多租隔离与 QoS**（pageserver 按租户限流、DynamoDB adaptive capacity——"把状态拆出去"只是半个工程，拆出去后怎么按租户隔离是另一半）。经济学前提：单元/租户固定开销足够小，否则池化密度收益被底座成本吃掉（呼应 §3.2）。

**阵营内部也有密度分级**：Supabase 每项目独占 PG 实例（租户级粒度、单租户密度低）；**本架构实例边界在 Cell（租户组）级，组内租户以 schema 共享实例——密度是卖点而非代价**，与 Supabase 的"粒度粗"不可混谈。

**两个值得记的业界细节**【模型知识·待核实】：Aurora Serverless v1 能缩零但一集群一库且恢复数十秒，v2 有秒级热调却砍掉缩零——真正的难点不是"缩零"而是"**高密度+快恢复**"兼得，恰好印证台阶三的工程量级；TiDB Serverless（共享多租集群 + 引擎内 RU 资源组限流 + PG 协议兼容）是与台阶三最同构的现存参照。

**阿里云展开**（用户点名，均【模型知识·待核实】）：PolarDB Serverless 与 Aurora 同构——存算分离（RW/RO 计算节点 + 共享分布式存储），serverless 形态按计算单元秒级伸缩、一集群多库共享；PolarDB-X 是自研分布式内核（无状态计算节点 CN 横扩 + 数据分片 DN + 元数据服务 GMS，分片对应用透明，在线扩缩分片是其核心工程）；Lindorm/Hologres 提供多模型/实时分析场景的实例级隔离与计算分离形态；函数计算 FC 同 Lambda 模式（按请求拉起+预留实例）。**结论：阿里云与 AWS 同路线**——动态池化全部建立在自研或深度改造的引擎之上；两家云都没有"原生引擎+分组"形态的 serverless 数据服务可直接替代本架构的 Cell 模式（可借用的只有存储层的存算分离，即 §5 台阶二）。

**术语澄清**：Vitess 的 "cell" 指可用区/故障域（拓扑分区），与 AWS 的 cell（租户分组）语义不同，勿混淆。

## 5. 更好的管理方式（建议）

1. **少而大**（首要）与**故障半径的显式取舍**：目标形态 = 2~5 个大共享 Cell（按地域×版本维度，注意这是乘法：4 地域×2 代维度即 8 个起）+ 极少专属 Cell。**必须直面的张力**：Cell 少则单 Cell 故障影响面大（2~5 个时为 20%~50% 租户）——"少而大"与"爆炸半径=1/N"互相牵制。取舍：**版本半径**用 Cell 内实例级金丝雀化解（ELB 加权路由新版本实例先小流量再全量——把交错发布粒度从 Cell 细化到实例，吸收 shuffle sharding 的精神）；**数据层半径**（单 RDS）无法靠分组化解，只能靠 HA 时长（<2min，主文档 §8-F4）+ 预案兜底，须向客户明示。两个前提必须声明：租户总量 ≲10 万量级时 Cell 数才是个位数到十位数（更大规模线性增长）；**Cell 只增不减**——dedicated 套餐与维度换代开的 Cell 不会自动消失，需要退役流程（冻结写入→租户迁移→归档销毁）纳入运营手册。另计"扛到阈值再开"的**迁移债**：触发分片时存量租户 export/import 搬运+排空窗口，越晚开单次越重；近阈值运行（万级 schema）的内存压力也在上升。
2. **Cell 即代码**：一份参数化模板（~10 个差异参数）+ 每 Cell 一份 values；平台控制器的"开通 Cell"= apply 模板 + 注册 + 冒烟三步。差异面 90%+ 可覆盖（§3.3）。
3. **Cell 作为灰度单元是红利不是负担**：交错发布（金丝雀 Cell → 批次推进）比"单一共享池的百分比灰度"更安全——坏版本的爆炸半径天然=1/N Cell。把发布流程设计成 per-cell 流水线，升级的"线性"变成批次数（近似 log）。
4. **统一 Cell 规格**：共享 Cell 用同一 RDS 规格/同一预算参数集，消除监控阈值差异与 values 分叉；专属 Cell 才允许异构。
5. **演化台阶**（长期，按风险升序）：
   - **台阶一（中间件层）**：**跨实例的库路由**——连接代理按 schema 前缀把 SQL 转发到对应 PG（主文档 ADR 的 A-2 代理形态），或引擎侧多池选库（B' 形态）。两者都把租户从"单实例"解耦、从而提升密度；但按主文档结论如实：**都要改引擎**（poller 的单库发现语义重构，数周级），不是零改动；A-2 还依赖未验证的 schema 路由代理（pgvector 兼容待 POC）；
   - **台阶二（换存储引擎）**：迁移到存算分离的托管引擎（Aurora/PolarDB 类）——真实红利是**秒级纵向伸缩与存储弹性**；"副本参与读"须加前提：recall 固定走副本是**引擎行为**（源码级），Aurora 副本同样异步复制，写后立读问题依旧要引擎侧 freshness 处理——换存储层不消除它；
   - **台阶三（自研/内核级）**：Neon 式"每租户独立库+按需计算"——存储引擎剥离重构，**数据库内核级工程，无法靠编排层补齐**（TiDB/CockroachDB Serverless 的引擎内资源组路线是同量级的另一条自研路）。主文档 §2.4"引擎原生支持动态数据源后 A 形态反超"在台阶一/二的引擎改造完成时即可成立，台阶三是其极致形态。
   - **每上一级台阶，Cell 的职责就卸下一项**：台阶一卸"容量分片"、台阶二卸"存储伸缩"、台阶三卸"租户密度"——**最终 Cell 退化为纯故障域/灰度域**，这正是 AWS 内部 cell 的终态用法。

## 6. 对用户五个问题的直接回答

| 问题 | 回答 |
|---|---|
| Cell 模式合理吗 | 合理（业界同款 + 约束下唯一解），差距在"单实例数据层"与"未托管化"两点，解法是自动化而非换模式 |
| 什么情况扩 Cell | §2 决策表：万级索引/schema、连接预算全调满、dedicated 套餐、换维度/引擎——四类硬判据 + 两类可先 Cell 内吸收的软判据 |
| PG/引擎都能扩，管理成本高吗 | 运行期**配置**解耦（质疑在配置层面不成立），但有三条负载联动（客户端连接线性涨/缓存冷启动/TEI 传导，§3.1）；真实成本=每 Cell 一套操作×Cell 数 + 规划期预算算术；模板化+少而大后接近常数（定性） |
| AWS/阿里云怎么做 | AWS 把 cell 藏在托管层后（内部 cell+shuffle sharding），其 Serverless 数据服务靠存算分离+自研引擎做动态池化；阿里同路线（PolarDB）；两者都不暴露 cell 给客户——我们要做的是把 cell 管理自动化到同等无感 |
| 有没有更好的管理方式 | §5 五条：少而大 / Cell 即代码 / 灰度红利 / 统一规格 / 三级演化台阶 |
