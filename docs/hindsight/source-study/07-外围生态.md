一个值得先立住的全局观察：**核心（hindsight-api-slim）对外只暴露一种协议**——`/v1/default/banks/{bank_id}/...` 上的 REST + SSE + MCP。CLI、控制面、coding-agents 集成、评测套件没有一家走 SQL 或进程内 import（extensions 除外），这让"换一家部署形态"（云、自托管、本地 daemon）对上层完全透明，也是全篇反复出现的模式。

## 2. hindsight-cli：Rust CLI

### 2.1 职责与技术底座

`hindsight-cli` 编译出名为 `hindsight` 的单二进制（`hindsight-cli/Cargo.toml:2-3`，版本 1.2.0；`[[bin]]` 块在 :9-11），定位是"漂亮的 CLI for Hindsight"。它不是脚手架玩具，而是一个覆盖核心 API 全部资源的运维界面，外加一个 k9s 风格的 TUI 探索器和本篇的重点：`hindsight fs mount`。

技术底座三层分工明确（`hindsight-cli/Cargo.toml:13-52`）：

| 依赖 | 用途 |
|---|---|
| `hindsight-client = { path = "../hindsight-clients/rust" }` | API 调用走 **progenitor 生成的 Rust SDK**（progenitor：从 OpenAPI spec 生成 Rust 客户端代码的工具，§3.2 详述；path 依赖，不单独发布 crates.io） |
| `clap 4.5`（derive + env） | 命令面；全局 `--output pretty/json/yaml`、`--verbose`、`-p/--profile` |

| `reqwest` | **blocking client 仅 fs 子命令用**（同步镜像引擎刻意避开异步 SDK）；async client 用于 timeout 配置与 multipart 文件上传（`Cargo.toml:23-25`） |
| `sha2` + `libc` | fs 的内容哈希与 POSIX daemon 控制 |

配置解析优先级在 `main.rs:145` 的 after_help 里写死：环境变量 `HINDSIGHT_API_URL`/`HINDSIGHT_API_KEY` > 命名 profile（`~/.hindsight/cli-profiles/<name>.toml`，`hindsight profile create/list/show/delete`）> `~/.hindsight/config` > 默认 `http://localhost:8888`。

`main.rs:1465-1479` 的 `main()` 还处理了一个发布级细节：release profile 用 `panic = "abort"`，而 Rust 启动时忽略 SIGPIPE，管道下游提前关闭（`hindsight ... | head`）会变成 SIGABRT 静默崩溃，所以在 Unix 上恢复 `SIGPIPE` 默认处置。

### 2.3 API 客户端：生成代码之上的"humanized"错误层

`src/api.rs` 是 1919 行的薄封装：类型直接 `pub use hindsight_client::types;` 转出（`api.rs:7`），调用是同步桥接异步。它解决的核心痛点是 progenitor 生成的错误把响应体吞掉：

```rust
// hindsight-cli/src/api.rs:37-67
async fn humanize_client_error<E>(err: ClientError<E>) -> anyhow::Error
where
    E: serde::Serialize + std::fmt::Debug + Send + Sync + 'static,
{
    match err {
        ClientError::ErrorResponse(rv) => {
            let status = rv.status();
            let body = rv.into_inner();
            let body_str = serde_json::to_string(&body).unwrap_or_else(|_| format!("{:?}", body));
            anyhow::anyhow!("API request failed ({}): {}", status, body_str)
        }
        ClientError::UnexpectedResponse(response) => {
            let status = response.status();
            let body = response.text().await.unwrap_or_default();
            if body.is_empty() {
                anyhow::anyhow!("API request failed ({})", status)
            } else {
                anyhow::anyhow!("API request failed ({}): {}", status, body)
            }
        }
        ClientError::InvalidResponsePayload(bytes, src) => {
            let body = String::from_utf8_lossy(&bytes);
            anyhow::anyhow!(
                "{}: {}\nResponse was: {}",
                crate::errors::INVALID_RESPONSE_PAYLOAD,
                src,
                body
            )
        }
        other => anyhow::anyhow!("{}", other),
    }
}
```

- 原始错误渲染为 `Unexpected Response: Response { ... }`，不带服务端返回的校验细节（注释引用了 issue #1007 与 #4049，见 `api.rs:36, 73`）。摘录第三分支的 `Response was:` 标记正是 `errors.rs:270-281` 做失败归类时切分的锚点（#5515）。
- `Humanized` 扩展 trait（`api.rs:75`）让每个生成客户端调用都能写成 `call(..).humanized().await?`，把 HTTP 状态码 + 响应体带进 anyhow 错误。
- 极少数 OpenAPI 未覆盖的端点（如 `AgentStats`）在 `api.rs:92` 起手写 struct，注释自嘲 `// Types not defined in OpenAPI spec (TODO: add to openapi.json)`。
- 0.10.3 修了这条链下游的**归类**（#5179）：`errors.rs` 的 `format_error_message` 现在只拿 `split_http_error` 切出的 `"<what> failed (<status>)"` 标题段判连接拒绝/超时/DNS，不看服务端 body——body 里恰好提到 timeout、DNS 或资源数字不该改变分类（一个快速 400 的校验错误曾因 body 里的 "timeout" 字样被误标成传输超时）。1.0.0 窗口再补一刀（#5515）：**解码失败就是解码失败**，不再拿 body 文本猜——服务端加了一个新响应字段导致旧 CLI 反序列化失败时，报"响应无法解码"而不是被误判成超时/DNS 错误（`errors.rs` +56 行）。

### 2.4 `hindsight fs mount`：把 knowledge base 挂载成文件树（重点）

**动机**：knowledge base 是核心引擎里"auto-refreshing 的合成文档树"（mental model 页 + 文件夹）。`fs mount` 把这棵树镜像成普通 markdown 文件夹，让 `ls / cat / grep / rg / fzf` 等一切 shell 工具、以及任何会读文件的 agent，无需知道 Hindsight API 就能消费记忆。`commands/fs/mod.rs:1-6` 自述是从独立的 TS 工具 `hindsight-fs` 移植进 Rust CLI。

**模块划分**（共 1889 行）：`mod.rs`（命令分发 + 刷新循环）、`client.rs`（极简 REST 读客户端）、`format.rs`（树→镜像计划）、`sync.rs`（同步引擎）、`state.rs`（state.json）、`daemon.rs`（后台进程）、`config.rs`/`paths.rs`/`health.rs`（配置、控制目录、健康检查）。

#### (1) 数据获取：一次同步 = 两次 HTTP

`client.rs:1-8` 的注释把设计说透了——不逐页拉取，只调两个端点再按页 id join：

- `GET /v1/default/banks/{bank_id}/knowledge-base/tree` → 文件夹/页层级（无正文）；
- `GET /v1/default/banks/{bank_id}/knowledge-base/export` → 一个 bundle，含每页 `<page-id>.md`、`index.md`、`<page-id>.log.md`（历史）。

```rust
// hindsight-cli/src/commands/fs/client.rs:136-153
```

#### (2) 镜像规划：文件夹→目录，页→`.md`

`format.rs:206-243` 的 `plan_mirror` 递归 `walk_plan`，把树压平成"要建的目录列表（父先子后）+ 要写的文件列表"。三个工程细节：

- **slug 化**（`format.rs:92-126`）：页名/文件夹名转小写、非 `[a-z0-9._-]` 连续字符折叠成单个 `-`、点号去重；全不安全字符则回退 `untitled`。单元测试直接锁行为：`slug("Net-30 / Terms!") == "net-30-terms"`（`format.rs:326-331`）。
- **撞名消解**（`format.rs:129-153`）：兄弟节点同名时用节点 id 的末 6 位字母数字做后缀，保证路径唯一。
- **正文回退**（`format.rs:172-197`）：页还没被 LLM 合成出来时，写一个带 YAML frontmatter（`id/type: knowledge-page/title/tags/timestamp`）+ 占位文案 `_This page has not been generated yet._` 的文件——mount 一个空 bank 也能得到结构可读的骨架。

frontmatter 序列化器是手写的极简版（`format.rs:64-87`），`is_plain_safe`（`format.rs:26-52`）决定标量是否需要引号：含 `:#[]{}` 等字符、疑似布尔/数字/日期的一律用 JSON 字符串语法（合法 YAML 子集）转义。

#### (3) 同步引擎：单向镜像的"以磁盘为准"哲学

`sync.rs:5-12` 的模块注释是理解整个设计的钥匙——镜像是**严格单向（API → 磁盘）**的，靠两个机制保证：

1. 镜像文件写成只读（Unix `0444`，除非 `--writable` 则 `0644`，`sync.rs:26-29`），普通编辑直接 EACCES；
2. **每一轮都拿磁盘上的字节和最新渲染内容做全量对比**，任何漂移——被篡改、被强 chmod 改写、写了一半——下一轮都会被覆写回服务器版本。

```rust
// hindsight-cli/src/commands/fs/sync.rs:120-143
for page in &plan.files {
    let hash = hash_content(&page.content);
    let prev = state.files.get(&page.rel_path);
    let abs_path = config.dir.join(&page.rel_path);
    if let Some(parent) = abs_path.parent() {
        fs::create_dir_all(parent)?;
    }

    // Source of truth is the bytes on disk — so a local edit is detected
    // and overwritten even when the page is identical to last time.
    let on_disk = read_file_or_none(&abs_path);
    match &on_disk {
        Some(disk) if disk == &page.content => {
            set_mode(&abs_path, mode);
            unchanged += 1;
        }
        _ => {
            atomic_write(&abs_path, &page.content, mode)?;
            written += 1;
            if on_disk.is_some() && prev.map(|p| p.hash == hash).unwrap_or(false) {
                reverted += 1;
            }
        }
    }
    // ... 记入 next_files
}
```

逐点看：

- **判断基准是磁盘字节，不是 state 里的 hash**。重写分两种情形：服务端内容确实变了（普通 written），或服务端没变、只是本地文件被动过（计入 reverted，即篡改回写）。
- **`atomic_write`**（`sync.rs:72-78`）：先写 `<file>.<pid>.tmp` 再 `rename`，读方（编辑器/agent）永远不会看到半页文件；写完立即设权限位。
- **失败不破坏现场**：`run_sync` 在 fetch 失败时只更新 `state.last_sync_ok=false` 就返回错误（`sync.rs:96-105`），注释强调"修剪只发生在成功 fetch 之后，瞬时网络错误绝不清空镜像"（`sync.rs:86-87`）。
- **删除同步**：state 里记录的、本轮不再出现的文件被删（先解除只读位再 unlink，`sync.rs:153-159, 203-207`）；消失的空目录按路径从深到浅 `remove_dir`（只删得动空的，`sync.rs:162-173`）。
- 产出物还包括控制目录里的 `.hindsight-fs/index.md`——带 frontmatter（bank/api_url/folders/pages）+ 树状总览的导览文件（`sync.rs:187-191`，`format.rs:246-292`）。

**state.json**（`state.rs:24-58`）：`.hindsight-fs/state.json` 记录 `bankId/apiUrl/lastSyncAt/lastSyncOk/lastError`、每页 `rel_path → {file, sha256}`、已建目录列表。它的目的注释写得很直白：让未变页面不被重写，**保住 mtime 稳定**——这样编辑器的 file watcher、`ls -la`、agent 的增量读取都不会被每 30 秒的轮询骚扰。

#### (4) 后台 daemon 与健康检查

`daemon.rs:1-6` 明确 **POSIX-only**：`fs start` 用 `setsid` 脱离控制终端，spawn 自身执行隐藏子命令 `fs run`（`FsCommands::Run` 标了 `hide = true`），stdout/stderr 追加进 `<dir>/.hindsight-fs/daemon.log`，pid 与元数据写 `daemon.pid`。停止时先 SIGTERM、轮询 5 秒、再 SIGKILL（`daemon.rs:158-174`）；Windows 上 `start_daemon` 直接返回错误而非假装可用（`daemon.rs:125-130`）。

`fs status` 汇总 daemon 活性 + 最近同步年龄，同步超过 `max(interval×3, 15s)` 视为 stale，**不健康时进程以非零码退出**（`mod.rs:390-392`）——这是给 cron/监控用的设计。

### 3.4 新增 API 参数后 SDK 怎么同步？

开发者的操作只有一步：本地跑 `./scripts/generate-openapi.sh && ./scripts/generate-clients.sh` 并提交产物。真正的防线在 CI（`.github/workflows/test.yml`）的四个守门 job：

1. **`verify-generated-files`**（test.yml:5627-5714）：重跑全部生成脚本后 `git status --porcelain` 非空即失败——忘了再生就直接红。
2. **`check-openapi-compatibility`**（:5715-5779）：从 PR merge-base 取旧 spec 与新 spec 对比，拦截破坏性变更。
3. **`check-cli-coverage`**（:5780-5819）：CLI 侧的对应检查（实现 `hindsight-dev/hindsight_dev/cli_coverage_check.py`，即 §9 所列脚本之一），与下面的 client coverage 合成两端防线。
4. **`check-client-coverage`**（test.yml:5820-5858；实现 `hindsight-dev/hindsight_dev/client_coverage_check.py`（454 行，1-34 行为模块 docstring））：专盯**手写 wrapper 的漂移**——扫描 `hindsight_client.py` 与 TS `src/index.ts` 的调用点，断言每个被覆盖操作的 request-body 参数（snake_case↔camelCase 自动换算）都出现在 wrapper 里，防止"生成层已更新、手写层漏字段"。

0.10.1 → 0.10.2 的一次真实再生成可以当这条链路的样例看：spec 新增 bank 别名端点（`/aliases`、`/aliases/{alias}`），并把 consolidation 策略从内联 dict 类型化为 `ConsolidationStrategySpec`/`ConsolidationScopePattern` 模型，四语言生成层随之各多出若干模型文件（Go 192→199 个 model），Python wrapper 补了 `search_knowledge_base`/`get_knowledge_base_tree` 两个高层方法与 tag 过滤选项——生成物入库 + CI 四守门保证这次变更在 review 里逐文件可见。

### 4.1 coding-agents（重点深讲）

`hindsight-integrations/coding-agents`（npm 包 `@vectorize-io/hindsight-coding-agents`，上一窗口发到 **v0.8.5**（`package.json:3`、`plugin.json:3`、`package-lock.json` 三处同步），再上一个窗口是 0.8.4，本窗口发到 **0.8.6**（§4.1(7)））是全部集成里最重的一个：README 开篇即定位——"Long-term project memory for **coding agents**... #### (1) 三段生命周期：每个 hook 型 harness 的统一契约

先立住术语：**harness 指承载集成的宿主编码 agent**（Claude Code、Cursor、Codex 等），分两类——**hook 型**（宿主在生命周期事件时以子进程运行集成提供的 hook 脚本）与**常驻插件型**（集成以宿主原生插件形式常驻）。先看前者的统一契约。

`src/harness/hook-lifecycle.ts:1-6` 的文件头说明了这个文件的角色："The single lifecycle contract for every hook-based harness... Adding a harness means adding one complete declaration here; its lifecycle cannot silently drift between the runtime and installer."

契约是三段固定生命周期（`hook-lifecycle.ts:41`）：`sessionStart`（种子注入）→ `prompt`（召回注入）→ `stop`（transcript 写回）。每个 harness 用一个 `HookHarnessSpec` 声明：宿主事件名、入口 js、超时、hook 配置风格（`nested`/`flat`/`process`/`toml-array`，对应 Claude Code 的 matcher 组、Cursor 的扁平对象、ZCode 的无 shell argv 拆分、以及 Kimi Code 的严格四键 TOML 表——多写第五个键会以 warning 告警并丢弃整个文件里的每个 hook，`hook-lifecycle.ts:42-54`）、stdin 事件字段怎么 `parse`、上下文怎么 `emit` 回宿主，以及专属 transcript 读取器。

**7 个常驻插件型 harness**（`src/harness/registry.ts:108-116` 的 `PLUGIN_ENTRYPOINTS`）：`opencode`（`src/index.ts`）、`opencode2`、`kilo`、`cline-cli`、`pi`、`prime-agent`、`dsh`。它们不跑 hook 二进制，而是以宿主原生插件 API 加载 `dist/<name>.js`，由插件入口直接调用共享核心（播种/召回/写回），不经 stdin/stdout。`registry.ts:41-84` 的 `HARNESS_NAMES` 共 22 项 = 15 hook 型 + 7 插件型，是**全仓库 harness id 的权威清单**（workbuddy/codebuddy 的 registry 注释也点明：两者是同一 `@genie/agent-cli` 宿主、CodeBuddy CLI 写 WorkBuddy 的 transcript 格式、IDE 另有读取器）。安装侧由 `installer.ts` 的 `genieInstaller` 工厂共用：hooks 合并进各自 `<home>/settings.json`，MCP 落在 `mcpPaths` 优先级链里**已存在的第一个**文件（卸载时全链清扫，防止高优先级文件后来才出现时留下休眠副本）。

先看时序（以默认 autoInject=reflect 为例），再拆代码：

**种子半边**（`src/core/session-start.ts:1-22`）：SessionStart 做两件事——冷 bank 的 git 历史后台播种 + 向宿主注入一条可见提示与知识页 roster。冷判定是**三态**而非布尔：`listDocumentIds` 抛错（服务器不可达）→ 不播种也不写状态（下个会话重试）、非空（已热）→ 只记 `seededAt`、空（真冷）→ 后台播种并注入提示。注释里保留了设计演化的证据：早期让 agent 自己问用户"要不要播种"再执行命令的方案实测失效（模型问了但不执行），改成 hook 直接播种。

v1.1.0 把这条播种链的两端都改了。**写端从"每次整篇重发"变成"只追加新提交"**（#5711，`core/git.ts`）：`syncGitLog`（`git.ts:459`）先问 `gitLogIsCurrent`，不 current 就走 `appendGitLog`（`git.ts:385`）——从文档的 `gitlog-head:<sha>` tag 取出基准提交，`gitLogRecordsSince`（`git.ts:241`）先用 `merge-base --is-ancestor` 确认它是 HEAD 的祖先，再 `git log --no-merges --reverse base..HEAD` 只取缺的那几条，以 `update_mode=append` + 确定性 `operation_id`（`uuidV5(bank\ncanonical\nappend\nbase\ncontent)`）发出。为什么值得这么绕：服务端的 delta retain 只在"前面的文本没变"时保留已存 chunk，任何让文本移动的事——一个合并进日期序中间的提交、窗口起点前移——都会让整篇日志重新抽取一遍；追加不会移动已存内容，新记录落在末尾，只抽取它们。退回整篇重发（`ingestGitLog`，`git.ts:337`）有四个明确条件：没有文档或没有 gitlog-head tag（首次播种）、基准不是 HEAD 的祖先（rebase / force-push / 分叉的 worktree）、新提交比 `seedLimit` 还多、或服务端不能安全 append。追加正文刻意以 `GITLOG_DIVIDER.slice(1)` 开头（`git.ts:407`）——服务端拼接 append 时只补一个 `\n`，这样接缝与其它记录之间的分隔符逐字节相同。整篇重发时会 `log` 一句"丢掉了最老的 N 个提交"，因为落到窗口外的提交会连同事实一起消失（#5708）。另有一处小防御：读回 bank 里存的 sha 时走 `gitLocal`（`git.ts:42`，`GIT_NO_LAZY_FETCH=1`），否则 partial clone 会为了一个它从来没有的提交去问 remote，每次白等几秒才失败（#5606）。

**调查（survey）端则从"每个会话都重跑"变成"每个提交最多三次"**（#6054 落地 #5623）：`startCodebaseSurvey` 新增的 `sha` 参数（`survey.ts:362`）把启动次数记在租约旁边一个小文件里（`survey.ts:336` 的 `surveyAttempts`），`SURVEY_MAX_ATTEMPTS = 3`（`survey.ts:328`）用尽即跳过——一次失败（没有可用的 agent CLI、预算被 kill、抽取服务故障）不会每个会话再全量重跑一遍。计数放本地而不是 bank，是因为失败的常常是服务端的抽取，写进 bank 的计数会连已经拿到的发现一起丢。同一个 PR 修了两处 Windows 启动：`binOnPath` 现在返回**解析到的完整路径**并支持 `exts` 收窄（`util.ts:18`；不带 shell spawn 时只认 `.exe`，而 npm 放在 shim 旁那个无扩展名文件是 `#!/bin/sh` 脚本，spawn 根本跑不了），codex 的 `-c key=value` 改用 `smol-toml` 序列化（`survey.ts:206` 的 `tomlValue`）——此前把 `C:\Users\…` 原样插进 TOML 基本字符串，`\U` 是非法转义，codex 直接拒绝配置退出（#5710）。失败现在都会留一行 `[survey]` 日志（`survey-lease.ts:193-206`），因为 agent 输出是 `stdio: "ignore"`，否则一次从没跑起来的调查什么痕迹都不留。

**召回半边**（`src/core/hook.ts`）：`runHook`（`hook.ts:428`）从 stdin 读事件、`spec.parse` 取字段、空 prompt 直接静默退出；`HINDSIGHT_DISABLE_HOOKS` 环境变量是防递归开关（代码库自己的 headless 会话靠它不让 hook 记自己）。注入源由 `cfg.autoInject` 决定（`hook.ts:245-345`）：`reflect`（每会话首轮做一次 reflect 综合，`budget:"low"` + `reflectTimeoutMs`）、`pages`（知识页搜索）、`recall`（观测召回）或 `none`（纯工具模式）。关键取舍写在注释里：**hook 注入的上下文落在用户消息里、会随 transcript 持久累积，所以 reflect 块只在运行的那一轮注入一次**，绝不按节奏重播（`hook.ts:245-253`）；知识页则不自动注入，只把"页清单 + 工具名"作为 roster 刷新，让 agent 用 `hindsight_search_knowledge_pages` 工具主动拉取（`hook.ts:347-353`）。

v1.1.0 改的是**同一块内容往哪儿落**（#6053 落地 #5914）：hook 型宿主本来就把注入放进 `additionalContext`（即用户消息侧），但三个常驻插件型宿主此前把它推进 system prompt——opencode 的 `experimental.chat.system.transform`、opencode2 的 `context` hook、pi/Prime Agent 的 `systemPrompt`。块的内容逐轮变化（recall 一轮只跑一次，roster 按节奏刷新），放在 system prompt 里就等于**每次请求的 system 段都不一样**，从那一轮起供应商的前缀缓存全部失效。现在三者一律把块追加到本轮的 user 消息：opencode 在 `chat.message` 里 `unshift` 一个带 `prt-hindsight-<messageId>` id 的 synthetic text part（`harness/opencode.ts:112-131`，id 前缀用 `prt-` 而非宿主的 `prt_`，因为宿主回读时按 part id 排序，这样无论是实时列表还是存下来的列表，块都在最前），opencode2 调 `ctx.session.synthetic({..., resume: false})`（`harness/opencode2.ts:184-207`，`resume: false` 让它不自起一次 run），pi 把注入作为一条 `customType: "hindsight"` 的 message 返回（`harness/pi-extension.ts:168`），事件上的 `systemPrompt` 字段直接删掉。`RuntimeCore.getInjection` 也随之收窄（`runtime.ts:237`）：只按 sessionId 取，**删掉了 `lastInjection` 那个"最近一块"的兜底**——它当初只为 opencode 那个不带 sessionId 的 system.transform 而生，现在没有消费者了。同一处还有一条容易忽略的清理：某一轮 prompt 为空（纯工具续答）时直接 `delete(sessionId)`（`runtime.ts:171-176`），否则上一轮的块会被再发一次——每个宿主的块现在都会持久化进 user 消息，重发就是真的重复。

**工具面的两条可靠性规则**（0.10.2 期间补齐，全部在共享核心层，所有 harness 同时受益）：

- **crediting（署名）是义务，不是判断题**（#4677）：agent 用知识页搜索写答案时曾出现"搜了十个相关页、一字不提来源、被追问才承认出处"的失败模式——等 guide 在长上下文里滚远时，规则已经无法执行。修法是让提醒**跟着搜索结果一起返回**：`hindsight_search_knowledge_pages` 的返回负载带一个 `crediting` 字段（`knowledge-tools.ts:241`），措辞是常量 `CREDIT_REMINDER`（`:66-72`）——"只要结果对你的回复有任何贡献（引用、转述、甚至只是印证了你要说的话），就用规定的 markdown blockquote 开头署名；自己改写过的句子不因此变成你的"。工具描述里复用同一常量（`:214`，宿主列出工具时看到的就是它），#4791 又补了一句定位："这些是过往记录——'已修复/可用'的断言先对代码验证再采信"，并加了 `toolGuideExtra` 配置项让团队附加自己的工具指南（`:128-129`）。
- **瞬时故障不再把知识页判死刑**（#4712）：修的是三件事。其一，bank 尚不存在时的 404 曾被当成"服务器没有 knowledge-base API"而把能力**终身锁死**（bank 由第一次 retain 铸出，所以新 bank 的首个会话必然先读页后建库），现在 `isEndpointMissing` 只认 FastAPI 路由未命中的裸 `{"detail":"Not Found"}`（`hindsight.ts:201-218`）——措辞对不上的 bank 错误让能力保持"未知"、下次调用重试，宁可错在安全的方向；`searchKnowledgePages` 这条漏网路径同样处理（`:870-877`）。其二，autoInject 三个注入源曾把"跑过但没结果"和"失败"折叠成同一个值缓存——一次首轮超时废掉整个会话的记忆；现在 `resolveInjection`（`hook.ts:120`，预算 `HOOK_INJECT_ATTEMPTS = 2` 个轮次、常量在 `:105`）把失败留作可重试。其三，常驻插件的开机前言改为**每会话从当次 roster 重建**，不再缓存进程级副本（消灭"前言说 0 个页、同轮却递来 3 个页 id"的自相矛盾）。

**写回半边**（`src/core/retain-hook.ts` + `chat.ts`）：Stop 事件到达后，`buildRetain`（`retain-hook.ts:99` 起）读 transcript 归一化成 `TransportTurn[]`（`{role, content, timestamp?}`），无可用轮次（纯工具调用）就 no-op，失败永远 fail-open 不抛。归一化后调 `retainLiveSession`（`chat.ts:273`），核心语义是**增量 upsert 一个会话文档**。发送前先解决三件状态事（`chat.ts:329-364`）：append 探测的"是"缓存在 cursor 上（hook 型宿主每个 Stop 都是全新进程，不缓存则每轮重问，#4560）；cursor 里挂着的失败 append 先结算再发新的（settleOps）；多 transcript 会话（side session）用 `cursor.paths` 记住文档现有哪几个文件，replace 只重建本次这一个文件、其余的留给下一轮 append 回来（#5508）。然后构造载荷：

```typescript
// hindsight-integrations/coding-agents/src/core/chat.ts:377-411
  /** Identity of ONE payload: a resubmission of the same bytes is collapsed server-side into the
   *  original operation instead of extracting (or appending) twice. */
  const opId = (mode: string, content: string) =>
    uuidV5(`${client.bank}\n${refId}\n${mode}\n${content}`);
  const submit = (content: string, operationId: string, append: boolean) =>
    client.retain(
      content,
      // Configured context wins. Extraction reads this to decide whose claim a sentence is, so the
      // default names both speakers: the previous "coding agent session" said nothing about
      // authorship and let an assistant's proposal be recorded as the user's decision.
      stamp?.context ?? DEFAULT_RETAIN_CONTEXT,
      refId,
      // Configured tags first, built-ins last and deduped: `source:chat` and `harness:<id>` are what
      // the documents list filters and draws its agent logo from, so a template cannot displace them.
      [
        ...new Set([
          ...(stamp?.tags ?? []),
          "source:chat",
          ...(harness ? [`harness:${harness}`] : []),
        ]),
      ],
      "conversation",
      {
        timestamp: startTs,
        updateMode: append ? "append" : undefined,
        operationId,
        metadata: {
          ...stamp?.metadata, // configured first: the built-ins below win on any key collision
          source: "chat",
          session_id: sessionId,
          ref_id: refId,
          ...(harness ? { harness } : {}),
        },
      }
    );
```

逐点讲解：

- **document_id 稳定**：整个会话始终 upsert 在 `conversation:<sessionId>` 下；已有 cursor 且服务端支持幂等 retain 时走 `updateMode:"append"` 只发新增轮次，否则整体 replace（`chat.ts:335-346`）。
- **operation_id 幂等**：`uuidV5(bank\nrefId\nmode\ncontent)`——同样的字节重投会被服务端折叠进原操作，而不是重复抽取或重复 append。这是 append 语义敢在网络重试下存在的前提。
- **cursor 状态机**（`chat.ts:415-470` + `retain-cursor.ts:89`）：发送前先写 cursor（带着待发字节，标 dirty/pending），宿主中途杀进程也能留下可重放缓冲而非永远重发全量；确认后逐项清空。另有一条"是否仍归我们重试"的 staleness 检查（`chat.ts:429-435` 的 `stillOurs`）：如果游标已被更靠后的写入认领，本次重试直接放弃——新写入包含旧内容。
- **跨 bank 移动只保存自己那一段**（#6052 落地 #5812）：cursor 原本只有一个 `bank` 字段，而 bank 是**每次 hook 调用按当次 cwd 重新推导**的——会话 `cd` 进另一个仓库（或跨过 `mapPathToBank` 的前缀）就换了 bank。旧行为是"换 bank 就整篇 replace"，于是同一个会话每碰一个 bank 就把整段对话复制一份进去，包括那些本就该留在别的项目里的话。现在 cursor 多了 `segments?: CursorSegment[]`（`retain-cursor.ts:107`，"某一段 transcript 从第几轮起属于哪个 bank"），`advanceSegments`（`retain-cursor.ts:145`）在换 bank 时追加一段、回到旧 bank 时不追加，`bankTurns`（`retain-cursor.ts:154`）在 replace 时只渲染本 bank 名下那几段；`planRetain` 的换 bank 分支也据此分流（`retain-cursor.ts:207-210`）：**从没写过的** bank 走 replace（只写它那一段），**回来**的 bank 走普通 append——否则 replace 会把之前那一段清掉。同时 `moved` 为真时既不去结算旧 bank 留下的 ops，也不把旧 bank 的 pending outbox 重放进新文档（`chat.ts:339-355`），那些 op 是另一个文档的账。还有一个相邻的幂等漏洞（#5845）：replace 的 `operation_id` 原本只由 `content` 决定，而会话回到更早的分支时（A → B → A）正文会重复，服务端对一个"已完成"的 id 直接应答而不重放，于是磁盘上留着 B 的内容；现在 id 里编进了上一位置的 `${cursor.turns}\n${cursor.fingerprint}`（`chat.ts:447-449`），重试仍带同一个 base，不同位置自然不同 id。
- **归因由此写入**：tag `harness:<id>` 与 metadata `harness` 字段都在这一次 retain 调用里落库；用户自定义 `retainTags/retainMetadata` 模板排在前面但内建键碰撞时内建胜（`chat.ts:388` 注释），且 `source:`/`harness:` 是保留命名空间，用户模板里配了会被丢弃并告警（`retain-stamp.ts:29, 106-107`）。

**内容形态**：turns 被 `renderSessionJsonl`（`chat.ts:42-47`）渲染成 JSONL——**一行一 turn**，行首是一个 `REF-ID:` system turn；工具活动被各 transcript 读取器压缩成 `role:"action"` 的紧凑 turn（工具名 + 主目标，不保留参数），函数输出整体丢弃（`transcript-codex.ts:15-17`）。选 JSONL 的理由写在 `chat.ts:36-41`：追加不重写文档，且服务端结构化分块把每行当原子单位，turn 不会被拦腰截断。

#### (3) daemon 模式：记忆可以不部署

`src/core/daemon.ts:1-38` 是一个把"本地 daemon 作为第三种部署形态"讲透的文件。三档连接模式按序解析：外部 API（Cloud/自托管）> 端口上已健康的现成服务器（直接采纳，永不重启）> 启动 daemon（实际由 `@vectorize-io/hindsight-all` 负责 uvx——uv 工具链的临时运行器，从 PyPI 拉包执行——拉起、profile 创建、就绪轮询）。

**时序是唯一约束**：冷启动要付 uvx 下载 + 模型加载（数十秒），而 prompt hook 必须按时返回——所以只有两个点保证 daemon 存活：SessionStart（预算 `DAEMON_WAIT_SESSION_START_MS = 12_000`）和 Stop（`DAEMON_WAIT_RETAIN_MS = 40_000`，预算最长且无人等结果），prompt 路径完全不碰 daemon。一个宕掉的 daemon 不被任何下游特殊对待：不可达的本地端口与不可达的云端产生同一种连接错误和同一条 `retain_failed` 诊断。

#### (5) 0.8.3/0.8.4：一个包被三代宿主加载

更早连发两版（0.8.3 / 0.8.4），合计只碰了四个源文件（`index.js` 与 `opencode2.ts` 的注释、`pi-extension.ts`、`auto-update.ts`），但每一处都是"宿主版本变了"这类最难在 CI 里复现的问题。

**OpenCode 的入口解析现在有三条路。** v1 与 v2 读同一份 `~/.config/opencode/opencode.json`，而 v1 看到 v2 的 `plugins` 键会**拒绝整个文件**，所以不能给两代宿主各写一条配置；只能让同一个包目录在两种解析器下都落到对的插件。三条路分别是：v1 跟随 `package.json` 的 `main`（→ `dist/index.js`，v1 插件）；v2 到 2.1 为止找 `<dir>/index.js`（包根那个再导出 `opencode2` 的文件）；v2 2.2 起改为"有 `name` 和 `exports` 的目录按包名解析"，于是读 `exports["./server"]`——三条路最终都指向同一个实现，但**只有 `exports["."]` 还留在 v1 插件上**时，那些"按名解析又不读 `./server`"的 v1 宿主才不会拿到 v2 的定义（`src/opencode2.ts:12-19`、`index.js:4-11`）。这条约束没有类型系统保护，靠 `src/opencode-entry.test.ts:5-14` 把三个值钉死：`exports["./server"] === "./index.js"`、`main === "dist/index.js"`、`exports["."].default === "./dist/index.js"`。取舍很清楚：一个包要伺候三代解析器，注释就是规范；任何"把 `.` 统一指向 v2"的清理都会静默打断一批 v1 用户。

**pi 的 run 有两种触发。** pi 1.3+ 的 `before_agent_start` 是一个联合类型：用户 prompt 的 run 带 `prompt`，而 `pi.sendMessage(…, {triggerTurn: true})`（pi 自己的 goal resume）带 `message`、没有 prompt（`harness/pi-extension.ts:26-33`）。旧代码直接 `event.prompt.trim()`，于是这类 run 在插件里抛异常，整轮失败（#5592）。现在非字符串一律按空 prompt 处理（`harness/pi-extension.ts:160`）——而"空 prompt"在共享核心里本来就有确定语义：丢弃上一轮注入的块（`runtime.ts` 的 `delete(sessionId)`，见 (2)），所以 custom message 既不会触发召回，也不会把旧块重复注入。测试断言的是两次调用的实参：`["s", ""]` 与 `["s", "next"]`（`src/harness/pi-extension.test.ts`）。

**npm 12 把单字段 `--json` 改成了数组。** 自动更新用 `npm view <pkg> version --json` 取最新版本；npm 12 起同样的命令返回 `["0.8.2"]` 而不是 `"0.8.2"`，`JSON.parse` 后不是字符串，函数返回空串，于是**自动更新静默地永远不触发**（#6135）。修法是解一层单元素数组（`src/core/auto-update.ts:328-331`），同时保留后面的发布号白名单正则——这个值最终会进 `spawn` 的 argv，`"1.2.3 && calc"` 这类字符串必须挡在门外。

顺带把版本史对齐：0.8.3 的发布说明覆盖的多是**合并于更早窗口**的改动（调查在 Windows 上启动与重试上限、每个会话轮次只存一次的分段、注入块进 user 消息、恢复 OpenCode 2.1 支持），只有"保证 OpenCode 2.2 下正确加载"这一条来自上一窗口的注释提交（c12f29430）；0.8.4 才是那两处代码修复（pi custom message、npm 12）的发布。这是"发布滞后于合并"的一个具体样本：只看 changelog 判断某行为何时上线，会晚一个窗口。

#### (6) 0.8.5：调查重新从每个宿主出发，且不再带着用户的终端身份

上一版（(5)）修的是"一个包被三代宿主加载"；这一版修的是**"调查在有些宿主上根本没跑"**，外加两处"给终端准备的东西漏进了不该去的通道"（子进程 env 与 ANSI 转义）。三处修复都在本窗口内合并、随后发版，与 0.8.3/0.8.4 那种"滞后一个窗口"的发布正好相反。

**A. 没有自己调查配方的宿主，不再让整条链静默失败（#6251；0.8.6 删掉了这里的“借用下一个 agent”，见 (7)）。** 0.8.5 的调查 agent 按一张优先级表依次试：`preferred` 是**当前宿主的 id**，后面依次是 claude-code、codex、antigravity-cli、opencode——而调用方是 `harness as SurveyHarness`（`session-start.ts:284`、`:322` 两处），把任意宿主 id 强转进来。**在 #6251 之前**，`resolveAgentBin` 的 `switch` 只列了 5 个分支、没有 `default`，于是 pi / opencode2 / kilo 这类没有专属配方的宿主走到函数末尾：类型标着 `string`，运行时是 `undefined`。下一行 `resolveBin(name)` 把它交给 `binOnPath`，后者在"没有名字"时直接抛 `TypeError`——测试把这个契约写成了注释："binOnPath's contract: a name in, a path or undefined out — it throws on no name at all"（next5 的 `survey.test.ts` 注释）。而这个异常又被 `startCodebaseSurvey` 最外层的 `catch { /* best-effort: a failed spawn must not break the caller */ }` 吞掉（本窗口仍在，`survey.ts:477-480`），函数返回 `false`：**没有日志、没有计数、没有下一次重试**——因为抛出点在尝试计数之前，连"每提交最多三次"那个预算都不会被消耗。0.8.5 的修法两行：给 `switch` 补 `default: return undefined` 并把返回类型改成 `string | undefined`（**next5 树里已经在**，本窗口仍是 `survey.ts:120-133`），以及循环里的 `if (!name) continue`（next5 在，本窗口随顺序表一起删除）。取舍很清楚：`default` 分支意味着**以后新增宿主、忘了写配方不会报错**，只会退化成"用下一个 agent 跑"；0.8.5 用测试把"pi 宿主交给 codex 执行"钉住，0.8.6 把这条测试反成"pi 宿主不 spawn"（见 (7)）。

**B. 调查不再继承用户终端管理器的 pane 身份（#6075）。** 调查子进程的 env 以前是 `{...process.env, HINDSIGHT_DISABLE_HOOKS: "1", ...}`（`buildSurveyPlan` 的 env 字面量，`survey.ts:223-234`）。问题在于**终端管理器会用环境变量给 agent 命名它所在的 pane，并 hook agent 的 Stop 事件**：`ORCA_*`/`HERDR_*` 被调查 agent 继承之后，它看起来就是用户自己那个 pane 的会话——于是 Orca 把用户的 pane 关掉、Herdr 把 pane 重绑到调查的 session。修法一行：`...Object.fromEntries(Object.entries(process.env).filter(([k]) => !/^(ORCA|HERDR)_/.test(k)))`（`survey.ts:227`，理由写在 :224-226 的三行注释里）。**边界要看清**：正则带下划线，所以 `ORCAS`、`MY_HERDR_X` 这类"名字里含 ORCA/HERDR 但不是 pane 变量"的照样保留，`PATH`（agent 靠它找自己）与 `HINDSIGHT_DISABLE_HOOKS`（防递归）也不受影响——测试把这四个都断言了。取舍：这是一张**按前缀的黑名单**，下一个终端管理器得再加一个前缀；代价是调查进程从此看不到用户 pane 的任何信息，而它本来也不需要。

**C. OpenCode 的 toast 不再显示 ANSI 转义（#6257）。** 同一个 `runtime.ts` 里，种子横幅那条路早就把转义剥掉了（`out.systemMessage.replace(/\x1b\[[0-9;]*m/g, "")`，`runtime.ts:152`），而首轮 recall 的 notice 只做了空白折叠（`replace(/\s+/g, " ")`）。notice 是画给终端上色的，OpenCode 的 `client.tui.showToast` 把它当纯文本渲染，于是用户看到一屏 `\x1b[2m…\x1b[0m`。修法是补上同一句正则（`runtime.ts:211-218`），顺序是**先剥转义、再折叠空白、再截 140 字符**——先剥再折很重要，否则 `\x1b[` 与 `2m` 之间一旦被空白规则切开就再也匹配不上。测试断言 toast 文本里不含 `\x1b`（`runtime.test.ts` 的 `shows the recall toast as plain text`）。

## 5. hindsight-control-plane：Next.js 管理面

### 5.1 定位与目录结构

`hindsight-control-plane` 是 Hindsight 的 Web 管理界面（npm 包 `@vectorize-io/hindsight-control-plane`，可被 CLI `hindsight ui` 直接 `npx` 拉起）。页面层极薄——`src/app/[locale]/` 下只有四个 `page.tsx`（banks 列表、`banks/[bankId]` 详情、dashboard、login），真正的工作量在 `src/components/`（v1.1.0 起 75 个 tsx：bank-config-view、constellation 图谱、audit-logs-view、content-composer、document-history 等）和 `src/app/api/`（**70 个 route.ts**，计数方式 `find src/app/api -name 'route.ts' | wc -l`；上一轮 68，v1.1.0 新增 `documents/history` 与 `audit-logs/[logId]`）。**上一窗口这两个数都没变**（70 route / 75 tsx，同一方法重数；`hindsight-control-plane` 上一窗口只改了 `package.json` 的版本号，`src/components` 与 `src/app/api` 零改动），没有新增页面骨架。

route 层在 0.10.2 有一个值得一提的结构变化：`documents/[documentId]/route.ts`（详情/chunks/reprocess 三个动态路由）被**删除**，改为在 `documents` 集合路由上用查询参数取单个文档（`GET /api/documents?document_id=...`，chunks/reprocess 同理）。注释写明了动机——document id 是任意字符串、**经常含 `/`**，作为 path 段编码费解（`documents/route.ts:21-23`）；另一组新增是 `banks/[bankId]/aliases` 两个路由，把 dataplane 的 bank 别名 CRUD 带进控制面。

0.10.3 窗口还恢复了 Reflect 答案的 Markdown 排版（#4777）：根因是 Tailwind v4 不再自动加载 `tailwind.config.ts`，typography 插件从未注册——`prose` 类名都在、样式全是死的，之前有人用 79 行手写 `.prose table` 覆盖硬扛。修法是在 `globals.css` 里显式 `@plugin "@tailwindcss/typography"`、删掉手写覆盖、只留 `.reflect-answer { overflow-wrap: break-word }`；think-view 的答案卡回到 `prose-base` + 标题字号阶梯，表格包进稳定组件 identity 的 `overflow-x-auto` 容器（`ReflectMarkdownTable`，控件切换不丢滚动位置）。新增的 `tests/styles/typography.test.ts` 用 postcss+tailwind **编译**样式表后断言 `:where(p/h2/ol/ul)` 规则真的生成了——防止"类名在、样式 inert"这种 v3 时代测不出的回归。

1.0.0 窗口的功能批次（八个 PR）：**失败可重试**（#5689）——documents-view 给失败上传加重试按钮、bank-operations-view 一键重试全部失败操作；**失败上传不再无声消失**（#5310/#5643）——上传卡片保留到它排队的 retain 真正结束，机制在新模块 `lib/pending-uploads.ts`；**知识页/mental model 导出**（#5457）——PDF 或 Markdown 下载，逻辑在新模块 `lib/page-download.tsx`（118 行）；**时间线 newest/oldest 切换**（#5681，data-view）；**大 bank 的 Memories 标签秒切**（#5692）——三层合力：graph 路由透传浏览器中断信号、**不解析直接流式转发**响应体（大 bank 一次好几 MB，解析再序列化白费半秒）并顺手 gzip（#5548，图谱 JSON 缩约 13 倍）、新增客户端缓存 `lib/graph-cache.ts`（30 秒内直接复用、过期后台刷新、去重在途请求、至多留 9 份）让 tab 切回时显示上次内容而非转圈；**401 语义分离**（#5452，见 §5.3）；实体标签编辑器两处修复（#5518 next build 类型错误、#5450 根级无操作的 `+field` 按钮隐藏）。#5674 的 cron 触发设置也拿到了控制面侧的配套编辑 UI（`components/mental-model-trigger-fields.tsx`，该窗口 +106/-29 行）。

v1.1.0 窗口有四条主线。

**① 手机上能用**（#5776）。做法不是给每个组件写响应式分支，而是四条**全局兜底规则**，写在 `globals.css:360-394`、**刻意留在任何 `@layer` 之外**（无层级 CSS 胜过 Tailwind 工具类，一次生效于所有组件）：`html, body { overflow-x: clip }` 让页面本身永不横向滚动（超宽内容必须在自己容器里滚，比如表格、tab 行）；`@media (hover: none)` 下把所有 `opacity-0` + `group-hover` 的控件强制成 `opacity: 1`——Tailwind v4 只在能 hover 的设备上应用 `hover:`，否则这类控件在触屏上永远不出现；iOS Safari 给日期/时间输入框一个原生最小宽度，`w-full` 压不下去，于是 `input[type=date|time|datetime-local] { min-width: 0 }`；`@media (pointer: coarse)` 把输入控件字号抬到 `max(16px, 1em)`，否则 iOS 一聚焦就放大页面且不缩回。知识页那个 Obsidian 式工作区在窄屏改成上下堆叠（`knowledge-base-view.tsx:540-542`，高度用 `100dvh` 而不是 `100vh`，手机浏览器地址栏收起/展开才不会把内容顶出屏幕）。侧栏在窄屏变成左侧抽屉：头部的 `SidebarMenuButton` 发一个 `hindsight:open-nav` 事件（`md:hidden`），`Sidebar` 用 Radix Dialog 接住（`role="dialog"`），`drawer-in` 动画（`globals.css:599`）在 `prefers-reduced-motion` 下关闭。这些规则由 `tests/styles/mobile-safety-nets.test.ts` 用 postcss+tailwind **编译**样式表后断言存在，并专门检查它们"不在 layer 里"——搬进 `@layer` 就会静默失效。

**② 键盘与读屏可达**（#5741）。侧栏原本是一个 `role="button"` 的 `<aside>` 包住整组链接——读屏软件看不到里面的 nav，点 aside 空白处还会误折叠。现在 aside 不带 button 角色，唯一的折叠控件是底部按钮（`aria-expanded` + `aria-controls="bank-sidebar-nav"`），每个链接有 `aria-label`、当前项带 `aria-current="page"`；`tests/components/sidebar.test.tsx` 把这三条钉死（"总共只有 1 个 button"、"nav 不在任何 button 里"、"8 个 link"）。banks 列表的选择器改成 `role="combobox"` + `aria-expanded`（`bank-selector.tsx:636-637`）。

**③ 文档变更历史**（#5638）。新增 `src/app/api/documents/history/route.ts`（转 dataplane 的 `documents/{id}/history`）与 `components/document-history.tsx`（297 行）；文档详情 tab 从 3 个变 4 个（`documents-view.tsx:1957` 的 `grid-cols-4`），每行显示这次操作给事实加/减多少、给观测新建/更新/删除多少，被删的观测 id 以红色删除线列出。它填的是一个具体盲区：编辑一条事实（哪怕只改日期）会删掉所有基于它的观测再由 consolidation 重建，被删的行从此无迹可寻——重建把两件不相关的事合并了，也没有任何地方能查。

**④ 两条"轻/重分离"**。审计日志（#5822/#5826/#5834）：列表**不再返回 request/response 体**——一条 retain 的审计行存着提交的全部内容，几页大 retain 就能把 API 进程拖垮；行先出现，点开才按 id 拉全文（新增 `app/api/banks/[bankId]/audit-logs/[logId]/route.ts`），动作过滤补上了"全部"以及服务端会写的每一个动作名（HTTP 路由的 `@audited(...)`、worker task 类型、memory_defense 三处都进 i18n；MCP 调用按工具名记，不在此列）。LLM 请求页（#5835）的描述改成"每一次模型调用——LLM、embeddings、reranker 与 decision model"，因为这三类调用也开始进请求历史：每种调用一个带计数的小徽章（`Embedding | 5`），而 trace 对话框里的"Input"仍只汇总 LLM 调用——把 embedding 的输入 token 加进同一个 Input 会被读成 prompt token。

另有几件小事：`next lint` 在 Next 16 被移除，`npm run lint` 改成 `eslint .`，配置换成 `eslint-config-next/core-web-vitals` + `/typescript` 的 flat config，并接上 react-hooks v7 的 React Compiler 规则（`set-state-in-effect`/`purity`/`immutability`/`preserve-manual-memoization`/`refs` 先设 warn，等存量重构完再提 error），同时删掉 `.eslintrc.json` 与 `eslint-plugin-react`/`eslint-plugin-react-hooks`/`typescript-eslint` 依赖（#6049）；Inter 与 JetBrains Mono 从 `next/font/google` 换成 `next/font/local`、woff2 入库（#5765——`next/font/google` 在构建时下载，CI 网络一抖就失败）；新增 `public/manifest.json` + `apple-touch-icon.png`/`icon-512.png`，iOS 加到主屏时才有图标与主题色（`src/app/layout.tsx:11-13`）；知识页与独立 mental model 在 UI 上分开（#5665/#5759，`mental-models` 路由透传 `exclude_knowledge_pages`，Mental Models 页多一个 "Hide knowledge pages" 开关（`mental-models-view.tsx:337`），默认关——知识页本身也是 mental model，不隐藏就一并列出）；bank 配置里新增 "Default observation scopes" 编辑器（#5666，`lib/observations-config.ts` 的 `ObservationScopes` 与 `scopesToText`——一行一个作用域、tag 用逗号分隔），文案在 #5827 改成中性描述。

再上一窗口（`2c00b59ae`）的界面改动有三处，都在"把已有的数据多露一点"，没有新增页面：

- **LLM 请求页多了两个维度**（#6222）。服务端现在返回 `retention_days`（`null` = 永久保留），列表与统计**只覆盖保留窗口**，于是 30 天周期里一条平线不再等于"没有调用"；统计接口多一个 `split_by=model|operation`，每个桶带 `series`（每个模型/操作的 calls 与 tokens），前端 `llm-requests-view.tsx` 据此把 24 小时图拆成多条线。动机很具体：请求历史里 LLM、embedding、reranker、decision model 四类调用混在一起，总量曲线看不出是谁在花钱。
- **知识页的证据图片**（#6217）。页面背后的 mental model 的 `reflect_response.based_on` 里，每条事实已经带 `attachments`；原来只数条数，现在把附件按 id 去重后铺成一条 strip（同一张截图被多条事实引用只显示一次），并在"下载 PDF"时追加到正文之后——**Markdown 导出刻意不带**，因为一个 `.md` 文件没有可移植的地方指向这些图（`lib/page-download.tsx:12-14` 的注释）。切换页面时先清空再加载，否则会短暂显示上一页的图。
- **Windows 下不再弹控制台窗口**（#6104）。`npx` 起动器 `bin/cli.js` 用 `spawn('node', …)` 拉起 Next 的 standalone server，在 PM2/服务这类**没有控制台**的父进程下，Windows 会给子进程新开一个可见窗口；加 `windowsHide: true` 即可（`bin/cli.js:99`），日志仍走 `stdio: "inherit"` 回到父进程。

**本窗口控制面动了两处，都是“把已有能力接到 UI”，不是新端点**（route.ts 70 / 组件 tsx 75 两个数不变）。

- **recall 的 prune/dedup 开关进 bank 配置（#6312）**。这两个开关在更早的 `bc5ea195a` 窗口就已经进了 dataplane 的 bank config（`recall_decision_model_prune` / `_dedup`），控制面此前只在单次 recall 的 `rerank` 对象里透传。现在它们和四个检索阶段、`prefer_observations` 一起被收进 `lib/recall-config.ts`：`RECALL_FIELDS` 是**七项**（4 个 stage + prefer_observations + prune + dedup），每项三态（`null` 继承服务端默认，`true/false` 覆盖本 bank），`recallSlice` 只从 bank override 里挑这七项（`recall-config.ts:11-33`）。`bank-config-view.tsx` 的保存路径与渲染循环都改成遍历同一张表（`:750`、`:1414`）——此前这两处各有一份手写清单，正是加字段时最容易漏一处的地方。**这个改动没有新增 API**：新测试直接读 `openapi.json` 的 `BankTemplateConfig.properties`，断言七项都是服务端接受的 per-bank 配置（`tests/lib/recall-config.test.ts:17-21`），并断言默认语言里每项都有 label 与 description（`:24-33`）——把“UI 敢显示”与“服务端肯接受”绑在一条测试里。文案解释了代价：prune 不额外发模型调用，dedup **每次 recall 多发一次决策模型调用**（`src/messages/en.json` 的 `recallDecisionModelDedupDescription`）。
- **文档标签的增量修改（#6339/#6411）**。服务端 `add_tags`/`remove_tags` 一落地，控制面就把“编辑标签”从“整表替换”改成“只发改动”：`lib/tag-change.ts` 的 `tagChange(current, next)` 返回 `{add_tags, remove_tags}` 两个差集（15 行，纯函数，3 个单测），`documents-view.tsx` 保存时只发差集、**再从服务端回读一次**（`:1179-1191`）——回读不是多余：别人同时加上的 tag 会被保留，本地 `next` 未必等于最终集合；回读失败才退回本地值。`lib/api.ts` 的 `updateDocument` 类型补了 `add_tags`/`remove_tags`（`:1149-1156`）。这条链与 §2.2 的 CLI、§3.3 的 SDK 是同一份契约的另外两个入口。

### 5.2 BFF 代理链：route.ts → 生成 SDK → dataplane

每个 API 路由都是同一个模式的手写 BFF（Backend for Frontend，专为自家前端服务的中间层）：解构请求体 → 用 TS 生成 SDK 的函数式出口 `sdk` 调 dataplane → 序列化返回（多数路由按需裁剪字段；recall 在 0.10.3 之后改为**整包透传**，见下）：

```typescript
// hindsight-control-plane/src/app/api/recall/route.ts:5-55（节选）
export async function POST(request: NextRequest) {
  try {
    const body = await request.json();
    const bankId = body.bank_id || body.agent_id || "default";
    const {
      query,
      types,
      fact_type,
      prefer_observations,
      rerank,
      max_tokens,
      trace,
      budget,
      include,
      query_timestamp,
      tags,
      tags_match,
      tag_groups,
      min_scores,
      temporal_window,
    } = body;

    const response = await sdk.recallMemories({
      client: lowLevelClient,
      path: { bank_id: bankId },
      body: {
        query,
        types: types || fact_type,
        prefer_observations,
        rerank,
        max_tokens,
        trace,
        budget: budget || "mid",
        include,
        query_timestamp,
        tags,
        tags_match,
        tag_groups,
        min_scores,
        temporal_window,
      },
    });
    // ...
    // Pass the whole body through: a hand-picked projection silently dropped
    // fields the caller asked for (source_facts, source_facts_truncated).
    return NextResponse.json(response.data, { status: 200 });
```

要点：

- **`rerank` 是 CLAUDE.md 那条三步清单的又一个实例**：dataplane 的 recall 请求体多了一个可空的 `rerank` 对象（`prune`/`dedup`，§3.3），控制面要做的正是三件事——route 解构并透传（`recall/route.ts:14`、`:34`）、`lib/api.ts` 的 `recall()` 参数类型加 `rerank?: { prune?: boolean; dedup?: boolean }`（`api.ts:658`）、把嵌套对象原样交给生成层，而不是在这里展开成两个布尔参数。嵌套对象值得保留原形：服务端每加一个决策模型开关，BFF 与类型都不用再改。
- **recall 的整包透传是 0.10.3 的教训**（#5410）：这个路由原本手挑字段组响应 JSON，调用方通过 `include.source_facts` 要的字段被静默丢掉（`source_facts`、`source_facts_truncated`）；现在 `response.data` 原样下发——BFF 的默认应当是"透传"，要裁剪就得显式列出并说明为什么。
- **客户端实例集中在 `src/lib/hindsight-client.ts`**：`DATAPLANE_URL` 来自 `HINDSIGHT_CP_DATAPLANE_API_URL`（默认 `http://localhost:8888`，`:15`）；三个客户端各有用途——`hindsightClient`（手写类实例，供高层语义调用）、`lowLevelClient`（生成层客户端，作为 `sdk` 调用的传输层传入）、`sdk`（生成层函数式出口，路由直接调操作）；dataplane 的 API key 由服务端环境变量 `HINDSIGHT_CP_DATAPLANE_API_KEY` 注入 Bearer 头，**浏览器永远见不到**。1.0.0 窗口起所有发往 dataplane 的请求都带 `hindsight-control-plane` User-Agent（#5536，`:25`），服务端日志可按来源区分控制面流量。
- `src/lib/api.ts`（2635 行）是给 React 组件用的第二层：文件头注明 "Client for calling Control Plane API routes (which proxy to the dataplane via SDK) / This should be used in client components, not the SDK directly"（`api.ts:1-3`）——即组件 → CP 路由 → dataplane 的两级结构。
- 这正是 CLAUDE.md "Control Plane API Routes" 清单的由来：dataplane 加参数时，route.ts 解构、SDK 传参、`lib/api.ts` 类型三处都要同步。

### 5.3 认证：单访问密钥 + HMAC 会话 cookie，鉴权全在 CP 层

**先回答一个自然会问的问题：控制面没有自己的存储**（全包搜不到 sqlite/prisma/任何数据库依赖），它是纯 BFF + 静态 UI；**鉴权也只发生在控制面这一层**，dataplane 只认 Bearer key（且该 key 只配在服务端）。

- 配置 `HINDSIGHT_CP_ACCESS_KEY` 即启用认证；**未配置时所有路由直接放行**（`src/middleware.ts:32-34`）——单机本地开发零配置。
- 登录（`src/app/api/auth/login/route.ts`）：常量时间比较提交的 key，通过后下发 cookie `hindsight_cp_access`，有效期 `SESSION_MAX_AGE_SECONDS = 24h`。
- 会话令牌是无状态 HMAC（`src/lib/auth/session.ts:10-16`）：`<issuedAtSeconds>.<base64urlHMAC-SHA256(issuedAt, accessKey)>`——拿 access key 当 HMAC 密钥，令牌不可伪造，**轮换 key 即吊销全部会话**，无服务端会话表；校验含时钟偏移容忍 60s 与常量时间比较（`session.ts:23-42` 的 `verifySessionToken`，`constantTimeEqual` 在 :88）。
- `middleware.ts` 统一把关：`/api/*` 未认证回 401 JSON（带 i18n 本地化错误键），页面路由未认证重定向 `/login?returnTo=...`，然后才委托 next-intl 做语言协商；静态资源与 `/api/health`、`/api/version` 在 `PUBLIC_PATTERNS` 白名单。1.0.0 窗口补了一个重要区分（#5452）：middleware 自己发的 401（**UI 会话**缺失/失效）现在带 `SESSION_REQUIRED_HEADER = "x-hindsight-session-required"` 响应头（`session.ts:5`），`lib/api.ts` 只有见到这个头才把浏览器送去登录页——dataplane 透传回来的 401（比如 dataplane 侧 key 配错）显示为错误而不是把一个有效的 UI 会话拉去重新输 key；顺带已登录访问 `/login` 时按 `returnTo` 直接送回原目标。
- 这是**单访问密钥模型**：一人一库的自托管场景，而非多用户 RBAC——"多用户"的隔离由 dataplane 侧的 bank 隔离与 extensions 层（06 篇）承担，CP 本身不区分用户身份。

## 6. hindsight-embed：内嵌 Python CLI 与本地 daemon 管理器

`hindsight-embed`（PyPI 侧包，版本随核心发布统一，本窗口为 1.2.0；运行时仅依赖 `aiohttp` + `rich`）解决"零服务器本地记忆"的最后一环。它有两个身份：**daemon/UI 生命周期管理器**，以及一个**转发前端**——除自身命令外的所有记忆操作（`memory retain/recall/reflect`、`bank list`……）原样转发给 hindsight Rust CLI，`main()` 经 `daemon_client.run_cli`（`daemon_client.py:247-309`，转发点 `cli.py:1595`）自动安装 CLI（curl 安装脚本）、确保 daemon 在跑并注入 `HINDSIGHT_API_URL`。

自身命令面：profile 侧 `list/create/set-env/remove-env/delete/set-active/show`（`cli.py:1067-1104`）；组件侧是三个组件各带同一组 start/stop/status/logs：daemon、ui、control（控制中心）（`cli.py:1509-1553` 分派处）；另有 `configure --web` 走 Web 配置向导（`:1463`）。0.10.3 统一了 profile 解析：`main()` 开头一次性 `resolve_active_profile()`（`cli.py:1506`），把**解析结果**（而非原始 flag）传给 daemon/ui 子命令与转发 CLI——此前各命令拿原始 flag 会绕过 env/active-profile 优先级链，同一进程里配置与目标可能指向不同 profile；`--profile default` 与 `HINDSIGHT_EMBED_PROFILE=default` 也从此显式选中默认 profile，不再落回 active-profile 文件。1.0.0 窗口又修了两处 profile 机制：`--profile` 的值现在存进 `profile_manager` 的模块级 `_cli_profile_override`（`cli.py:1454` 写入）而不是 cli.py 自己的全局变量——以 `python -m hindsight_embed.cli` 方式运行时（launchd/systemd/cron/容器入口点的常见姿势）cli.py 会被加载两份（`__main__` 与模块名各一份），全局变量一份写一份读互相看不见，profile_manager 只加载一次（#5694）；profile `.env` 文件的读取统一进 `profile_manager` 并剥离手写值里的包裹引号——`KEY="value"` 从此得到 `value` 而不是连引号一起当凭据（#5301，`profile_manager.py:213-229`）。

**连本地 API 还是外部 API**：决策在 `hindsight_embed/daemon_client.py:280-298`——设了 `HINDSIGHT_EMBED_API_URL` 就直接用外部 API（跳过 daemon；`HINDSIGHT_EMBED_API_TOKEN` 映射为 `HINDSIGHT_API_KEY`，:296-298）；否则 `ensure_daemon_running()` 启动/复用本地 daemon。

**用哪个数据库：用户的覆盖优先于 pg0**（#6158 落地 #6065）。旧实现直接把 `HINDSIGHT_API_DATABASE_URL` 改写成 `pg0://hindsight-embed-<profile>`，于是在 pg0 起不来的机器上（缺二进制、受限容器、公司策略）**没有任何办法**让本地 daemon 连外部 Postgres；用户设了也被覆盖。现在解析集中到一个方法，按 `HINDSIGHT_EMBED_API_DATABASE_URL` → `HINDSIGHT_API_DATABASE_URL` 的顺序找，每一个都先看 profile `.env`、再看进程环境，两个都没有才回落到 per-profile pg0（`daemon_embed_manager.py:326-343`）：

```python
# hindsight-embed/hindsight_embed/daemon_embed_manager.py:338-343
        for key in ("HINDSIGHT_EMBED_API_DATABASE_URL", "HINDSIGHT_API_DATABASE_URL"):
            url = config.get(key) or os.getenv(key)

```

取舍是**两层变量名**：embed 专属变量优先（它更具体），API 的同名变量作为兼容入口——否则所有已经按 API 文档配好数据库的人，在 embed 下都会发现配置被无声忽略。`cli.py` 的 `daemon status` 与控制中心的 `get_profile_paths` 都改调这一个方法（`cli.py:602`、`control_center/service.py:430`），避免"显示的数据库"和"实际连的数据库"再次分叉。

**daemon 管理机制**（`hindsight_embed/daemon_embed_manager.py`，`DaemonEmbedManager` 实现 `embed_manager.py` 的抽象 `EmbedManager`：`ensure_running/get_url/stop/is_running`）：

- **端口分配**：default profile 固定 8888，命名 profile 在 8889-9888 内按名字哈希分配（`PROFILE_PORT_BASE=8889`、`PROFILE_PORT_RANGE=1000`，`profile_manager.py:195-196, 638-647`）；UI 端口 = daemon 端口 + 10000（`profile_manager.py:200`）。
- **启动**：per-profile 文件锁（flock/msvcrt）串行化并发启动，锁内复查 `is_running()` 短路（`daemon_embed_manager.py:806-840`）；环境合并 profile `.env` 与进程环境，数据库由 `resolve_database_url` 决定（默认才是 per-profile 的 `pg0://hindsight-embed-<profile>`，见上），然后 `subprocess.Popen` 脱离父进程（spawn 点在 `:1055`）——POSIX `start_new_session`，Windows `CREATE_NO_WINDOW|CREATE_NEW_PROCESS_GROUP` 且优先 `pythonw.exe` 避免弹终端窗（`_detach_popen_kwargs` :189-225；0.10.3 从 `DETACHED_PROCESS` 换成 `CREATE_NO_WINDOW`——DETACHED 让 uvx 这类控制台启动器没有自己的控制台、其子孙反而能各自弹出可见窗口，且两标志同设时 Windows 直接忽略 `CREATE_NO_WINDOW`，#4562，经 #5291 落地）。0.10.2 补了一个环境卫生问题：embed 自身从别的 Python 环境（如 Hermes 的 venv）被拉起时，继承的 `PYTHONPATH/PYTHONHOME/PYTHONSAFEPATH/VIRTUAL_ENV` 会让 uvx 的 3.12 解释器 import 到宿主环境的 pydantic 等库——spawn 前现在用 `_strip_parent_interpreter_env`（`:169-188`）把 `_PARENT_INTERPRETER_ENV` 里的这 4 个变量剥掉，且只对"命令行里有 uv/uvx 形态"（`_runs_a_foreign_interpreter`，`:154-168`）的情况下手，以免破坏 `pip install --target` 布局对 PYTHONPATH 的合法依赖（#1240）。
- **API 进程命令解析链**（`_find_api_command`，`:493-535`）：开发模式用 `uv run --project <repo>/hindsight-api-slim --extra all hindsight-api`；发布安装优先找与 embed 同环境的 `hindsight-api` 入口二进制——查三个地方：① sysconfig scripts 目录（pip/venv 安装，#1401）；② **本文件所在 venv 的 scripts 目录**（按 `__file__` 上两级 `site-packages` 的父目录里有没有 `pyvenv.cfg` 认出来，上一窗口新增 #6272）；③ `__file__` 相对路径（`pip install --target` 布局，#1240）。**fallback 是 `uvx hindsight-api@<version>`**（`:549`）。触发 fallback 的条件不只"找不到二进制"：`_can_use_installed_api_binary`（`:479`）发现默认 `local` embeddings/reranker 需要 sentence-transformers 而当前环境没有时，主动放弃 slim 二进制退回 uvx 并打 warning。
  **#6252/#6272：被别的解释器加载时，仍要找到"装我的那个 venv"。** sysconfig 报的是**当前解释器**的 scripts 目录，而 venv 的 site-packages 可以被另一个基础解释器加载（Hermes 启动器就是这么干的：基础 Python + `site.addsitedir`）。此时 sysconfig 指向基础环境的 `bin`/`Scripts`，`hindsight-api` 不在那里，于是静默退到 `uvx`——一个已经 `pip install` 过的用户会看到它去下载一份全新的包。修法是把 `__file__` 上两级的 `site-packages` 认出来，再在它上面两级内找带 `pyvenv.cfg` 的目录，拼出 `<venv>/bin` 或 `<venv>/Scripts`，与 sysconfig 的结果**去重后合并**成候选列表（`daemon_embed_manager.py:515-524`）；`installed[0]` 也就是 sysconfig 的那个仍优先，所以常规 venv 的行为不变。
  两个刻意的边界：**只走两级**（Windows `<venv>/Lib/site-packages` 与 POSIX `<venv>/lib/pythonX.Y/site-packages`），不遍历所有父目录——否则一个外层 venv 会遮住 `--target` 装在自己目录里的 bundle（#1240）；**`--target` 的兄弟二进制仍然优先**（`:541-546`），注释写明退回 uvx 会重新引入 #1240。测试三条：Windows venv 布局、POSIX 布局（且缺本地 ML 依赖时仍回退 uvx）、以及"外层 venv 里的 `--target` bundle 用自己的兄弟二进制"（`tests/test_embed_manager.py`）。0.10.3 还修了 Windows 下 uv venv 的 GUI 启动路径（#4974/#5025，随 #5360 落地）：uv venv 的 `Scripts/pythonw.exe` 只是个 trampoline，会 CreateProcess `pyvenv.cfg` 里记录的基础解释器——现在 `_windows_gui_api_command`（`:415`，由 `_windows_gui_interpreter` 改名并改为返回命令列表）在 trampoline 情形下直接跑基础 `pythonw.exe`，并用 `_VENV_SITE_BOOTSTRAP`（`:259-262`：`site.addsitedir` 后 `runpy.run_module('hindsight_api.main')`）挂上 venv 的 site-packages——.pth 文件（pywin32、fastmcp）得以执行，旧的 PYTHONPATH 方案只保证 importable。UI 同理：优先 monorepo 源码，否则 `npx -y @vectorize-io/hindsight-control-plane@<ver>`（`_find_ui_command` :1231）。
- **健康探测与进程安全**：热路径 `is_running()` 用 2s 活性超时；判定性检查 `_port_health_ok`（`:823`）只探 `http://127.0.0.1:{port}/health`，要求返回 `status=="healthy"` **且** `database=="connected"`；`127.0.0.1`+`::1` 双栈探测不在这函数里——它属于端口占用检查 `_is_port_in_use` 与 UI 存活检查 `_reachable_ui_host`（`LOOPBACK_HOSTS` :118；Next.js 以 `--hostname localhost` 启动时只绑 `::1`，#3527）；启动超时 180s（`DAEMON_STARTUP_TIMEOUT` :72）。杀进程只基于端口占用 + 命令行指纹 `DAEMON_PROCESS_MARKERS = ("hindsight-api","hindsight_api")`（:123）——只按"谁占着端口"选目标曾误杀无关服务（#3520），无法识别身份的进程拒绝杀（`_owned_pid_on_port` :785-821）；Windows 命令行查询先走进程内的 `NtQueryInformationProcess`（见下），失败才退回 wmic/PowerShell Get-CimInstance；POSIX 走 lsof/ss/procfs（`:574-680`）。健康 daemon 占着端口时直接复用不杀（`_clear_port` :859）。
- **控制中心的三处"按真实状态判断"**（#6193）。其一，profile 名可以是中文，UI 用 `encodeURIComponent` 编码后发来 `%E5%B7%A5`，服务端原先按未解码的段匹配，于是这类 profile 在列表里点不开；现在每段 `unquote` 一次再比较，**同时**把解码后仍是路径片的段（`%2F`、`%5C`、`.`、`..`）整条判 404（`control_center/server.py:75-85`）——只解码一次，既支持 Unicode 又不引入穿越。其二，停止/重启不再先用 `/health` 判断"在不在跑"：一个忙到探针超时的 daemon 仍然是活的，旧逻辑会直接回"本来就没在跑"，用户永远停不掉它；现在无条件交给 manager（它按端口占用判断），并用 `running = not ok` 表示失败（`control_center/service.py:355-374`）——一次失败的停止意味着进程还在。其三，删除 profile 时如果 daemon 或 UI 任一停不下来就**保留 profile**（`:504-521`），因为配置、日志、pid 文件正是用户找出那个"停不掉的进程"所需要的；先删配置再发现进程还在，等于把现场毁了。
- **Windows 上先问内核再起子进程**（#6017）。判断"端口上的进程是不是我们的"要读命令行；旧路径走 `wmic`（新镜像里已移除）再退到 PowerShell，冷启动在负载高的机器上可能超过任何固定超时，而超时被调用方读成"不是我们的进程"，于是 manager **拒绝停掉一个确实属于自己的 daemon**。现在先用 `NtQueryInformationProcess(ProcessCommandLineInformation)` 在本进程内读（`daemon_embed_manager.py:700-760`，Windows 8.1+ 可用，同用户进程只需 limited query 权限），子进程探测降为兜底。这是"调用外部命令来做系统查询"的典型代价：答案正确但延迟不可控，而不可控的延迟在这里被当成了否定事实。
- **空闲退出**：代码默认 `DEFAULT_DAEMON_IDLE_TIMEOUT = 0` 即**禁用**自动退出（`daemon_embed_manager.py:74`），可用 `HINDSIGHT_EMBED_DAEMON_IDLE_TIMEOUT` 打开——注意 embed 包 README 写的"5 分钟自动退出"与代码默认不符，以代码为准。
- **与 coding-agents 的关系**：§4.1 的 daemon 模式把生命周期完全委托给 `@vectorize-io/hindsight-all`（它内部再落到 hindsight-embed），自身只决定"何时启动、带什么环境"（`coding-agents/src/core/daemon.ts:4-7`）。即链路是 coding-agents → hindsight-all → hindsight-embed → uvx/本机 `hindsight-api`。

### 8.1 hindsight-system-tests：黑盒 + stub 的"story"层

它存在的理由（README 开篇）：`hindsight-api-slim/tests` **706 个 test 文件**（`find hindsight-api-slim/tests -maxdepth 1 -name 'test_*.py' | wc -l` → 706，与 `ls hindsight-api-slim/tests | grep -cE '^test_.*\.py$'` 交叉一致；上一窗口 684，本窗口 +22）各测一个机制，抓不住**组合** bug——"consolidation 把事实擦掉、delta 刷新漏掉回填窗口、transfer 丢掉证据"这类活在步骤**接缝**上的缺陷。组织方式就是"story"：一个文件一个故事，共 **108** 个（`find hindsight-system-tests/tests -maxdepth 1 -name 'test_*.py' | wc -l` → 108，与 `ls | grep -cE '^test_.*\.py$'` 同值；上一窗口 100，本窗口 +8 个新文件，另有 2 个故事加在既有文件里）。**上一窗口零增删**（只在 `test_30_mental_models.py` 末尾加了一个测试函数 `test_a_chosen_id_stays_reachable_and_exportable`）；**更早的 `bc5ea195a` 窗口 +5 −1**：新增 `test_18_timezones`、`test_19_reranker_failover`、`test_25c_consolidation_answer_per_fact`、`test_65c_logged_out_llm_failover`、`test_95c_document_delete_traces`，删除 `test_39_refresh_document_shape`。

编号仍是**人类阅读顺序而非执行顺序**，复用继续变多：19/22/47/65 各三个，18/24/45/70 各两个（39 删除后只剩一个）；字母后缀已成常规插队手段（`25b`、`25c`、`95b`、`95c`）。每个测试必须能单独跑。

更早的 `bc5ea195a` 窗口五个新故事，每一个都恰好落在两套机制之间：

- **18_timezones**（#6208/#6224）：抽取模型把内容里的 "the job started at 09:44:23" 原样抄成 `occurred_start="2026-01-05T09:44:23"`，**没有偏移**。旧实现当 UTC 存，上海的客户端写的事实整体前移 8 小时，于是"发生时间"晚于"学到它的时间"。新语义是：这样的钟点读在 **retain item 自己的 timestamp 偏移** 里，没有就用 bank 的 `default_timezone`，都没有才按 UTC。故事在两个时区下各 retain 一次再读回，断言的是接缝处的换算而不是解析器本身。
- **19_reranker_failover**（#6072/#6154）：failover 链的不同成员分数不可比，客户端要对 `scores.reranker` 设阈值，就必须知道这一次是谁打的；而 trace 里的 `reranker_provider` 默认关闭（它暴露服务端 reranker 配置）。同一个 bank 的记忆分别过一次普通服务（flag 关）和一次 `failover_server`（主 reranker 指向 discard 端口 9，`rrf` 顶上，flag 开），断言 trace 点名了成员、且 failover 的 warning 行带着与该次 recall 的 start 行相同的 id——并发时能把散落的日志 join 回一次请求。
- **25c_consolidation_answer_per_fact**（#6164）：consolidation 的回答从"一串 creates/updates 列表"改成"**每条新事实一条裁决**（repeats / changes / ends / unrelated）"，因为小模型会在列表里丢条目。对 bank 的 API 不变：一次调用里旧观测就地结束、新观测记录、闲聊什么都不留。故事断言的是写入形状（`FactConsolidation`、`ObservationJudgement`、`batch_fact_id` 这几个 payload 原语），也就是"模型的输出格式换了，落库语义没换"。
- **65c_logged_out_llm_failover**（#6095/#6108）：ChatGPT 计划登录可以在运行中被撤销（refresh 返回 `invalid_grant`，本地会话被清空）。运行中的服务还能靠 failover 撑住，**一重启就再也起不来**——构造 primary 时抛异常，启动失败，容器无限重启，连完全不需要模型的 recall 也一起下线。故事的 server 以"空凭据目录作 member 0、stub 作 member 1"启动：能起来就证明修好了一半，之后的 retain/recall 证明链上后面那位确实在服务。
- **95c_document_delete_traces**（#6098/#6218）：`HINDSIGHT_API_LLM_TRACE_DELETE_WITH_DOCUMENT=true` 时，删文档要连它的请求历史一起删——该文档的 retain 调用，以及消费过它记忆的 consolidation 调用；同 bank 另一份文档的历史必须原样留着。flag 是 server 级，所以故事自带 server 与独立 schema，避免别的故事的 worker 认领它的任务。

- 断言风格是**全量 pin**：如 `test_01` 把 recall 响应的排序、四个分数的小数位、`chunk_id` 复合格式全部钉死。

前提：只需 `hindsight-api-slim` 的 `--extra embedded-db`（pg0），无 provider secrets；README 特别警告不要用 xdist（session 级单服务器使它无意义，本包也未装 pytest-xdist）。

**按后端可移植性分层**（1.0.0 起的 `memory_backend_incompatible` 标记）仍在：v1.1.0 实测 104 个文件带标记，本窗口 706 个测试文件里 **111** 个（上一窗口 105）（`grep -rl memory_backend_incompatible --include=*.py hindsight-api-slim | wc -l`）——凡断言或播种 Postgres 内部状态的测试（裸 `memory_units`/`memory_links`/`unit_entities`/`documents`/`chunks` 行、内部列），都是"在量存储布局而不是行为"，用 `-m 'not memory_backend_incompatible'` 摘掉后仍须在 Postgres 上跑。

**本窗口（核心改动 #6349 的测试侧）stub 从"宽容的假 provider"变成"会拒绝非法对话的假 provider"。** 两处配套：① `validation.py` 在 `validate_chat` 的逐条消息循环里新增一条拒绝——第 i 条是 `user` 而第 i−1 条也是 `user` 时报 `messages[{index}]: consecutive user turns; roles must alternate (roles: [...])`（`hindsight_system_tests/validation.py:82-88`）。它复现的正是 Gemma chat template 在 llama.cpp / vLLM 下的行为；把这条规则放进 stub，等于让**每一个** story 都顺带验证"任何一次请求都不含相邻 user"，而不是只在新写的 story 里验证。② `stub_server.py` 的具名回合识别从 `re.match`（只看开头）改成 `re.findall(..., re.MULTILINE)` 并取最后一个匹配（`stub_server.py:46`、`:77-79`）：既然请求现在会被合并成一条更长的 user 回合，`^Call \`x\` now` 不再位于字符串开头，注释写明了原因——"The request closes the last user turn, after the question or the previous result it is joined onto (Hindsight sends no two user turns in a row, #6349), so it is the last line that opens this way." 这是"契约改动先在黑盒层的假服务里落成一条可执行的断言"的一个小样本：核心只改了发送侧的拼装，测试侧则把"角色必须交替"变成所有 story 的公共前提。

### 8.3 hindsight-system-evals：质量评测（LLM-as-judge）

README 的第一张表仍是定海神针：system-tests 把每个 LLM 调用指到 stub 换来确定性；**eval 不能 stub——stub 模型就只能评出 stub 的好**。所以它继承黑盒形态但放弃确定性机制，连带两个后果：断言只能交给 judge，且单次红只是"重跑信号"，不是回归证据。落地时的三个工程细节支撑这句话：

- **judge 与被测模型强制分离**：`hindsight_system_evals/judge.py:1-9` 要求两者独立配置（同模型自评等于自我认同），fixture 在相同时告警（`evals/conftest.py:44-71`）；judge 后端走 `google-genai`（Gemini API key 或 VertexAI 服务账号），**从不经过 hindsight_api**。CI 配置即一例：被测 `gemini-2.5-flash-lite`，judge `gemini-2.5-flash`（perf-test.yml:348-354）。
- **温度去噪，且方向要对**：temperature-0 判出的单个 "not met" 会在更高温度下重问 `_CONFIRMATIONS`（默认 2，`judge.py:31`）次，**多数票才能维持一次失败**（`judge.py:123-145`）。再上一窗口改的是判据提示本身：JSON 字段顺序从 `{"meets_criteria": …, "reasoning": …}` 翻成 `{"reasoning": …, "meets_criteria": …}`（`judge.py:34-44`）——**生成顺序就是字段顺序**，verdict 在前时 judge 会先下结论、再写出相反的推理：一个 horse-farm trap 被 3 个 judge 里的 2 个判为"命中"，而它们自己的推理写着"没有任何观测断言了用户未明确提到的马匹数量"，于是一次正确的运行被判红。trap 判据的极性仍是反的——"命中"才是失败，所以 `evaluate(..., confirm_met=True)` 重问的是那个 "met"（`judge.py:116-131` 的 docstring 写明理由：平滑错了一侧，会把一次正确的 "not met" 用两次更宽松的重问推翻）。
- **每次运行全新数据库**：服务器默认起全新 pg0 实例（`hindsight-system-evals-<uuid>`，结束即 drop，`server.py:45-60`）——上一轮残留 bank 的排队任务若被 worker 认领会烧掉真模型的 token；也可 `--api-url` 指向在跑的服务器。

**再上一窗口把这个包整个重组了**（#6118，64 文件 +5376/−2093）。旧结构是 `evals/test_00…test_11` 十三个文件、按"主题"分；新结构是 **一个操作一个文件**：`evals/<operation>/test_<operation>.py`，操作共五个——`retain`、`recall`、`consolidation`、`reflect`、`refresh-pages`（`misc/` 另有 `test_coding_agents_metric.py` 的 6 个确定性测试，不走 `case_params`，不计入用例总数）。文件数从 13 降到 **6**（`find evals -name 'test_*.py' | wc -l`），但**用例没有减少**：它们被拆成带 category 的参数化用例，test id 就是 `<category>/<case id>`（例如 `test_retain[temporal/no-event-date]`）。

这个 id 形状不是装饰，它是整条报告链的主键。`case_params`（`hindsight_system_evals/report.py:112-121`）把每个 case 包成 `pytest.param(case, id=f"{case.category}/{case.id}", ...)`，不在最小验收集合里的再打一个 `full` 标记；所以同一个 id 同时服务三件事：`-k "temporal/"` 选一组跑；`--full` 只放开"非最小验收"的那些（默认跑 minimum，`full` 标记在 `evals/conftest.py:97-112` 被 skip）；运行结果按"操作 × category"聚合成 `by_category`（`report.py:98-102`），再被新命令 `eval-table` 并排成一张多模型对比表（`table.py:20-39`，入口在 `pyproject.toml` 的 `[project.scripts]`）。**为什么值得这么改**：旧的十三个套件只能回答"这套过没过"，而一个模型往往在某类能力上强、另一类上弱（README 的 retain 表就是 35 个用例在六个模型上的分布），没有 category 就没有可比性；而 category 又必须至少有两条用例，才不至于把一次抽样噪声读成能力差异——`tests/test_categories.py` 用 `pytest --collect-only` 把这条下限变成测试（`thin` 集合非空即失败）。

**规模重数**（方法：每个操作的用例数 = 该操作所有 test 文件参数化出来的 case，逐文件读源码清点；category 数 = 各文件里出现的不同 `category=` 取值）：

**口径**：`FOLLOW_UP_CASES`（`hindsight_system_evals/orchestration.py:127-157`，2 个 `category = "orchestration"` 的用例）在 `evals/reflect/test_reflect.py:521` 与 `evals/refresh-pages/test_refresh_pages.py:690` 各参数化一次，所以同一组 2 个用例会在两个操作下各跑一遍。上表按 **pytest 实际收集** 计：**127 个测试实例、44 个 `operation:category` 组**——用例数 42+23+25+17+20 = 127，组数 12+9+9+7+7 = 44（`tests/test_categories.py:70-87` 正是用 collect-only 按这个键分组校验"每组至少两例"）。本卷其余地方引用总数时统一用 127/44；跨操作复用的那 2 个用例计入两个操作的小计。

**retain：能力即用例**（`hindsight_system_evals/retain_capabilities.py`）。35 个用例覆盖 11 个 category（selectivity 3、completeness 2、attribution 4、temporal 4、language 3、fidelity 5、mission 2、mode 4、entities 2、entity_labels 3、inputs 3），每个都注明它来自哪条 prompt 规则、哪个 issue 或 commit。判定是双轨的：**judge** 看渲染后的事实（带 type、日期、实体），先判 `traps`（"事实说出了那个具体的错东西"，任一命中即失败）再判 `must`（"必须记下什么"，每条独立一次 judge 调用，所以失败能指名丢了哪条主张）；**确定性**的部分（实体、`key:value` 标签、tag、逐字文本、事实条数）直接断言，不花 judge。九条进最小验收。README 里那张"每个模型过了多少"的表是这个套件的**交付物之一**：它证明失败的是模型而不是用例（`gpt-6.1-sol` 35/35，`gemma-4-26b-a4b` 27–33/35）。

**recall：排序被测，且不花模型调用**。19 个能力用例，每个只在自己那几条记忆里搜索，但 bank 里另有约 300 条"别人的生活"作干草堆（`recall_haystack.py:31` 的 `HAYSTACK_SIZE` 默认 300，正好等于 reranker 的默认候选上限）——四个记忆的 bank 里任何保住正确事实的排序都及格，300 条里才分得出 RRF 与 cross-encoder。公平性由两条不变量守住、并由单测检查（`tests/test_recall_haystack.py`）：池子里的记忆**不得出现任何用例用于判分的词**，**不得落在某个时序用例所问的时间窗内**；每个用例还另带 decoys（只靠单路检索就会选中的错答案：日期在窗口内、共享 query 词、说的是别人）。用例的记忆由真实模型抽取一次后**冻结成 zip**（`fixtures/recall-cases/<case id>.zip`，19 个，`manifest.json` 记模型与录制时间），运行时导入归档、干草堆按原文写入（chunks 抽取、不调模型），所以一次运行**零 LLM 调用**就能评排序——分数动了，只能是排序动了。这也让"换 ranker"变成可 A/B 的变量：README 实测本地 cross-encoder 6/19、纯 RRF 10/19、决策模型 19/19。`prune`/`dedup` 两个开关的池子用例都在 `PRUNE_CASES` 里（3 个：1 个 `duplicates` + 2 个 `distinct`）：剪枝下"像但不同"的事实必须全留、无关的大多要走；去重下改写过的一次陈述要合成一条。

**consolidation：25 个场景，每个都复刻一次真实翻车**。事实按波 retain，每波等真实 consolidation 跑完，再评剩下的观测；用例分三处定义——`SCENARIOS` 19 个（`:74-575`）、`SCALE` 3 个（`:595`，30 个近似服务、20 个名字近似的人、以及同一批服务在 mission 下再跑一次）、`REPETITION` 3 个（`:606-724`，其中两个字面 `Scenario`，第三个是 `repetitive_service_bank()` 构造的 `repetitive-service-catalogue`）；category 九组（merge 3、update 4、recency 2、counts 2、entities 2、language 2、mission 4、scale 3、repetition 3），合计 25。除 judge 外每波都有确定性检查：证据存在且与 `proof_count` 相符（#4955）、日期来自证据（#501/#3477）、prompt 元数据不漏进正文（#2544）、每条持久事实都被引用（#5054）、纯复述的一波不新增观测。成本也一并记录（`HINDSIGHT_EVAL_CONSOLIDATION_COST=FILE` 每场景一行 JSON：调用数、输入/缓存/输出 token、LLM 秒数、从 retain 到稳定的墙钟），因为"更便宜的配置只有在同等质量下才算便宜"；triage 请求以 `decision_consolidation_triage` 单独计入，不和 LLM 调用混在一起。README 末尾那张"consolidation 能力清单"把每条规则标注为由 eval（真模型）、system-test（桩）、还是 unit test（api-slim）把守——三层的分工在这里第一次被逐条写死。

**reflect / refresh_pages：语料是生成器与 gold 一起产出的**。`corpus.py` 的每个事实属于一个共享 gold 词汇的簇，near-miss 只差一个属性（版本、环境、日期、数字、极性、实体）；七个问题覆盖 precision 3、update 1、aggregation 1、no_overreach 2。`sources.py` 再加六个来源权威问题（guide 与 chatter 冲突、只有 guide 能答、只有 chatter 能答、一次带日期的会议决定推翻 guide、规则加例外），于是 reflect 自有 15 个 case、6 个 category；refresh_pages 用同一批语料（作为页）加 `delta_updates.py` 的 8 个更新场景、`page-never-collapses` 与两个一致性场景，共 18 个、6 个 category。两者再各自挂上同一组 2 个决策编排用例（`FOLLOW_UP_CASES`，category `orchestration`），所以按收集口径分别是 17/7 与 20/7（见上表口径说明）。页与 reflect 的每个问题都判两次：先 `trap`（答案说出了被钓的那个具体假话），再 `correct`（答案不完整也算失败）。

**BEIR 从独立套件挪进了 recall 操作**，但性质没变：仍是唯一**不发任何 provider 调用**、也不需 judge 与密钥的一套（README 的说法是 "makes no model call"，指没有生成式模型调用；排序仍用本机 embedder/reranker），recall 直接对 SciFact 自带的相关性标注打分（k=1/3/5/10/20/100 的 nDCG/MAP/Recall/P/MRR/Hit + 无截断 MRR + R-precision，定义与 `pytrec_eval` 对拍——那个对拍抓出过 nDCG 用了指数增益而非线性）。语料仍是"构建一次、评测多次"：500 篇摘要抽成 **1,812** 条记忆（`fixtures/beir-scifact-bank.json` 记录 `documents: 500, queries: 50, facts: 1812`，模型 `gemini-3.1-flash-lite`、concise 抽取），冻结成 zip；评测期 `HINDSIGHT_EVAL_LLM_PROVIDER=none` 恢复归档、跑 50 条 query。指标地板与两道管线健全性断言（多数 query 须命中任一 gold；非剪枝模式下平均返回文档数须 >100）原样保留，定位仍是**基线不是 CI 门**。

**新模块 `orchestration.py`（157 行）解决一个很窄的问题**：decision-orchestrated reflect 先搜一次、问决策模型"这些证据够不够"、答"不够"就强制 LLM 再搜一次。LLM 是否**服从**这个强制轮，是模型与调用方式的属性，不是 bank 的属性——在小 bank 上第一轮通常就含答案，评答案根本看不出强制轮有没有发生。于是这个模块提供一个**脚本化决策模型**：对"证据是否充分"永远答 "partly"（中间档），并计数它被问了几次——只有在第二轮搜索真的跑过之后，才会被问第二次。其余问题一律给出"保持检索原样"的答案（候选按来序、全留、页全部相关）。这组用例（`FOLLOW_UP_CASES`，2 个）不在最小验收里，且每个用例**自起一个服务**（脚本化决策模型是 server 级配置），所以只在 `--full` 跑。它们几乎不评答案本身：建一个小 bank、retain 几条事实，让 reflect（以及 refresh-pages 里"把同一问题写成页"的那次刷新）跑一次，然后数决策模型被问了几次——`verdicts >= 2` 才算强制轮真的发生；模型若用 `done` 敷衍这一轮，桩只听到一次裁决。这是"要测的是机制而不是答案"的极端例子：把被测对象换成一个可数的副作用。

**发布契约**：运行结果写 JSON（`--output`），字段是仪表盘的契约（`report.py:1-5` 明说），含 `model_config`（序列化别名）、`by_kind` 与新增的 `by_category`；`mode` 记录这次是 `full` 还是 `minimum-acceptance`。`pytest_sessionfinish` 在**红色运行也照写**——对质量指标，红跑本身是数据点。CI 侧 `perf-test.yml:395-396` 默认 `--full`，手动 dispatch 可切 `minimum`；本包的 `tests/` 另有几个不花模型的单测（category 下限、表格式、A/B 开关透传、干草堆公平性、检索指标对拍），CI 把 `tests` 排在 `evals` 前面跑，因为"它们只要几秒，而那里坏了后面的评测结果就不作数"。

## 10. 必答问题速答

1. **coding-agent 集成的数据流？** 三段 hook 生命周期：SessionStart 注入种子（含 git 历史 ingest 与 daemon 冷启动）、UserPromptSubmit 注入 reflect 综合（每会话一次，budget low）或页/召回结果、Stop 读宿主 transcript 归一化为 `TransportTurn[]` 后以 JSONL 增量 upsert 到 `conversation:<sessionId>`（append 靠 cursor + `operationId` uuidV5 幂等）。harness 归因在这次 retain 里同时写入 tag `harness:<id>` 与 `metadata.harness`，控制面据此渲染 logo（§4.1、§5.4）。v1.1.0 在这条链上加了四个约束：git 日志只追加新提交（不再整篇重发）、调查每个提交最多启动三次、常驻插件型宿主把注入块放进本轮 **user 消息**而非 system prompt（否则逐轮变化的块会让供应商的前缀缓存每轮失效）、会话换 bank 时按 `segments` 只保存新 bank 名下那一段、回到旧 bank 走 append 而不是 replace（§4.1 的"种子半边""召回半边""写回半边"）。上一窗口又补了两处宿主边界：pi 的 custom-message run 没有 `prompt`（按空 prompt 处理，正好复用"空 prompt 丢弃上一轮注入块"的语义），OpenCode 2.2 起按包名解析并读 `exports["./server"]`——但 `exports["."]` 必须继续指向 v1 插件，否则按名解析的 v1 宿主会拿到 v2 的定义（§4.1(5)）。本窗口的 0.8.6 又把上一版 (6)A 的借用顺序推翻：没有自己配方的宿主不再借别的 CLI（§4.1(7)）。
2. **SDK 纯生成还是混合？** 混合：四语言全部由 `hindsight-docs/static/openapi.json` 生成底层，Python/TS 各有 **3367/2230** 行手写 wrapper 高层类，Go/Rust 手写部分极薄。**本窗口的再生成是 16 个文件**（Go 4 / Python 8 / TypeScript 4 / Rust 0），而 spec 的 path/operation/schema 仍是 **79/101/203**、`info.version` 仍是 1.2.0——变的是 document PATCH 的 `add_tags`/`remove_tags`、bank 统计的 `paused_mental_models`、mental model 的 `candidate_rejected` 与两处描述（§3.3）。手写层两边处理不同：TS 的 `updateDocument` 补了 `addTags`/`removeTags`/`observationScopes` 映射与一个映射测试，Python 因为根本没有 `update_document` 高层方法，只改了一行 docstring。上一窗口（v1.2.0）的再生成波及 **463** 个文件（Python 232、Go 230、TypeScript 1、Rust 0），几乎全是版本注释；更早一窗口 31 个文件（Python 14、Go 9、TypeScript 6、Rust 2）并多出 2 个模型。新参数同步靠"生成物入库 + CI 四守门"（test.yml:5627/5715/5780/5820：verify-generated-files 无 diff 校验、openapi 兼容性检查、CLI 覆盖检查、client coverage 检查手写层漏参）（§3.2-3.4）。
3. **fs mount 怎么映射文件树？** knowledge-base 的文件夹→目录、页→`slug(name).md`（撞名加 id 后缀），正文取 export bundle；一次同步 = tree+export 两次 HTTP；以磁盘字节为真值做漂移回写，`0444` 只读 + 原子写 + 失败不修剪；后台 daemon 是 `setsid` 的自身进程（POSIX only），state.json 保 mtime 稳定（§2.4）。
4. **control-plane 纯 BFF 还是有存储？多用户鉴权在哪做？** 纯 BFF，无任何自有存储；鉴权是**单访问密钥**（`HINDSIGHT_CP_ACCESS_KEY`）+ 无状态 HMAC 会话 cookie，在 CP 的 middleware 完成，dataplane 只见服务端注入的 Bearer key。未配置密钥时全放行（本地单机模式）(§5.3)。dataplane 的新参数（如 recall 的 `rerank`）在 CP 只做透传：route 解构、`lib/api.ts` 加类型、原样交给生成层（§5.2）。
5. **三层测试的分工与运行前提？** 先看规模（本窗口重数）：api-slim 单元/集成 **706** 个测试文件（`find tests -maxdepth 1 -name 'test_*.py' | wc -l` → 706，递归同值；上一窗口 684，本窗口 +22；其中 **111** 个带 `memory_backend_incompatible` 标记（`grep -rl … | wc -l`），在替代存储上应被 deselect）、system-tests **108** 个 story 文件（本窗口 +8，另在 `test_55_bank_aliases.py`/`test_73_decision_model_recall.py` 各加一个测试）、system-evals **6** 个文件 / **5** 个操作 / **44** 个 `operation:category` 组 / **127** 个收集到的用例（44 组 = 12+9+9+7+7；BEIR 与若干 benchmark 不算 case；本窗口 `evals/` 与 `tests/` 零代码改动，数字沿用上一版的静态清点）。system-tests：stub 全接管 LLM/embeddings/rerank + pg0 内嵌库 + editable 发布客户端，无需密钥，fork PR 可跑（CI `test-system` `:3672`，故意不设 secrets 门控）；本窗口桩新增"任意维度 embeddings + 调用记录"与"决策模型可整体报错"两个能力，并把 keep-alive 抬到 60s（§8.1）。integration-tests：要活服务器或 docker-compose，测 MCP/部署形态（CI `test-integration` 需 secrets，`:3550`），本窗口零改动。system-evals：真实模型 + 独立 judge（多数票去噪，trap 判据反向确认）+ 每轮全新 pg0，需要密钥；默认只跑 minimum 集（`full` 标记的用例被 skip），CI 的 `perf-test.yml:395-396` 默认 `--full`，手动 dispatch 才切 `minimum`；recall 的 19 个能力用例与 BEIR 一套**零 LLM 调用**（记忆冻结在归档里，排序仍走本机 embedder/reranker），因此不需要 provider 密钥，是唯一能在无密钥环境跑的两块。LoComo/LongMemEval/BEAM/PersonaMem/sde-bench 的数据与评分完全外包给 AMB 仓，`run-amb` 只是适配入口（§8.3）。
