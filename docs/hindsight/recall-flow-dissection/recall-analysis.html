2专章:四臂为什么变两臂

2.1 先认识四个臂:每个臂是干什么的

上游的四臂不是一个平行的清单,而是一张递进的信息网:

  1. semantic(向量)——找"意思像的"。问"围挡干完没",靠语义相似找到事实A。两边都实现,是唯一两边都指望得上的臂。上游有相似度地板 0.3(config.py:1309);产品没有(query.py:636 semantic_min=-1)。
  2. BM25/keyword(关键词)——找"字面同的"。问"QB-9",靠字面命中编号。上游把词用 |(OR)拼接,命中任一词即可(sql/postgresql.py:463-464);产品用 plainto_tsquery(AND,native_query_sql.py:261),所有词都得出现——合同自己写明"不声称上游OR-token等价"。
  3. graph(图扩展)——找"和已找到的说了同一件事的"。它不是独立召回:先拿 semantic 高分命中(≥0.3 的前 20 个)当种子(link_expansion_retrieval.py:46),做一轮三路扩展:①实体路:在 unit_entities 里找共享同一实体的事实(事实B 因为也提"青桥项目"被拉进来,ops_postgresql.py:941-981);②语义路:沿 retain 时预计算的 kNN 相似边;③因果路:沿 caused_by 等因果边。
  4. temporal(时间)——给带日期的问题兜底。有"10月"这类时间约束才跑(postgres.py:155);窗口来自调用方或 CPU 日期抽取(retrieval.py:854-874);过滤 occurred/mentioned 三列(:575-584)。核查修正:过滤后排序仍按向量距离,窗口只管本臂、不约束其他臂——上游也不是"时间过滤得很干净"。

2.2 产品现状:两臂,还各带一处简化

上游产品
semantic地板 0.3(候选更精)无地板(候选更全也更脏,全交给重排兜底)

上游本来就能用 bank 级开关降级成两臂(config.py:1929-1931)——产品的两臂形状上≈上游"关掉 graph/temporal"的配置态,但三处不等价:keyword AND vs OR、语料收窄到 world/experience base facts(上游含 observation 等全部类型)、能力面整体拒绝。

2.3 为什么会变成这样:四个原因(按证据强度排序)

  1. 最硬的原因:图臂的"米"根本没种——写侧不产数。产品 retain 投影只写 documents/chunks/memory_units/memory_links 四张表(native_projection.py:112);实体解析被合同整体关闭(native_retain.py:269-270 原话 "Entity resolution and user entities are closed");现有边只有 entity_id=None 的因果边。entities/unit_entities 表建了但是空表(native_catalog.py:167-301),连图臂依赖的实体优先索引都没建。就算把图臂代码接上,它也只能走因果单路。
  2. 时间臂缺"窗口来源"这块零件。四个时间列在 QP01 例程里现成可用(native_sql.py:427;native_query_sql.py:101-102)——数据不缺,缺的是:上游窗口要么调用方传、要么 CPU 日期抽取件,产品两者皆无,还在边界拒收窗口参数。
  3. 治理成本:加臂从开关问题变成重注册问题。上游关/开臂是 bank 级布尔;产品每动一个 SQL 例程 = 重写 baseline_sha256(native_sql.py:683)+catalog seal+execution_contract_digest+新 pair 注册与激活(INTERFACE.md:39-41),旧 READY 不许 patch。
  4. 设计意图:base 链先行,breadth 后补。首发计划把"Retain→base Recall"定位为中间检查点(NEXT-STAGE-PLAN:13),图/时间/原文入口明确排到 D8/T11(:47)。两臂是把第一版验收面压到最小的主动裁剪。

2.4 定性:设计分期 + 明示边界,不是实现 bug

  • 对当前 base Query 合同:两臂是合同明示范围(NATIVE-SEAM.md:45),拒绝是 fail-closed 设计——不是缺陷。
  • 对 S1 全量设计:MP-03 明文要求"向量、关键词、图关系和时间检索",FIRST-RELEASE-SCOPE.json 未后置——两臂态是未完成的中间态,承接包 D8/T11。
  • 两处有意识的简化(不是 bug,后果要认账):keyword OR→AND;semantic 去掉 0.3 地板。
  • 一处继承+收紧:english 是上游默认值,但上游可换配置/后端(pgroonga bigram 等对中文有效),产品把可配置面锁死。
  • 一个计划结构观察(推断,非文档原义):图臂的数据前提在 retain 写侧,而 D8 只覆盖读侧入口——这条写侧前置在当前计划里没有显式承载包。

2.5 两臂会导致什么:四个案例

案例1 · 编号查询 "QB-9"

上游:预分词切成 qb、9,OR 拼接——命中任一即中。文档侧"青桥项目QB-9"无空格时"项目qb"粘成一个词元 推断,但 "9" 独立,OR 靠 "9" 仍命中。

产品:AND 要求 qb 和 9 都命中——"qb" 粘死了,可能整条漏掉。

大白话:AND 比 OR 苛刻;写事实时给编号两边留空格("…项目 QB-9 …")两边都能中。PG 推断,待实跑

案例2 · 关联事实 "青桥项目的相关方有哪些"

上游:semantic 先命中 A/C,graph 臂沿共享实体"青桥项目"把 B 拉进候选——这是 B 的主要通道。

产品:没有图臂。但小库(4 条事实)下 semantic 无地板,B 必进 top-k,只是排尾;真正漏召发生在大库——top-k 被更相似者填满时。

大白话:产品把"找关联事实"从检索问题变成了重排问题,库越大越吃亏。实体抽取成功与否 UNKNOWN

案例3 · 时间查询 "10月第一周的施工进展"

上游:中文规则里没有"N月第M周",最可能解析成整个 10 月;窗口只管 temporal 臂自己,排序仍按向量距离——D 仍可能从其他臂混进结果。

产品:候选层零日期谓词,时间约束传不进来;C 靠文本相似进候选,D 混入是真实风险。

大白话:丢时间臂 = 排序变差 + 无过滤;但别指望上游的时间臂本来就精确。

案例4 · 纯中文 "围挡施工完成了吗"

两边:纯中文在 english 配置下都切成一个整串词元,keyword 臂都失配 推断,都只剩 semantic 臂。

差别:上游 english 是可改的默认(换 regconfig 或 pgroonga bigram 后端),产品是协议级锁死。多出的 graph/temporal 臂对纯中文也帮不上。

大白话:"中文检索弱是继承上游"在默认部署下成立;产品额外放弃了换配置的退路。
