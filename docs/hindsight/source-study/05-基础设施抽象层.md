# 第 1 层【全景】：为什么要有一个可插拔的 provider 层

## 1.1 三个抽象，一个形状

Hindsight 的记忆引擎有三处必须"调用模型"：

| 能力 | 抽象基类 | 代码位置 | 典型实现数 |
|---|---|---|---|
| LLM（抽取/反思/固化） | `LLMInterface` | `hindsight_api/engine/llm_interface.py:78` | 32 个 provider 名字，17 个实现类 |
| Embedding（向量检索） | `Embeddings` (ABC) | `hindsight_api/engine/embeddings.py:142` | 13 个 provider 分支 |
| Reranker（重排） | `CrossEncoderModel` (ABC) | `hindsight_api/engine/cross_encoder.py:108` | 15 个 provider 分支 + failover 链 |

三者形状高度一致，都是同一个模式的实例化：

1. **抽象接口**声明最小能力面（`call` / `encode` / `predict`）；
2. **工厂函数**按配置字符串分派到具体实现（`create_llm_provider` / `create_embeddings_from_env` / `create_cross_encoder`）;
3. **默认值**全部落在 `config.py` 的 `ENV_*` / `DEFAULT_*` 常量里，实现类不读环境变量（LLM 侧甚至被注释明确要求"构造函数不读全局 config"——`llm_wrapper.py:922-925`）。

除此之外还有第四个同形状的可插拔面——**文件存储**（上传附件的 `engine/storage/`，`create_file_storage` 工厂 + `FileStorage` ABC），它不调模型但同属基础设施抽象，0.10.2 起获得流式读写能力，见 3.10。

为什么必须可插拔？从代码里可以直接读出三个动机：

- **本地/离线运行是一等公民**。`llamacpp_llm.py:1-12` 的 docstring 写明 "fully offline operation"：provider 会自己下载 GGUF（llama.cpp 的单文件模型格式）模型、起 `llama-cpp-python` 子进程；embedding/reranker 默认就是本地模型（`DEFAULT_EMBEDDINGS_PROVIDER = "local"`，`config.py:1278`；`DEFAULT_RERANKER_PROVIDER = "local"`，`config.py:1340`）。
- **订阅账号复用**。`openai-codex`、`chatgpt`、`claude-code`、`cursor`、`github-copilot`、`xai-oauth`、`nous` 这一批 provider 的存在，说明项目要"用你已有的 ChatGPT Plus / Claude Pro / Copilot / SuperGrok 订阅"跑记忆管线，而不是强制 API key（`hindsight_api/provider_auth.py:16-35` 明确列出了无需 API key 的 provider 集合；其中 `chatgpt` 走 OpenAI 的 "Sign in with ChatGPT" OAuth 流——见 3.3.4）。
- **测试与降级**。`mock` provider 让 600+ 个测试文件（hindsight-api-slim/tests 实测 648 个 `test_*.py`）不碰网络；`none` provider 让系统退化成"纯 chunk 存储 + 向量检索"（`none_llm.py:1-8`）。

## 1.2 分层配置解决什么问题

配置体系是三级：**全局 env → 租户（扩展钩子）→ bank（数据库）**（`config_resolver.py:1-9` 的模块 docstring 原话；路径说明：`config_resolver.py` 与 `config.py` 同在 `hindsight_api/` 根目录、不在 `engine/` 下，本文下文裸写同此约定）。

> **术语约定**：bank 是 Hindsight 的隔离与配置单元——一个 bank 即一个独立记忆库（相当于某个用户/agent 专属的一颗"脑"），对应数据库 `banks` 表的一行；下文"bank 级覆盖"即按记忆库覆盖配置。

它解决的问题分两类：

- **多租户/多 bank 的行为隔离**：不同 bank 可以有不同的 retain 策略、召回预算、disposition（1-5 的怀疑/字面/共情度）——这些是"行为字段"，落在 `banks.config` JSONB 里，逐 bank 解析。
- **防误用**：全局配置单例被一个代理包住——`get_config()` 返回 `StaticConfigProxy`，访问任何 bank 可配置字段直接抛 `ConfigFieldAccessError`（`config.py:62-90`），强制开发者去走 `ConfigResolver.resolve_full_config(bank_id, context)`。这是一个用类型系统之外的运行时手段实现的"你在热路径上读错配置了"的警报。

**一个必须先纠正的常见误解**：CLAUDE.md 的通用指引说"LLM settings (provider, model, API key) 是 hierarchical 可逐 bank 覆盖的"，但**当前代码并不是这样**：

- `llm_provider` / `llm_model` / `llm_base_url` / `llm_api_key` **不在** `_CONFIGURABLE_FIELDS`（可被 bank/租户覆盖的行为字段白名单，详见 3.7）里（`config.py:3986-4062` 全量枚举里没有任何 provider/model 字段；`config.py:3983-3985` 的注释原话："Excludes credentials, infrastructure config, **provider/model selection**, and performance tuning"）。
- `llm_api_key`、`llm_base_url` 反而显式列进 `_CREDENTIAL_FIELDS`，禁止通过 API 写入（`config.py:3905-3981`；写入侧在 `config_resolver.py:523-529` 直接 `raise ValueError`）。
- bank 级唯一能动的 LLM 链路参数类字段是 `llm_gemini_safety_settings`（`config.py:4059`；decision model 的三个"用不用"开关是行为字段而非链路参数，见 3.7）。

也就是说：**provider/model 的切换发生在两个层级——进程级 env（全局默认）与操作级 env（`HINDSIGHT_API_RETAIN_LLM_MODEL` 等，仍是服务器级）**，bank 只能影响"行为参数"。这是本文后面所有例子的前提。（1.0.0 新增的两个"例外通道"都不破坏这一前提，但值得点名：其一，decision model 的 `*_use_decision_model` 开关进了可配置白名单——bank 能决定"要不要用决策模型"，但选不了是哪个（见 3.7）；其二，#5578 的 LLM request extension 让操作员代码在**服务端**逐调用替换 LLM 与凭据——同样不经 bank 配置（见 3.7 末段）。）

# 第 2 层【主流程】

## 2.1 一次 LLM 调用的完整路径

### 静态骨架：谁在什么时候创建了 provider

`MemoryEngine.__init__` 在进程启动时为 retain / reflect / consolidation 三个操作各建一条 LLM 链（`memory_engine.py:2801 / 2897 / 3020`）；第四条——mental-model-refresh——0.10.2 起改为**按需解析的 property**（`memory_engine.py:15361-15376`，issue #4463）：没有 `MENTAL_MODEL_REFRESH_LLM_*` 覆盖时它**就是**当前 `_reflect_llm_config` 这个对象本身（连测试在 `__init__` 后换掉的 provider 也一并生效）；override 只为"给 refresh 一个更长 timeout"时同样让位给被换入的 reflect provider：

1. 先解析"操作级请求默认值"：`_op_defaults()`（`memory_engine.py:2696-2714`）把 `HINDSIGHT_API_RETAIN_LLM_TIMEOUT` / `..._MAX_RETRIES` / `..._INITIAL_BACKOFF` / `..._MAX_BACKOFF` 逐字段落到"没配就回落全局 `llm_*`"。`mental_model_refresh_` 这一组仍以 reflect 的已解析值为 fallback（`memory_engine.py:2715`），但 0.10.2 起有一处刻意的例外：**timeout 永不继承 reflect 的**（reflect 默认 30s 是给"调用方在线等"定的，refresh 是后台任务、最终答案要过 3 万-9 万 token 的 prompt，30s 每次重试都超时，动机注释 `memory_engine.py:2716-2723`、replace 覆写 `:2724-2727`，issue #4532）——refresh 取自己的 `mental_model_refresh_llm_timeout`，否则回落全局。
2. 用静态配置构造 `LLMConfig`（即 `LLMProvider` 的向后兼容别名，`llm_wrapper.py:1957`）作为链首成员（member 0——多链场景下 `MultiLLMProvider` 的主成员，机制见 3.2 末段），再交给 `_build_llm()`：如果配置了 `llm_members` + `llm_strategy`，就把 indexed 成员（`HINDSIGHT_API_<OP>LLM_<n>_*`）包成 `MultiLLMProvider`（failover / round-robin / metadata 三种路由，`multi_llm.py:1-29`；加权轮询用 nginx 的 SWRR（Smooth Weighted Round-Robin，平滑加权轮询）算法，`multi_llm.py:78-102`）。
3. `LLMProvider.__init__` 里真正的分派只有一行：`self._provider_impl = create_llm_provider(...)`（`llm_wrapper.py:1097`）。

`create_llm_provider`（`llm_wrapper.py:458-827`）是整个 LLM 层的分派中枢。1.0.0 起它的开头只有一行惰性导入——`from . import providers`（`llm_wrapper.py:542`，上一行 :541 注释原话 "Each provider (and its SDK) loads only when chosen; see providers/__init__.py"）——每个 provider 类经 `providers.X` 按需取（PEP 562，见 3.2）。它的完整清单（以代码枚举为准）：

关键步骤逐条对应代码（图内各消息标签为缩写示例，完整 stage 命名见第 1 步与第 4 步）。1.0.0 起列表之前多了一道**第 0 步**：`call()` 一进来先问 LLM request extension——操作员注册的扩展槽可以只换凭据（网关虚拟 key）或整条换掉 LLM，被拒绝的调用在创建任何东西（比如 provider 侧缓存）之前就短路（`llm_wrapper.py:1245-1262` 的 `bind_llm_request`，扩展契约在 `extensions/llm_request.py`，#5578；详见 3.7 末段）：

1. **stage 面包屑**：进入 `LLMProvider._call` 先打 `.queued`，拿到并发许可后才切到真实 stage（`llm_wrapper.py:1310-1327, 1384-1396`）。这是为了解决 issue #3002 ——一个在信号量前排队太久的调用，以前看起来像 provider 慢。
2. **重试参数三级解析**：显式 per-call 参数 > provider 构造时的配置（per-op env 回落全局）> 方法默认（`call` 是 10/1.0/60.0，`call_with_tools` 是 5/1.0/30.0）（`llm_wrapper.py:1329-1341`）。
3. **strict_schema 一次性解析**：per-call 显式 `True/False` 双向都赢，否则读 `HINDSIGHT_API_LLM_STRICT_SCHEMA`（`llm_wrapper.py:1343-1358`；注释强调"`or` 会把 per-call False 和未设置混在一起"）。
4. **并发许可**：`scope` 字符串前缀映射到操作桶（`retain` / `reflect` / `consolidation` / `mental_model_refresh`——中文对照：写入抽取 / 问答推理 / 观察固化 / 心智模型刷新，`llm_wrapper.py:117-135`），先拿 per-op 信号量再拿全局信号量（"先窄后宽"排队，`llm_wrapper.py:138-163`）。1.0.0 起（#5597）桶的判定多了一层：refresh 后台跑的是 reflect agent、其调用 scope 仍是 `reflect*`，所以 `_semaphores_for_scope` 先看当前 trace 绑定的操作、再回落 scope 前缀，否则后台 refresh 的调用会挤占交互式 reflect 的桶（`llm_wrapper.py:147-153`）。全局默认 32（`DEFAULT_LLM_MAX_CONCURRENT`，`config.py:1231`），信号量是 `CrossLoopSemaphore`——进程内多事件循环共享的信号量，因为模块级 `asyncio.Semaphore` 会绑死在第一个等待它的循环上（实现已抽到 `_cross_loop.py`）。
5. **attempt-scoped 并发**：自带重试循环的 provider（anthropic、openai 兼容系、gemini、codex、claude-code、cursor、copilot、litellm、llamacpp、xai-oauth、openai-responses 全部实现了 `supports_attempt_scoped_concurrency`）不走第 4 步的整体持有，而是每个上游 attempt 用 `attempt_context` 现取现还，让退避睡眠不占许可（`llm_wrapper.py:181-199, 1384-1401`）。
6. **provider 内部**：`AnthropicLLM.call` 把 OpenAI 风格 messages 拆成 `system` + Anthropic messages，system 块加 `cache_control: ephemeral` 内联缓存标记（`anthropic_llm.py:90-120`）；strict 模式把 response schema 包成一个强制 `tool_use` 工具做约束解码（`anthropic_llm.py:346-372`）；然后进自己的重试循环（401/403 立即失败，429/5xx/连接错误/超时指数退避 + 20% 抖动，`anthropic_llm.py:385-545`）。1.0.0 起循环里多一个立即失败的分支：SDK 响应的 `stop_reason` 是 `refusal`/`content_filter` 时直接抛 `ProviderContentPolicyError`——以前这会被当成 invalid JSON 重试到耗尽（#5616，`anthropic_llm.py:42-53`）。每次 SDK 调用还包了一层 `asyncio.wait_for` 墙钟上限——SDK 的分相位 read timeout 每收一个字节就重置，上游"滴漏式" keep-alive 永远触发不了它，调用会把 worker 槽位钉死（issue #4763，`anthropic_llm.py:392-396`）。
7. **usage 先 stash 再解析**：`stash_response_usage` 在本地 JSON 解析/校验**之前**记录 token 数，这样解析失败也能把已计费的成本记进 trace（`anthropic_llm.py:398`，issue #2387）。
8. **成功上报**：metrics 采集器与 OTel span recorder 各有一个**同名**的 `record_llm_call` 方法（分属 `metrics.py` 与 `tracing.py`，前者记指标、后者记分布式 span），外加慢调用日志（>10s 带 token 明细）（`anthropic_llm.py:455-500`）。
9. **出口消毒**：`LLMProvider.call` 最后统一 `sanitize_value(result)`（`llm_wrapper.py:1452`）——剥掉模型输出里可能存在的孤立代理对（`\udXXX`）和控制字符，否则 asyncpg 写库、cross-encoder 的 Rust tokenizer（3.5 的本地重排模型分词用）、stdout 全都可能炸（issue #3729）。

### bank 级覆盖如何注入（示例 B）

**示例 B：bank 覆盖 `llm_gemini_safety_settings`**。操作入口（如 retain，`memory_engine.py:7594`、`:13286`）会执行：

```python
retain_llm = self._retain_llm_config.with_config(resolved_config, bank_id=bank_id, operation="retain")
```

`with_config` 生成一个轻量代理 `ConfiguredLLMProvider`（`llm_wrapper.py:1747-1788` 是 `with_config` 方法体，`ConfiguredLLMProvider` 类体在 1847-1930），每次 `call` 前把 bank 解析出的 safety settings 塞进 ContextVar、同时绑定 trace 上下文，调用后复位（`llm_wrapper.py:1880-1904`）。该注入对所有 provider 无条件发生，非 Gemini 的 provider 直接忽略这个值（ContextVar 只有 GeminiLLM 会读）：

```python
# hindsight_api/engine/llm_wrapper.py:1880-1888
async def call(self, messages: list[dict[str, Any]], **kwargs: Any) -> LLMCallResult:
    from .providers.gemini_llm import _safety_settings_ctx

    token = _safety_settings_ctx.set(object.__getattribute__(self, "_gemini_safety_settings"))
    trace_token = self._bind_trace_context()
    try:
        return await object.__getattribute__(self, "_provider").call(messages=messages, **kwargs)
    finally:
        _safety_settings_ctx.reset(token)
        self._reset_trace_context(trace_token)
```

- 代码里的 `object.__getattribute__(self, ...)` 是刻意为之（代码注释 :1857 原话 "avoid triggering __getattr__"）：直接读取代理对象自己的真实属性（`_provider` / `_gemini_safety_settings`），避免属性缺失等场景下落入本类 `__getattr__` 的透传。
- `ContextVar` 是 Python 的任务级局部存储——比 `threading.local` 更细，同一事件循环内每个 asyncio task 各一份。之所以用 ContextVar 而不是直接传参：provider 实例是全 bank 共享的长命单例，bank 级状态不能挂在它身上，只能在调用边界现场注入、调用后复位，嵌套安全且不泄漏（`llm_wrapper.py:1757-1765` 的 docstring 明确说"不更换底层 provider 或其长连接"）。
- attribute 全部 `__getattr__` 透传给底层 provider，调用方无感（`llm_wrapper.py:1875-1876`）。
- `trace_id` / `operation_span_id` 每次 `with_config` 生成一次，同一次操作的所有 LLM 调用共享，在 `llm_requests` 表里复现 OTel 的 父(操作)→子(LLM call) 层级（`llm_wrapper.py:1772-1786`、`llm_trace.py:59-78`）。
- 对于 `MultiLLMProvider`，`route_for(metadata)` 能在保持同一 trace 上下文的前提下换到 metadata 路由选中的成员（`llm_wrapper.py:1909-1930`）。

0.10.2 起 `rerank` 的返回值是 `RerankResult`（`results` + `provider_name`，`search/reranking.py:20-29`）：分数与"是谁打出来的"作为一个整体返回，because 并发请求会移动 failover 链的共享游标（详见 3.8）。`CrossEncoderReranker.rerank`（`engine/search/reranking.py:373-512`）把每个候选拼成 `[query, doc_text]` 对（doc 前面带 `[Date: ...]` 人类可读日期），调 `cross_encoder.predict(pairs)`，然后做分数归一：外部 API reranker（Cohere/Jina 等）返回的已经是 [0,1] 就直接用；本地模型输出 logits 则过 sigmoid（`reranking.py:462-475`）。NaN 一律清洗为 0。之后才是 recency / temporal / proof（证据条数）三个乘性 boost 的合成——代码是纯乘法 `combined_score = CE_normalized × recency_boost × temporal_boost × proof_count_boost`（`reranking.py:200` 公式注释、`:305` 实现），不是加权和——再按 `fact_budget` 做 token 预算截断。

`reranking` 参数有三个合法值：`"cross_encoder"`（默认）、`"rrf"`、`"interleave"`（`memory_engine.py:760`），bank 级 `enable_reranking=false` 时 `cross_encoder` 自动降级为 `rrf`（`memory_engine.py:1680-1689`）。1.0.0 侧注：给 recall 配置了 decision model 时（`HINDSIGHT_API_RECALL_DECISION_MODEL_*`），这里的 reranker 整个换成 `DecisionModelReranker`、重排语义不同——机制归 03 卷，本卷只涉及它的配置入口（`search/reranking.py:330-333` 按 `get_config().decision_model_config("recall")` 装配，见 3.7）。

几个有代码依据的细节：

- **浅拷贝而非 `asdict()`**：`_with_overrides` 用 `copy.copy` + `setattr`，注释里给出量级——config 有 400+ 字段、解析在每请求热路径上，旧实现的全量深拷贝曾主导 recall 耗时（`config_resolver.py:209-226`，issue #4209）。
- **bank 覆盖的读取**：`_load_bank_config` 查 `SELECT config FROM banks WHERE bank_id=$1`，走 `bank_info_cache` 进程内缓存；**缓存的是原始 JSONB 列而不是解析后的 overrides**，因为权限过滤因调用方而异，缓存解析结果会把一个调用方的权限漏给另一个（`config_resolver.py:387-457`）。
- **缓存一致性**：`_persist_bank_config` 写完立刻 `bank_info_cache.invalidate(bank_id, "config")`（`config_resolver.py:708`；批量改名路径 :738 同样失效）；而 `get_bank_config(cached=...)` 的默认值区分了两种调用方——读路径可以容忍一个 TTL 的滞后，"用户读回自己配置"的端点必须传 `cached=False` 读库，否则没执行写的那只 pod 会把刚写进的值读回旧值（`config_resolver.py:267-305`）。
- **写的原子性**：bank 配置写路径在事务里 `SELECT ... FOR UPDATE` 锁行、对"跨字段约束"（`retain_chunk_size` vs `retain_max_completion_tokens`、`recall_budget_min <= max` 等，`config_resolver.py:57-68`）用"投影后的完整配置"重验一遍再 `COALESCE(config,'{}') || $1::jsonb` 合并写入（`config_resolver.py:654-711`，COALESCE 合并在 :694-699）。注意这个跨字段复验**只在更新触及 `_CROSS_FIELD_CONSTRAINED_FIELDS` 集合内的字段时才执行**（`config_resolver.py:627-641, 684-690`）——不触及即不可能改变约束两侧，无需重验。注释解释了为什么用悲观锁：校验会跑租户配额钩子，必须只跑一次，乐观锁的重试方案做不到。
- **写校验漏斗**：`validate_bank_config_updates`（`config_resolver.py:484-653`）依次做 key 归一化（接受 `HINDSIGHT_API_*` env 风格或 Python 字段风格）→ 拒绝 credential 字段 → 拒绝非 configurable 字段（static 字段与未知字段分开报错）→ 租户权限检查 → 逐字段类型校验（从 dataclass 注解反推运行时类型；个别字段接受形态比注解更宽，由手工放宽表 `_WIDENED_FIELD_TYPES` 放行，`config_resolver.py:745-749`；类型校验本体 `_configurable_field_types`/`_value_matches_type`，`config_resolver.py:770-792`，针对 issue #3218"对象存进字符串字段后 bank 固化永久失败"）→ 各领域校验（entity_labels、recall budget、disposition 1-5 整数、**consolidation_strategies 形状校验**——0.10.2 新增 `_validate_consolidation_strategies`（`config_resolver.py:839-861`，调用点 :611-613）：config 侧类型只是 plain list，没有这一步时把 "scope" 写成 "scopes" 或把字符串塞进 tag 列表会被原样存库然后被固化阶段静默忽略，现在用 `StrictConsolidationStrategySpec` 在写入时按 shape 拒绝；不完整的草稿（还没填 tags 的规则）仍然放行，因为控制平面按 typed 保存、固化阶段会跳过不可用的策略）→ 跨字段投影校验。
- **读容错**：历史脏数据由 `_coerce_stored_bank_overrides` 兜底——字符串字段里的 JSON 对象会被 `json.dumps` 成文本（保住意图），其他类型错误直接丢弃回落全局（`config_resolver.py:883-933`）。

# 第 3 层【机制深潜】

## 3.1 LLMInterface：接口设计、structured output 与 token 计数

> **structured output** 指让模型按调用方预定义的 schema 返回可机器解析的数据（而非自由文本）。本层的做法：调用方传一个 pydantic 模型作 `response_format`，provider 层负责把它变成各家 provider 的约束机制，并把回复解析/校验回同一个模型实例。

### 核心方法签名

`LLMInterface` 的两个抽象方法（`llm_interface.py:156-203, 205-239`）：

```python
# hindsight_api/engine/llm_interface.py:156-171（节选）
@abstractmethod
async def call(
    self,
    messages: list[dict[str, str]],
    response_format: Any | None = None,
    max_completion_tokens: int | None = None,
    temperature: float | None = None,
    scope: str = "memory",
    max_retries: int = 10,
    initial_backoff: float = 1.0,
    max_backoff: float = 60.0,
    skip_validation: bool = False,
    strict_schema: bool = False,
    cached_prefix: str | None = None,
    attempt_context: Callable[[], AbstractAsyncContextManager[None]] | None = None,
) -> LLMCallResult: ...
```

返回值是 `LLMCallResult`（`engine/response_models.py:133-159`）：`content: Any`（传了 `response_format` 时是已校验的 pydantic 实例，否则是文本）+ `usage: TokenUsage`。签名里的 `scope` 默认 `"memory"`，决定并发归入哪个操作桶——不属于 retain/reflect/consolidation/mental_model_refresh 四桶的 scope（验证探针、memory_think 等）只吃全局上限（`llm_wrapper.py:119-123, 155-156`）。docstring 里记录了一段演进史：`call` 曾经按 `return_usage: bool` 布尔参数返回两种形状，导致 14 个实现都标 `-> Any`，现在无条件返回命名模型，与 `call_with_tools -> LLMToolCallResult` 对齐。

**prompt 缓存的两级参数**（0.10.2 增量窗口内由 #5123/#5245 引入）：接口层的 `cached_prefix` 传的是**句柄**（`get_or_create_cached_prefix` 返回的 cache 名）；而编排层 `LLMProvider.call` 另收一个 `prompt_cache: PromptCachePrefix | None`——一个 frozen dataclass（`system_instruction` + 可选 `response_schema`，`llm_interface.py:57-71`），只声明"**什么内容**想被缓存"。之前 retain/consolidation 自己找链首成员要句柄再传 `cached_prefix=`，多链 failover 到 Gemini 时 fallback 成员永远没缓存（主成员的句柄落到别的账号上也不可用）；现在调用方只传 `PromptCachePrefix`，`LLMProvider.call` 在进入重试/并发区之前用 `_cached_prefix_for`（`llm_wrapper.py:1209-1223`，调用点 `:1381`）让**实际服务本次调用的那个成员**自己解析句柄——provider 不支持缓存返回 None，缓存侧异常只记日志并退化为不缓存（软失败，不阻塞调用）。retain 侧在 `fact_extraction.py:2083`、consolidation 侧在 `consolidation/consolidator.py:3584` 构造它（1.0.0 把 consolidator 从 `engine/` 挪进了 `engine/consolidation/` 子包）。

基类还定义了一组**可选能力探针**（全部默认 False/None，provider 按需覆写）：

| 能力 | 方法 | 谁实现了 True |
|---|---|---|
| Batch API | `supports_batch_api`（`llm_interface.py:241`） | openai/groq 系（OpenAICompatibleLLM）、anthropic（Message Batches API，`anthropic_llm.py:782-786`）、gemini、fireworks |
| attempt 级并发 | `supports_attempt_scoped_concurrency`（:278） | 几乎所有 SDK provider（见 2.1） |
| 请求级凭据替换 | `supports_request_overrides`（:282-293，1.0.0 新增，#5578） | openai 兼容族（ollama 除外——它的原生 HTTP 路径不走 SDK client，`openai_compatible_llm.py:2381-2383`）、anthropic、litellm、litellmrouter、nous。False 的 provider（OAuth/CLI 会话系、router 每部署一套 key）收到扩展的改写请求时**直接拒绝**而不是用服务器凭据发出去 |
| 视觉 | `supports_vision` 三值 `bool \| None`（:294） | `None` = 该 provider 是网关（如 litellm/openrouter），不知道背后接的具体模型，无法自证；retain 遇到带图 item 时把 `None` 当 False 拒绝；操作员可用 `HINDSIGHT_API_LLM_VISION` 强制覆盖（`llm_wrapper.py:1173-1186`） |

`constructor` 里有两个值得注意的防御性设计（`llm_interface.py:86-145`）：`reasoning_effort` 为空串/None 一律归 None 并且**不发明默认值**（历史上曾默认 "low"，导致 #3449 的静默降级），不支持的 provider 必须调 `_warn_reasoning_effort_unsupported()` 在启动时喊出来；`timeout` 即使 provider 不用也必须存到 `self.timeout`（#3898——Codex 曾连这个属性都没有，请求挂死后无从区分" honoring"和"dropping"）。

### structured output 的三条路

以 OpenAI 兼容 provider 的组装逻辑为例（`openai_compatible_llm.py:1275-1305`）：

```python
# hindsight_api/engine/providers/openai_compatible_llm.py:1276-1305（节选；注释为意译，省略处以 … 标注）
if response_format is not None:
    schema = None
    if hasattr(response_format, "model_json_schema"):
        # strict / 非 strict 都先过 structured_output 的统一序列化器（含数值边界剥离，见下）
        schema = strict_json_schema(response_format) if strict_schema else provider_json_schema(response_format)
    if strict_schema and schema is not None:
        # OpenAI 的 strict JSON schema 语法强制
        call_params["response_format"] = {
            "type": "json_schema",
            "json_schema": {"name": "response", "strict": True, "schema": schema},
        }
    else:
        # 软模式：schema 文本注入 prompt……
        if schema is not None:
            schema_msg = f"\n\nYou must respond with valid JSON matching this schema:\n{json.dumps(schema, ...)}"
            # 注入首条消息……
        …  # 注入 if/elif 分支体省略（:1289-1296）
        if self._supports_json_mode():
            call_params["messages"] = _ensure_json_word_in_user_message(call_params["messages"])
            call_params["response_format"] = {"type": "json_object"}
```

三条路总结：

1. **软模式**（默认）：schema 文本拼进首条消息，且（默认）再发 `response_format={"type":"json_object"}`。是否真的发 json_object 由 `_supports_json_mode()`（`openai_compatible_llm.py:2209-2222`）决定：三态配置 `HINDSIGHT_API_LLM_OPENAI_COMPATIBLE_JSON_MODE`（`config.py:213`，与 `HINDSIGHT_API_LLM_VISION` 同款三态——None=按 provider 默认，True/False 强制覆盖）——`lmstudio/ollama/volcano` 默认不发（这些后端不能可靠支持 json_object），`llamacpp` 跟随 `HINDSIGHT_API_LLAMACPP_NO_GRAMMAR`，其余默认发；显式 False 时软路径只把 schema 拼进 prompt。开关的动机（#5261/#4935）：`provider=openai` 指向一个无法约束输出的本地服务器时，json_object 会让服务器改写 prompt、thinking 模型会在改写后的 prompt 上死循环。0.10.3 前这是硬编码的 `skip_grammar = provider in ("lmstudio", "ollama", "volcano")` + llamacpp 分支，现在收拢进这一个方法（1.0.0 起名单里又添了 `zai`——z.ai 的 coding 端点同样会被 json_object 改写 prompt，#5618）。
2. **strict 模式**：`json_schema strict:true` 语法强制（OpenAI 兼容系）；Anthropic 走 forced `tool_use`（input_schema 即 schema，`anthropic_llm.py:346-372`，解决 #1002 的 invalid-JSON 重试风暴）；Gemini 原生 `response_schema` 天生强制；LiteLLM 系可选 `structured_output_forced_tool`。schema 序列化由 `engine/structured_output.py` 统一：`UnionSafeSchemaGenerator` 把 pydantic discriminated union 的 `oneOf+discriminator` 改写成 `anyOf` 并把 tag 字段补进 `required`（没有任何目标 provider 接受 `oneOf`，`structured_output.py:11-67`）；0.10.3 起（#5401/#5275）两条序列化路径（`strict_json_schema` / `provider_json_schema`，`:160-171`）还统一剥离**数值边界关键字**——pydantic 为 `Field(ge=/le=/gt=/lt=/multiple_of=)` 生成的 `minimum` / `maximum` / `exclusiveMinimum` / `exclusiveMaximum` / `multipleOf`（`_strip_numeric_bounds`，`:138-158`）。动机（注释原话大意）：这些关键字在请求线上买不到任何东西——没有目标后端替你强制它们，而边界仍在 pydantic 模型上、响应回来照样校验；但**按白名单校验 schema 的后端会直接 400**：Bedrock Converse 报 "For 'integer' type, properties maximum, minimum are not supported"（issue #5275——一个在线部署的 131 个心智模型因此暂停了 60 个），OpenAI 在 strict 模式下对任何不支持的关键字报错。当时的两个肇事字段是 `reflect/delta_ops.py:154` 与 `reflect/structured_doc.py:85` 的 `level`（`Field(default=2, ge=1, le=6)`），但选择在序列化层统一剥而不是逐模型改，是为了下一个带边界的字段不再重开此洞。`maxItems` / `minItems` / `pattern` 刻意**不**剥：consolidation 与 retain 有意发送它们（接受它们的后端会做语法强制），由 `HINDSIGHT_API_LLM_SUPPORTS_MAX_ITEMS` / `HINDSIGHT_API_LLM_SUPPORTS_STRING_PATTERN` 门控。剥离只动 schema 节点自己的关键字，`properties` 这类"名字映射"的键是用户数据——一个字面叫 `minimum` 的属性会幸存。因为 anthropic（forced tool 的 input_schema）、gemini、codex、claude-code、cursor、copilot、litellm 全都从这两个函数取 schema，剥离一处生效、全部 provider 受益；`has_tagged_union`（`:181`，`lru_cache(maxsize=256)`，:180）两侧比较也都过剥离——否则"只差一个被剥掉的 minimum"的模型会被误判成 union 改写、无谓推离 Gemini 的原生 response_schema 路径。同提交还把它从无界 `lru_cache` 改为 `maxsize=256`：consolidation 每批构造一个新 response model（schema 钉住该批 fact id），无界缓存会把每一个都钉在内存里。
3. **解析兜底**：`parse_llm_json`（`llm_wrapper.py:378-448`）三级火箭——剥 markdown 围栏 → 控制字符转义（字符串内的换行保留为 `\n`，围栏外的丢成空格，#3361）→ `json_repair` 结构性修复；每次成功解析后再过一遍 `sanitize_value`（JSON 解码正是孤立代理对"出生"的地方，#3729）。

### token 计数

- **LLM 侧以 provider 报告值为主**：`TokenUsage` 有 `input_tokens / output_tokens / total_tokens / cached_tokens / thoughts_tokens` 五个字段（`response_models.py:90-130`），`thoughts_tokens` 单列是因为推理 token 按 output 计费但不属于可见输出；支持 `__add__` 聚合。0.10.2 起 `thoughts_tokens` 还被持久化进 `llm_requests` 表（迁移 `a6c4e8f1b203_add_reasoning_tokens_to_llm_requests`，历史行保持 NULL），`LLMProvider.call` 的错误路径上报也补齐了这一字段（`llm_wrapper.py:1420-1436`）。1.0.0 补齐了三个"假账"provider 的真实用量（#5693，issue #5541）：Codex 两个流解析器都改从 `response.completed` SSE 事件的 usage 块读 input/cached/reasoning/可见输出（此前是 char/4 估算加一堆 0；流里没有 usage 块时 `call()` 仍回落估算，`codex_llm.py:260-291`）；Claude Code 改用 Agent SDK 上报的 usage（`call()` 读 ResultMessage、工具轮读 AssistantMessage，cache 读/写折进 input_tokens、cache 读另记 `cached_tokens`，`claude_code_llm.py:53-80`）；Anthropic 把 `cache_read/cache_creation_input_tokens` 折进 input_tokens 并记 `cached_tokens`（`anthropic_llm.py:56-71`）。同窗口 #5675 修的是**聚合侧**：reflect 响应与同步 retain 的 HTTP total 原来按字段逐个重建 TokenUsage、把 cached/thinking 丢成 0，batch-API 抽取则根本不读 provider 的 usage 块——现在三处都透传。严格的"没有任何客户端估算"不再成立：Codex（无 usage 块时）与 Claude Code（无 usage 时）各保留一个 char/4 的兜底估算。
- **文本预算侧才有客户端计数**：`engine/token_encoding.py` 是全引擎唯一的 tokenizer 封装（也是全仓库唯一 import toktok 的地方，刻意收口——换实现只改这一个文件）：`count_tokens` / `truncate_to_tokens`（+批量形式 `truncate_many_to_tokens`）两个操作，服务于 chunk 大小、`fact_budget`、embedding 输入截断等场景。词表由 `HINDSIGHT_API_TOKENIZER_ENCODING` 选择（默认 `o200k_base`），加载结果 lru_cache 单例缓存。增量窗口（0.10.2 窗口，#5243/#5234）起 `count_tokens`（`token_encoding.py:121`）与批量形式 `truncate_many_to_tokens`（`:170`）接受显式 `encoding` 参数：**调用方若确知模型自己的词表就绕过全局配置**——目前唯一使用者是 embedding 输入上限（OpenAI `text-embedding-*` 按 `cl100k_base` 计数，见 3.6）；单条 `truncate_to_tokens`（`:146`）没有这个参数，仍用全局词表。按名加载走 `_encoding_by_name`（`:70-75`，同样 lru_cache、上界为内置的 3 个词表 `o200k_base / cl100k_base / o200k_harmony`），选择逻辑收在 `_encoding_for`（`:110-118`）。

## 3.2 Provider 清单与本地/远程的区分

以 `create_llm_provider` + `LLMProvider.valid_providers` 两处枚举为准，LLM provider 共 **32 个名字**（分派 `llm_wrapper.py:458-827`，`valid_providers :976-1012`），按分派目标分组：

- **OpenAI 兼容族**（→ `OpenAICompatibleLLM`，14 名）：`openai`、`groq`、`ollama`、`ollama-cloud`、`lmstudio`、`minimax`、`deepseek`、`volcano`、`openrouter`、`requesty`、`zai`、`opencode-go`、`atlas`、`meta`
- **订阅/OAuth 凭据系**：`openai-codex`、`chatgpt`、`claude-code`、`cursor`、`github-copilot`、`xai-oauth`、`nous`
- **网关/路由系**：`litellm`、`litellmrouter`、`bedrock`
- **Google 系**：`gemini`、`vertexai`
- **独立云端**：`anthropic`、`openai-responses`、`fireworks`
- **本地自管**：`llamacpp`
- **特殊**：`mock`（测试）、`none`（chunk-only 模式）

**实现类怎么加载**（1.0.0 变化，#5479/#5686）：`providers/__init__.py` 不再在 import 期拉起任何 provider——14 个实现类登记在 `_MODULES` 表里（`providers/__init__.py:31-46`），模块级 `__getattr__`（PEP 562）在首次访问 `providers.CodexLLM` 时才 `importlib.import_module` 对应子模块并把类缓存进 globals（`:66-71`）。动机写在文件 docstring 里：每个 provider 拖着自己的 SDK（google-genai 一个约 4s、openai 约 2s），而任何 import 了本包子模块的代码（`http.py` import `none_llm`）都会先跑这个 `__init__.py`——eager 导入让每个进程为用不到的 SDK 买单。配套有三个共同构成"启动不吃重模块"的措施：`provider_auth.py` 从 `engine/` 迁到包根（`hindsight_api/provider_auth.py`，并在 `llm_wrapper.py:36` 原位 re-export 兼容旧导入——迁出原因见 3.7）；sentence_transformers/onnxruntime 是否安装用 `importlib.util.find_spec` 探测而非 import（`config.py:4355-4381`——import sentence_transformers 要拉 torch、约 15s，连 `--help` 都得付）；OTel SDK 与 OTLP exporter 的导入移进 `initialize_tracing()`（`tracing.py:165-169`——tracing 默认关，模块顶层只留轻量的 `opentelemetry.trace` API）。同提交还新加了 `tests/test_config_import_cost.py` 守住这条启动成本线。

代码里**没有一个统一的 "local vs remote" 标志位**，而是三个互补的信号：

1. **是否要 API key**（`hindsight_api/provider_auth.py:16-35`）：`ollama/lmstudio/llamacpp/openai-codex/chatgpt/claude-code/cursor/github-copilot/mock/none/vertexai/litellm/litellmrouter/bedrock/nous/xai-oauth` 不需要——这个集合混合了"本地无鉴权"与"用 OAuth/订阅凭据"两类。还有一个 env 条件分支（:37-40）：`anthropic` 配置了 `ANTHROPIC_FEDERATION_RULE_ID` 时也免 key——SDK 自己拿平台身份令牌换短时访问令牌（Workload Identity Federation，issue #5502，#5690）。
2. **本地子进程 / 外部子进程 / 远程**：真正本地自管的只有 `llamacpp`——自己下载 GGUF、起一个 llama-cpp-python 服务器**子进程**并对它的本地 OpenAI 兼容 API 说话（`llamacpp_llm.py:1-5` docstring 原话 "Manages a llama-cpp-python server as a subprocess"；:48-53 的模块级单例 `_shared_server` + `CrossLoopLock` 让 retain/reflect/consolidation 各自的 provider 共享同一个进程）；`claude-code` 是起 claude CLI 的外部子进程；其余全部是远程 SDK/HTTP 调用。
3. **本地端点归一化**：`_V1_PATH_LOCAL_PROVIDERS`（frozenset）`{"lmstudio", "ollama"}` 会被 `_ensure_v1_base_url` 补 `/v1`（`openai_compatible_llm.py:109, 913`）——代码用"知道端点形状"来标记本地。

**mock 与 none**（必答问题 3）：

- `MockLLM`（`providers/mock_llm.py:32`）：测试 provider。记录每次调用到 `_mock_calls` 供断言，`set_mock_response` / `set_response_callback` 控制返回值/异常；`supports_vision()` 返回 True 使多模态抽取路径可测（`mock_llm.py:87-93`）。`LLMProvider` 里专门保留了 mock 调用同步的向后兼容层（`llm_wrapper.py:1123, 1438-1444`）。增量窗口（0.10.2 窗口，#5245）起 `call` 还接受一个 `prompt_cache: PromptCachePrefix | None` 参数并**忽略之**——consolidation 测试把裸 MockLLM 直接当 LLM 配置传入，不收下这个 kwarg 所有 mock 的固化调用都会炸（`mock_llm.py:115-121`）。
- `NoneLLM`（`providers/none_llm.py:26`）：`HINDSIGHT_API_LLM_PROVIDER=none` 时的占位。语义是"**chunk-only 存储模式**"——retain 走 chunks 模式不做事实抽取，reflect/consolidation 被禁用；它的 `call` 永远抛 `LLMNotAvailableError`，作为"任何意外走到 LLM 的代码路径会得到清晰错误而非连接失败"的安全网（`none_llm.py:1-8`）。注意 provider=none **并不跳过 LLM 链的构建**：`memory_engine.py:2606-2607` 只是 `self._skip_llm_verification = True`（跳过连接验证），retain/reflect/consolidation 三条操作链仍在 `memory_engine.py:2801 / 2897 / 3020` 无条件构建（此时包的是 `NoneLLM`），mental-model-refresh 链按需解析为同一批 property（见 2.1）；真正的短路发生在各操作入口的 `provider == "none"` 检查——retain 强制 `retain_extraction_mode="chunks"` 并关闭 observations 产出（`enable_observations=False`，即固化阶段的观察条目生成，`memory_engine.py:7578-7581`），consolidation 直接跳过（`memory_engine.py:4351-4354`）。

**MultiLLMProvider**（`engine/multi_llm.py:105`）在单 provider 之上叠加：`failover`（按声明序）、`round-robin`（SWRR 加权轮询，成员内部重试耗尽才推进下一成员；`OutputTooLongError` 不 failover 因为换 provider 也装不下）、`metadata`（仅 retain，按被抽取 item 的 metadata 路由，`multi_llm.py:60-77` 的匹配规则支持列表任一元素命中、bool 归一为 "true"/"false"）。batch retain 固定落在第一个支持 batch 的成员上且不 failover。prompt 缓存按成员各自解析：调用方只声明要缓存什么（`PromptCachePrefix`），failover 落到谁、谁就用自己的账号建缓存句柄（见 3.1，#5245）。

## 3.3 三个代表 provider 深讲

### 3.3.1 OpenAICompatibleLLM：公共骨架

这是覆盖面最大的实现（14 个 provider 名共用一个类），也是理解其他 provider 的模板。要点：

- **客户端构造**（`openai_compatible_llm.py:958-982`）：`AsyncOpenAI(max_retries=0)`——SDK 重试一律关掉，重试统一由 Hindsight 自己的循环管（这样退避、日志、metrics、跨 provider 行为一致）；timeout 用 `build_sdk_timeout` 生成**分相位** httpx.Timeout——connect 相位被 `HINDSIGHT_API_LLM_CONNECT_TIMEOUT`（默认 10s，`config.py:1241`）封顶，防止"永不完成握手的端点烧掉整个 120s 预算"（issue #3881，`llm_transport.py:52-71`）。
- **请求组装的差异点开关**：`_supports_reasoning_model`（按模型名家族识别 o1/o3/GPT-5/6，`openai_compatible_llm.py:1093`）、`_max_tokens_param_name`（`max_completion_tokens` vs `max_tokens`，:1128）、MiniMax 的 temperature 钳位 (0,1]、Groq 的固定 `seed=4242` + service_tier、`_TOOL_CHOICE_REQUIRED_UNSUPPORTED_PROVIDERS`（frozenset）`{"lmstudio","ollama"}`（这些实现声称支持 `tool_choice=required` 却静默忽略，导致 reflect 拿不到工具调用、误答"我没有信息"——用显式黑名单而**不是**从 URL 推断：自定义 OpenAI 兼容端点可能真的实现了 required 语义，静默降级会改变请求行为，`openai_compatible_llm.py:102`）。1.0.0 补了一处遗漏（#5652）：`HINDSIGHT_API_LLM_OPENAI_SERVICE_TIER` 原来只有 Responses provider 发送，OpenAICompatibleLLM 存了字段却从不发送——现在 `provider=openai` 时作为原生顶层参数 `service_tier` 发出（:1258-1262；Groq 仍走 `extra_body`，:1266-1267）。
- **Ollama 双轨**：带 schema 或配置了 `ollama_num_ctx` 的调用走 `_call_ollama_native`（Ollama 原生 `/api/chat`），因为 OpenAI 兼容端点会静默丢弃 `num_ctx`，而 Ollama 按 context size 区分已加载的模型实例——size 一变就整个重新加载，共享主机上的其他使用者一起遭殃（#3599）（分派与缘由注释 `openai_compatible_llm.py:1205-1212`，实现 :1931 起）。
- **响应侧清洗**（`openai_compatible_llm.py:164-269`）：`_strip_code_fences`（围栏剥离失败时回退"最外层可解析 JSON span"，:164）+ `_strip_reasoning_tags`（:215-269，`<think>` 等 5 对标记），后者处理三个 case——增量窗口（0.10.2 窗口，#4926/#4927）新增第 1 个：**孤儿闭合标签**。Qwen3 thinking 系、DeepSeek-R1-0528、Spark-X2.5 这类聊天模板把 `<think>` **预填进生成 prompt**，服务端又没开 reasoning parser 时，补全里只剩 `reasoning</think>answer`——开标签在 prompt 里、闭合标签悬空，旧逻辑对此不设防，推理文本原样漏进存储的记忆/心智模型。现在的处理：找到首个闭合标签后，若其前面没有配对的开标签、且前缀（lstrip 后）**不以** `{`、`[` 或代码围栏开头，就丢弃闭合标签及之前的全部内容；前缀以这三种字符开头说明闭合标签是被引用的字面量而非推理边界，保留。守卫刻意收窄——更严的版本（前缀里出现过任意围栏就不剥）会漏掉"推理正文自己起草了一个围栏块"的常见情形；代价是"以散文开头、正文里引用了闭合标签"的回答会被切断，注释明说这是接受的取舍（需要模型主动谈起闭合标签才会误伤，对比的是这一族模板**每份**心智模型都漏推理）。原有两个 case 不变：闭合块 `<think>...</think>` 任意位置移除；截断产生的悬空开标签只在**行首**出现时才剥到串尾，保护 JSON 值里的内联字面量。这个清洗不止 OpenAI 兼容族在用：独立的 `OpenAIResponsesLLM` 也导入同一函数处理 `/v1/responses` 的输出文本（`openai_responses_llm.py:64-65` import、`:521, :524` 调用），openai-responses provider 同样受益于此次修复。
- **重试循环**（`openai_compatible_llm.py:1329-1610`）：

- **OpenRouter 路由收窄**（0.10.3 新增，#5304）：请求带 `response_format` 且 provider 是 `openrouter`（或 `provider=openai` 但 base_url 指向 openrouter.ai，`_is_openrouter`，`:366`）时，注入 `extra_body.provider.require_parameters=True`（`:1309-1314`）——OpenRouter 把一个模型负载均衡到多个上游，不支持 `response_format` 的上游不报错、而是回答空 content + `finish_reason=stop`（#3494，对调用方来说就是解析失败）；`require_parameters` 把路由限制到"尊重每个发送参数"的上游。操作员已设置的 provider 路由键优先（dict 合并而非覆盖），provider dict 是拷贝、不原地改。
- **json_object 跳过**：软模式的 `response_format` 由 `_supports_json_mode()` 决定（三态配置，见 3.1 三条路第 1 条，#5261/#4935）。
- **prompt-cache 亲和**：见 3.6。

## 3.4 OAuth 类 provider 的 token 管理

四个 OAuth 后端共享一套存储约定，但所有权不同（`xai_oauth_auth.py:11-22` 的 docstring 总结："codex_auth.py 和 nous_auth.py 读一个 vendor CLI 创建的凭据文件并保鲜；本模块连登录也自己做"；1.0.0 的 chatgpt_auth.py 同样连登录自己做——见 3.3.4）：

- **Codex**：读 `$CODEX_HOME/auth.json`（默认 `~/.codex`），解码 access_token JWT 的 `exp`，到期前 ~60s 主动刷新 `POST https://auth.openai.com/oauth/token`，401/403 时再被动刷新一次；请求形状镜像 `@openai/codex` CLI 的 Rust 实现（`codex_llm.py:1-16`，账户 id 头的拼写也照抄 CLI——见 3.3.4 #5239）。`codex_home` 可以按 multi-LLM 链的成员分别配置，让"主成员限流后 failover"真正落到另一个 ChatGPT 账号（`llm_wrapper.py:916-919`）。
- **xai-oauth**：`HINDSIGHT_API_XAI_OAUTH_TOKEN_PATH`（默认 `~/.hindsight/xai_oauth.json`）存 access/refresh token、`expires_at`、`obtained_at`、scope 和发现的 `token_endpoint`；登录是显式的 `python -m hindsight_api.engine.providers.xai_oauth_auth login`（RFC 8628 device-code 流），请求路径永不触发登录。xAI **每次刷新都发新 refresh token 并作废旧 token**，所以 store 必须可写、多进程必须共读同一文件；manager 的刷新状态刻意放在 store 而非内存——每次刷新先抢锁、抢到后**重读 store**，发现兄弟进程刚刷过就跳过，防自旋的最小间隔也从 store 的 `obtained_at` 取（`xai_oauth_auth.py:38-39, 716`）。
- **双锁 `oauth_store_lock`**（`providers/oauth_store_lock.py:57-121`）：

```python
# hindsight_api/engine/providers/oauth_store_lock.py:72-83, 109（节选；注释为意译，省略处以 … 标注）
key = store.expanduser().resolve(strict=False)
async with _loop_lock(key):          # 第 1 层：本事件循环内的 asyncio.Lock
    if fcntl is None:                # Windows：只有第 1 层
        …  # logger.debug 与 yield/return 省略（:74-77）
    lock_path = store.with_suffix(".lock")
    …  # try/open、只读 store 降级分支与 with/while 循环壳省略（:80-104）
    …
    fcntl.flock(lock_file.fileno(), fcntl.LOCK_EX | fcntl.LOCK_NB)  # 第 2 层：跨循环/线程/进程
```

  为什么两层：刷新要 await 网络，持锁跨挂起点；`asyncio.Lock` 绑定第一个等待它的循环（一个 manager 可能被多个循环触达），`threading.Lock` 会阻塞循环而不是让出。所以循环内用 per-(loop, path) 的 `asyncio.Lock`（`LoopLocal` 管理，机制见 3.6），跨循环/进程用 `<store>.lock` 上的 `fcntl.flock`（POSIX 文件锁）——flock 在同进程的不同打开文件描述之间也冲突，恰好覆盖"同进程两个循环"的场景。非阻塞 flock + 50ms `asyncio.sleep` 轮询，超时报 `TimeoutError`；store 只读（如 K8s Secret 卷）时降级为仅循环内锁并打 debug，因为"有外部写者发布凭据"的场景里写者本来就不走这把锁（`oauth_store_lock.py:84-99`）。

## 3.5 本地模型：加载、设备选择与内存卫生

`engine/local_device.py` 集中管理所有 in-process torch 模型（`LocalSTEmbeddings`、`LocalSTCrossEncoder`）的三个问题，每个都有 issue 号背书：

1. **MPS 永不选择**（决策说明在模块 docstring `local_device.py:6-38`，`select_local_device` 在 :142）：只返回 `"cpu"` 或 `None`（让 sentence-transformers 自动选 CUDA / XPU——Intel GPU）。Apple Silicon 的 MPS（Apple 的 Metal GPU 后端）按输入张量形状缓存编译图和分配池且从不释放——在"文档长度各不相同"的 embedding/rerank 负载下无界增长（实测空闲 20GB），且并发 encode 会撞 Metal command buffer 直接杀进程（#4412）。曾经存在的 `*_LOCAL_ALLOW_MPS` 开关被删除，残留设置会被警告"已无效果"；Apple Silicon 的 GPU 路线是 MLX（Apple 的数组计算框架）reranker（`HINDSIGHT_API_RERANKER_PROVIDER=jina-mlx`）。
2. **权重对齐**（`local_device.py:293`）：safetensors 零拷贝 mmap 的参数继承文件头的字节偏移，`8 + len(json_header)` 不保证按 dtype 对齐——`ms-marco-MiniLM-L-6-v2` 的 12090 字节头让每个参数落在 `ptr % 4 == 2`，float32 matmul 返回 NaN/垃圾，reranker 把 NaN 清洗成 0 后**看起来一切正常**，实则排序退化。对策是加载时克隆错位张量（`align_local_model_weights`，只复制错位的），再跑冒烟测试 `assert_finite_local_output`——NaN 在启动时就炸而不是静默污染 recall。
3. **批后内存释放**（`local_device.py:262`）：每批推理后 `malloc_trim`（glibc）/`malloc_zone_pressure_relief`（macOS）把分配器高水位还给 OS（#1717），GPU 上 `torch.<backend>.empty_cache()`，MLX 上 `mx.clear_cache()`（MLX 默认缓存上限是整个设备内存）。

1.0.0 给本地 torch 模型加了一把**串行构建锁**（#5609，issue #4420）：transformers 5.x 在整个模型构建期间翻转进程级全局状态（`PreTrainedModel.tie_weights` 变 no-op、torch 默认 dtype 被改），而 embedder 和 reranker 原本在启动时于两个重叠的线程里构建——结果是 tied 权重留在 meta 设备上（"Cannot copy out of meta tensor"）或 reranker 冒烟测试混到 float/bfloat16。现在构建持有 `LOCAL_MODEL_BUILD_LOCK`（`local_device.py:93`，`embeddings.py:386` 与 `cross_encoder.py:324` 持锁），下载则先在锁外并行完成（`prefetch_local_model`）。**维度读取**也随 1.0.0 换了方法：sentence-transformers 5.4 把 `get_sentence_embedding_dimension` 改名 `get_embedding_dimension` 并对旧名发 FutureWarning——现在优先取新名、5.0-5.3（local-ml 仍允许）回落旧名（`embeddings.py:416-421`，#5660）。

**ONNX 路线**（`embeddings.py:491-760`）：ONNX 是跨运行时的本地推理格式（模型以 `.onnx` 单文件分发）。`OnnxEmbeddings` 支持显式 `dimensions` 配置并在 `initialize` 时比对模型自检输出——**不一致直接抛 `ValueError` 拒绝初始化**（`embeddings.py:664-668`），有自己的 query/passage 前缀对（E5 类模型）。0.10.2 起新增 **CUDA 设备支持**：`HINDSIGHT_API_EMBEDDINGS_ONNX_DEVICE`（`cpu`/`cuda`，默认 cpu）+ `HINDSIGHT_API_EMBEDDINGS_ONNX_CUDA_DEVICE_ID`（默认 0；常量 `config.py:512-513, 1297-1298`）。路径上的失败面被逐层封死：请求 cuda 但装的还是 CPU 版 onnxruntime → 初始化即 `RuntimeError`（在下载大模型图之前就拒绝）；CUDA wheel 加载库失败时 ORT 可能**不抛错地**回退成 CPU-only session——初始化会主动核对 `session.get_providers()`，没激活 `CUDAExecutionProvider` 就拒绝，并 `session.disable_fallback()` 防止 run() 时再回退（`embeddings.py:645-658`）；自检 warm-up 失败时把 `_session/_tokenizer` 复位为 None，避免下一次 `initialize()` 误判已就绪（`embeddings.py:669-672`）。GPU 镜像没有现成 extra 可装（`local-onnx` 只含 CPU runtime），仓库提供了自定义镜像配方 `docker/docker-compose/cuda-onnx/`（CUDA 分支 ImportError 的错误信息里直接指路，`embeddings.py:572-573`）。

**FlashRank / Jina-MLX**：flashrank 是 in-process 轻量 reranker（无 HindsightConfig 字段、直接读 env，`config.py:4113-4118`）；jina-mlx 是 Apple Silicon 上的 MLX reranker（`engine/jina_mlx_reranker.py`，144 行）。

## 3.6 Embeddings 的批量、并发与"缓存"辨析

**批量与 fan-out**：所有远程 provider 共用 `Embeddings._encode_batched`（`embeddings.py:235-288`）：

```python
# hindsight_api/engine/embeddings.py:253-288（节选；注释为意译，省略处以 … 标注）
size = batch_size if batch_size is not None else getattr(self, "batch_size", 0)
…  # size<1 兜底与空批提前返回省略（:254-258）
batches = [texts[i : i + size] for i in range(0, len(texts), size)]
slots = self._get_request_slots()
async def run(batch):
    # 批数多于槽位时就在这里排队——是上限在干活，不是放宽它的理由
    async with slots:
        return await encode_batch(batch)
concurrency = min(max(self.max_concurrent_requests, 1), len(batches))
if concurrency == 1:
    # 单批（如 recall 查询）内联执行：无 task——但仍过槽位，
    # 否则并发调用方会绕开上限（#5011）
    return [vector for batch in batches for vector in await run(batch)]
# create_task 会把调用方的 contextvars 带进每个 task……
tasks = [asyncio.create_task(run(batch)) for batch in batches]
…  # try/except：失败时取消全部 task 并收集结果省略（:281-287）
results = [await task for task in tasks]   # 按输入序 await，最早失败者胜出
```

并发上限 `max_concurrent_requests` 对 in-process 后端保持 1（没有往返可重叠），远程 provider 由 `HINDSIGHT_API_EMBEDDINGS_MAX_CONCURRENT_REQUESTS` 统一设置（`embeddings.py:2324-2332` 的 `_with_request_concurrency`）。信号量是**每 backend 实例一份、per-loop 创建**（`LoopLocal[asyncio.Semaphore]`）——注释强调它描述的是 embedding 服务的容量而非调用方：四个并发 retain 不能在网络上压 4×上限的请求（`embeddings.py:202-233`）。`LoopLocal`（`engine/aiohttp_session.py:84-124`）是"每运行循环一个懒建实例"的通用容器，因为 aiohttp session、asyncio.Semaphore、SDK 连接池都绑死创建它们的循环。增量窗口修了一处绕过（#5011/#5242）：单批内联路径原来**连信号量都不碰**——一次 recall 查询只发一个请求时"内联、无任务、无信号量"，字面上与旧循环逐字节一致；但"一次调用一批"不等于"同一时刻只有一批在飞"，多个并发 caller（比如同时到达的几个 recall）合计就超了共享上限。现在内联路径也走 `run()`，照样过槽位。

**非对称前缀与输入上限的词表**：E5/embeddinggemma 类模型查询与文档要用不同指令前缀，纯 text-in/vector-out 的 provider（TEI——HuggingFace Text Embeddings Inference 推理服务——及 OpenAI 兼容端点）只能由客户端拼——`encode_query`/`encode_documents` → `_encode_prefixed`（`embeddings.py:301-309`）；SentenceTransformers（自身 prompts）与 ZeroEntropy（`input_type` 字段）有原生通道则覆写。0.10.3 起（#5155）Cohere 也加入原生通道一组：v3 系模型的检索任务本来就是请求参数（`input_type=search_query/search_document/...`），`CohereEmbeddings` 现在覆写 `encode_query`/`encode_documents` 分别发 `search_query`/`search_document`，`encode()` 保持显式配置的 `input_type`（`embeddings.py:1287-1291`）——此前它把构造时的 `input_type`（默认 `search_document`）读在共享属性上，recall 的查询向量也被当成文档任务嵌入。任务随请求走而不是换 `self.input_type`，因为 recall 与 retain 并发共享同一个 provider 实例，换共享属性会让一个 retain 批被当成 query 嵌入（docstring 明说这个竞态）。前缀 token 还会从截断预算里扣除（`embedding_utils.py:40-56`）。增量窗口（0.10.2 窗口，#5243/#5234）给这条链补了另一半"预算算给谁"的问题：截断与前缀计数原来一律用 `HINDSIGHT_API_TOKENIZER_ENCODING` 的全局词表（默认 o200k_base），但 OpenAI 官方 `text-embedding-*` 自己按 `cl100k_base` 分词且在英文/markdown 上数得略多——按全局词表截到恰好的 8192 到了 provider 那边仍超限、直接 400。现在 `Embeddings` ABC 有了可选能力字段 `tokenizer_encoding`（`embeddings.py:195`，None = 未知，回落全局词表）；`OpenAIEmbeddings` 只对 `MODEL_DIMENSIONS` 认得出的官方模型设 `cl100k_base`（`embeddings.py:990-995`——同一个类也服务 OpenAI 兼容服务器上的其他模型，不认识就不设）；`embedding_utils` 侧因为 duck-typed Protocol 不声明该字段，用 `getattr` + isinstance 探测（`embedding_utils.py:28-37`），前缀计数与 `truncate_many_to_tokens(texts, budget, encoding)` 两处都把词表传下去（`:56, :77`，见 3.1 的 token_encoding 说明）。

**cache_affinity.py 到底是干嘛的**（必答问题 7 的直接回答，详见文末速查）：它**不是** embedding 缓存，也**不缓存任何向量**。它是 OpenAI 兼容系 provider 的**服务端 prompt-cache 亲和提示**：prompt cache 只有"同一会话落到同一后端副本"才命中，xAI 靠 `x-grok-conv-id` 头做会话粘滞、OpenAI 靠 `prompt_cache_key` 请求字段做路由（`cache_affinity.py:1-40`）。四种模式 `none / xai_conv_id / openai_prompt_cache_key / auto`（`CacheAffinityMode`，:61-67）；`auto` 是**白名单**而非探测——按 base_url host 匹配 `x.ai/grok.com` → xai 头，`openai.com`（且排除 Azure，因为同一 `*.openai.azure.com` 端点也挂 DeepSeek/Llama 等会拒绝该字段的模型）→ prompt_cache_key，其余一律 `none`（`resolve_cache_affinity`，:98-125）。亲和 id 的取值优先用本次操作的 `trace_id`（每次 `with_config` 生成的 uuid 的 sha256 前 32 hex），所以一次 retain/reflect 的所有调用共享一个 id；无 trace 时退回首条消息指纹（:127-170）。`apply_opencode_session` 是同文件的兄弟（:173-215）：`opencode.ai` host **要求** `x-opencode-session` 头（协议要求而非优化），与 cache_affinity 模式无关，host 级判定——0.10.2 起该 id 的来源除了 `messages` 还有 Responses API 的 `input` 字段：启动验证探针走 Responses 形状、只读 `messages` 会让这次调用无 id 可带，opencode-go 直接 400 MissingSessionID。配置在 `LLMProvider.__init__` 里解析一次（`llm_wrapper.py:888-895` docstring "Used verbatim"——per-op/global 回落是调用方的责任；`openai_compatible_llm.py:954` 在构造期调 `resolve_cache_affinity` 解析 "auto"，因为 base_url 构造后不可变），错值在启动时抛错——因为该设置的效果在响应里不可见，静默失效无法被发现（`llm_wrapper.py:968-972`，解析发生在 `LLMProvider.__init__`）。

Embedding 侧**真正**的缓存机制不在本层——memory_units 的向量本就落库、召回时随行读出，没有独立的向量缓存层；代码里未见 query→vector 的 memoization 缓存（未发现，如后续版本新增以代码为准）。

## 3.7 config.py 的字段分类机制与 ConfigResolver

**字段的三分法**（必答问题 4 的答案核心）：

- `_CREDENTIAL_FIELDS`（`config.py:3905-3981`）：永不出 API、永不许 bank/租户写。含各操作的 `*_llm_api_key`、`*_llm_base_url`、litellmrouter 配置、multi-LLM 成员列表（成员内嵌 key/url）、reranker 链成员、S3/GCS/Azure 凭据、`xai_oauth_*`、1.0.0 新增的 decision model 全局与逐操作 key/url（8 个）与 `llm_chatgpt_home`（chatgpt 的 OAuth 凭据目录）等。
- `_CONFIGURABLE_FIELDS`（`config.py:3986-4062`）：手工标记的"行为字段"白名单，1.0.0 实测 55 个——retain 分块/抽取模式/策略、召回四臂开关、consolidation 批量与 mission、reflect mission、recall token 预算与 budget 函数、disposition 三 Trait、`llm_gemini_safety_settings`、`memory_defense` 等。0.10.2/0.10.3 的新配置项（ONNX device/CUDA、reranker 本地超时、bank alias 缓存、json_object 跳过三态开关、DB 池慢获取阈值、reranker 逐候选 token 上限）都没有进这个白名单，仍是服务器级 static 字段。`get_configurable_fields()` / `get_credential_fields()` / `get_static_fields()` 三个 classmethod 暴露（`config.py:4164-4213`）；**static = 全部字段 − configurable**（不是显式列表）。
- 解析优先级：**bank 覆盖 > 租户覆盖 > 全局 env**（tenant 先 merge、bank 后 merge、`overrides.update` 字典序即优先级，`config_resolver.py:249-262`）。`_CONFIGURABLE_FIELDS` 之外的字段**不能**被 bank/租户覆盖——两条防线：写入侧拒绝（`config_resolver.py:531-547`），读取侧过滤（`_active_bank_overrides` 只保留 configurable，`config_resolver.py:442-457`）。credential 字段即使误列入 configurable 也会被二次剔除（`self._public_fields = frozenset(configurable - credential)`，`config_resolver.py:183`）。

**decision model 配置体系**（1.0.0 新增，#5607/#5613/#5284/#5382/#5664）：决策模型是"回答定型问题而非写文本"的小模型（每问亚秒级），recall/reflect/consolidation 拿它做中间判断、把 LLM 留给写作。配置分两层：

- **服务器级 setup**（static 字段，**只来自 env**——static 字段 bank 与租户钩子都覆盖不了，`config.py:701-708`）：全局 `HINDSIGHT_API_DECISION_MODEL_{PROVIDER,API_KEY,MODEL,BASE_URL,TIMEOUT,MAX_CONCURRENT,MAX_REQUEST_TOKENS}` + 逐操作覆盖 `HINDSIGHT_API_{RECALL,REFLECT,CONSOLIDATION}_DECISION_MODEL_*`（由 `_decision_model_env` 拼出，`config.py:1550-1552`）。provider 三选一（外加 `none`=不设）：`typesafe`（Jev，默认模型 `jev-latest`、System One API）、`cloudflare`（Clef on Workers AI，base_url 按账号必须自配）、`openai`（Decisions API，`gpt-6-luna`），见 `DECISION_MODEL_PROVIDER_DEFAULTS`（`config.py:1532-1537`）。解析收口在 `HindsightConfig.decision_model_config(operation)`（`config.py:5695` 起）：操作有自己的 provider 就用它，否则用全局的；key/model/url 只在"操作用了与全局相同的 provider"时才继承全局值——**别的 provider 的 key 绝不借用**；校验（未知 provider、超时/并发/token 上限非法、key 缺失）在启动 `validate()` 就做（`config.py:4218-4219`），不等到第一个请求。其中 8 个 key/url 字段在 `_CREDENTIAL_FIELDS`（`config.py:3971-3978`）。
- **bank 能动的只有三个"用不用"开关**：`consolidation_use_decision_model`（`config.py:4020`）、`reflect_use_decision_model`（:4035）、`mental_model_refresh_use_decision_model`（:4036）——三者都在 `_CONFIGURABLE_FIELDS`，HTTP 层也接受（`api/http.py:3951-3955, 4091`），默认 True。即：bank 可以关掉自己 bank 的决策模型分流，但选不了模型与凭据。生效点：consolidation 侧是 `engine/consolidation/triage.py:131-133`（开关关闭直接 `return None`、开关开着才解析 setup——决策模型先判定 fact 是"复述/新增/ chatter"从而免 LLM，#5664）；reflect/refresh 侧是 `memory_engine.py:15600-15605`（关闭则 reflect 保持纯 agent 轮）；recall 侧没有开关——配了 recall 的 decision model 就整体接管重排器（`search/reranking.py:330-333`，机制归 03 卷）。另有一处 provider 限制：reflect 的决策模型必须 `typesafe`——它复用 reranker 类 `TypeSafeCrossEncoder` 的 rank-and-cut，别的 provider 只告警并退回 agent 轮（`memory_engine.py:15378-15415`）。

**config 的进程生命周期**：`HindsightConfig.from_env()` 一次性解析全部 `HINDSIGHT_API_*` 并 `validate()`；`_get_raw_config()` 返回进程级单例 `_config_cache`（`config.py:5847-5856`）；`get_config()` 包成 `StaticConfigProxy`（`config.py:62-90`：只许读 static 字段，访问 configurable 字段抛 `ConfigFieldAccessError`，且 `__setattr__` 一律拒绝——配置只读，修改必须走 ConfigResolver）。0.10.2 顺手修了一个环境变量解析的通病：`int(os.getenv(X)) if os.getenv(X) else None` 这种写法把**同一个变量读两次**，测试的值与转换的值没有任何机制保证相同——新助手函数 `_env_int` / `_env_int_or` / `_env_float` / `_env_str_list` / `_env_default_model`（`config.py:2531-2570`）全部单次读取；操作级 LLM 配置（retain/reflect/consolidation/mental_model_refresh 的 max_concurrent/retries/backoff/timeout/model 等，:4546-4610 附近）与 disposition、consolidation/reflect 的 max_completion_tokens（:5352/:5473/:5515 起）都已迁到这组函数。本窗口另给 mental-model refresh 单独拆了采样温度（#5500/#5683）：`HINDSIGHT_API_LLM_TEMPERATURE_MENTAL_MODEL_REFRESH`（`config.py:232`，字段 `llm_temperature_mental_model_refresh` :3243）未设时经 `_resolve_inherited_temperature`（:330-340）继承 **consolidation 已解析的温度**（consolidation 自身的 env→全局 `HINDSIGHT_API_LLM_TEMPERATURE`→默认链先解析完，`:4508-4516`）——refresh 走的是固化侧的改写调用，不是问答侧。provider_auth.py 是刻意设计的叶子模块：config.py 和 llm_wrapper.py 都需要在 import 期知道"哪些 provider 不要 key"，把答案独立出来避免两者互相 import 成环；1.0.0 把它从 `engine/` 挪到包根（`hindsight_api/provider_auth.py:1-14`）并给了更强的理由——import `engine/` 下任何东西都会先跑 `engine/__init__`，那会连带加载整个 engine（经 sentence-transformers 连 torch 一起），秒级开销连 `hindsight-api --help` 都不该付。

**MemoryEngine 侧的逐操作覆盖**（注意：这是服务器级 env，不是 bank 级）：`llm_*` 全局默认 + `retain_llm_*` / `reflect_llm_*` / `consolidation_llm_*` / `mental_model_refresh_llm_*` 操作级覆盖 + `llm_members`/`llm_strategy` 多链。per-op 缺省回落全局（`memory_engine.py:2762-2765`：`retain_provider = retain_llm_provider or config.retain_llm_provider or memory_llm_provider`）。

**bank 覆盖的生效点**只有两类：
1. `with_config(resolved_config)` 注入的 `llm_gemini_safety_settings`（示例 B）；
2. 各操作直接读 resolved config 的行为字段做分支（如 `enable_reranking` 降级 reranking、recall budget 函数、`*_use_decision_model` 开关、retain_strategies 经 `apply_strategy` 以 `dataclasses.replace` 拼接到 resolved config 上并再次校验分块约束，`config_resolver.py:1015-1062`）。

**第四个层级之外的通道——LLM request extension**（1.0.0 新增，#5578）：`HINDSIGHT_API_LLM_REQUEST_EXTENSION=module.path:ClassName` 指向一个扩展类，**每次 LLM 调用**前被问到（带租户 schema、bank、操作），返回凭据改写（同一 LLM、换 key/headers——给网关虚拟 key 计费用）或整条替换（换 provider/model/endpoint/key——服务器端按 bank/操作选模型，或按客户分云账号），返回 `None` 用服务器自己的 LLM，抛异常则拒绝本次调用（`extensions/llm_request.py:1-31` 的模块 docstring，钩子在 `llm_wrapper.py:1245-1262`）。它是"服务器级代码"而不是配置：API 调用方写不进任何东西，答案必须来自服务端状态——扩展若从 bank config 或 metadata 推导答案，文档明确要求自行校验（否则端点/key 就来自用户输入）。provider 侧以 `supports_request_overrides` 能力探针（3.1 表）分界：不支持的 provider 收到改写请求直接拒绝，而不是带着服务器凭据发出去。

双界重试的设计注释值得抄录（`remote_retry.py:62-71`）：attempts 单独用无法约束延迟（慢失败的上游把 5 次变成几分钟），budget 单独用无法阻止快失败的上游被反复捶——`budget_seconds` 只计失败尝试与退避睡眠，成功的工作不扣预算，所以大批量调用不会因成功的批次被惩罚。

Reranker failover 一行的机制集中说明：`MultiCrossEncoder`（`cross_encoder.py:2265-2430`）持有成员链，`_predict`（:2340 起）按序取**第一个给出可用分数**的成员（分数数量必须与 pairs 相等，否则视为该成员失败）；每个成员自带重试预算，所以普通的配额抖动在成员内部就被消化，不会烧掉 fallback；成员初始化失败不致命——记 warning 并在下一个请求到达该成员时懒重试；把 `rrf` 放在链尾，最坏情况是降级为融合序而不是整个 recall 失败。

`provider_name` 的语义在 0.10.2 收紧了：这个属性（`cross_encoder.py:2295-2302`）读的是链上共享的 `_active` 游标（:2288），并发请求会把它移走——所以它现在明确只作诊断用途。真正给下游用的是**随分数一起返回**的名字：`_predict` 在返回前把服务成员写进任务本地的 `_served_provider` ContextVar（`cross_encoder.py:75-76, 2370`），`Reranker.rerank` 把它抄到 `RerankResult.provider_name` 上再返回，recall 从结果对象上读它来判断 passthrough 语义与响应元数据（`memory_engine.py:10072-10076`）——一个发生了 failover 的请求不会再短暂污染邻居请求的标签。

## 3.9 预算控制：fact_budget 与 db_budget

- `engine/fact_budget.py`：决定 recall 返回哪些 facts 能装进 `max_tokens`。两条性质（docstring，:1-18）：按 rank 顺序花预算（截断只打尾部）、单个超预算 fact 只跳过自己不挤掉后面的短 fact；还有一个"地板"——只要调用方要正预算且确实有命中，绝不返回空（把 top1 整条超额返回），因为"空答案"会被读成"这个 bank 什么都不记得"。
- `engine/db_budget.py`：`ConnectionBudgetManager` 按操作限并发 DB 连接（每操作一个 `asyncio.Semaphore`），防"recall 的并行查询"独占连接池（`db_budget.py:1-34`）。
- 连接获取延迟的观测阈值（0.10.3 起 #5397 可配）：`acquire_with_retry` 对超过 `HINDSIGHT_API_DB_POOL_SLOW_ACQUIRE_THRESHOLD_SECONDS` 的池获取打 `[DB POOL] Slow acquire` 警告（默认 0.05s，0 关闭；`config.py:968, 1923`、`db_utils.py:182, 199`）。阈值读取刻意用 `_get_raw_config()` 缓存而非 `get_config()`——StaticConfigProxy 的每次调用约 0.3ms，而这在**每次**获取连接时都跑。连接池本身的构造与参数属 06 篇（数据库层），此处只涉及这个横切告警。

## 3.10 文件存储后端：FileStorage 的四个实现（0.10.2 起支持流式）

`engine/storage/` 是上传文件/附件（文档的 PDF、图片等）的存储抽象——与 3.5/3.6 的"调模型后端"同属基础设施可插拔层，但走的是文件面而不是模型面。它由一个工厂和四个内置后端组成：

### 接口形状（base.py）

`FileStorage`（ABC，`storage/base.py:14`）声明了五个抽象方法和四个带默认实现的可选方法：

| 方法 | 性质 | 语义 |
|---|---|---|
| `store(file_data, key)` / `retrieve(key)` / `delete(key)` / `exists(key)` | 抽象（:18, :55, :80, :100） | 整块字节读写删；`retrieve` 缺键必须抛 `FileNotFoundError` |
| `get_download_url(key, expires_in)` | 抽象（:113） | PostgreSQL 返回 API 路径（鉴权在 API 层），对象存储返回预签名 URL |
| `store_stream` / `retrieve_stream` | 默认实现（:37, :70） | 0.10.2 新增（#4689）：默认实现退化为整块缓冲再调 `store`/`retrieve`，支持流式的后端覆写它，大文件永不整体驻留内存 |
| `delete_prefix(prefix)` | 默认实现（:89） | 一个 bank 的文件共享一个 key 前缀，删 bank 即前缀清扫；**非抽象**——先于此机制写的第三方后端仍能加载，调用方按 best-effort 处理 |
| `get_size(key)` | 默认实现（:129） | 返回 None 表示后端不知道/不支持 |

三个对象存储后端（S3/GCS/Azure）共享 `ObstoreFileStorage` 基类（`base.py:150`）：它们都构建在 obstore（Rust 实现的 object-store 绑定）上，retrieve 把 obstore 自有的 Bytes 缓冲**拷回原生 `bytes`**（Starlette Response 的 render 会对非 bytes 调 `.encode()`，:205-216）；三个云的"键不存在"错误词形不同，统一由 `_is_not_found` 按消息匹配（`base.py:144-147`）；前缀删除用分页批量删（S3 的 DeleteObjects 一次至多 1000 键，`base.py:134-146`）。

### 四个后端各自的角色

- **PostgreSQLFileStorage**（`storage/postgresql.py:46`，`storage_type="native"`）：默认、零配置，文件进 `file_storage` 表的 BYTEA 列——开箱即用、与库事务一致、pg_dump 一并备份，代价是库膨胀与分布式不友好（类 docstring 明说生产规模应换 S3）。0.10.2 的流式改造（#4689）是它最重的变化：`store_stream` 把字节流写成 4 MiB 的 chunk 行（`PG_STREAM_CHUNK_SIZE`，:17）加一行 manifest（`_CHUNKED_MANIFEST_SIGNATURE` 魔数前缀标识这是分块文件，:21；不足一个 chunk 的流按普通单行写），**任何时刻只缓冲一个 chunk、只在每次写时持有连接**（:174-231）；失败路径主动清掉已写的 chunk——没有 manifest 指向它们，不清就永远成孤儿（:220-231）。读侧 `retrieve_stream` 对分块文件逐 chunk 行读、对普通单行文件用 `substring` 按 4 MiB 分段从 TOAST 读——不可压缩的 blob（图片/PDF）本就未压缩存储、可直接切片，压缩型的每次多解压一点，由 4 MiB 的段大小把 CPU 限制在几十次内（:254-297，substring 在 :290）。Oracle 没有 SQL 形式能一次取 32 KB 以上的 BLOB，普通行仍整读（docstring 原话）。
- **S3FileStorage**（`storage/s3.py:12`）：S3 兼容（MinIO、Cloudflare R2、Tigris 等），`http://` endpoint 自动 `allow_http`（本地对象存储用）。
- **GCSFileStorage**（`storage/gcs.py:38`）：没有显式 service account key 时用 google.auth 凭据 provider——obstore 内建的解析只认 service_account/authorized_user 两种 JSON，google-auth 额外覆盖 Workload Identity Federation、impersonated、metadata-server 等（:14-35）；还要临时摘掉 `GOOGLE_APPLICATION_CREDENTIALS` 环境变量再建 store——obstore 的 Rust 层会在 provider 已给定的情况下仍抢先解析它（上游 obstore#605 的 workaround，:67-76）。0.10.3 起（#5369）覆写 `get_download_url`（:79-99）：存储 key 的段是 percent-encoded 的（见下 `key_segment`），bank id 带空格/点/非 ASCII 时对象名里**字面含 `%`**——"Express%20AI" 就是对象名，不是转义后的 "Express AI"；而 obstore 的 GCS 签名器把 key 原样放进 URL 路径，GCS 把 `%20` 解码后查的是另一个对象——导出成功、下载 NoSuchKey。覆写把 `%` 再转义成 `%25`，让路径解码回字面名，签名也按同一路径计算。仅 GCS 需要这层——obstore 的 S3/Azure 签名器已自行转义 `%`（这边再转义会双重编码）；`tests/test_file_storage_signed_urls.py` 对三个后端签名并断言路径解码回存储 key，兄弟后端回退或第四个后端加入都会在那里失败。
- **AzureFileStorage**（`storage/azure.py:12`）：account key / SAS / 默认 Azure 凭据。

### 工厂、扩展槽与 key 编码

`create_file_storage`（`storage/__init__.py:44-122`）按 `HINDSIGHT_API_FILE_STORAGE` 配置分派 `native / s3 / gcs / azure`，且**先查扩展槽**：`HINDSIGHT_API_FILE_STORAGE_EXTENSION=module.path:ClassName` 指向一个 `FileStorage` 子类，其余 `HINDSIGHT_API_FILE_STORAGE_*` 变量作为小写 config dict 交给它——厂商私有后端不必进本工厂（:128-159），与 memories store 的 `HINDSIGHT_API_MEMORIES_EXTENSION` 是同一个模式。key 编码有两个刻意的防御：`bank_storage_prefix`（:12-26）把租户 schema 放在前缀最前——对象存储的桶跨租户共享，否则两个租户的同名 bank 会写同一个 key、一个删掉内容寻址附件另一个也丢；`key_segment`（:29-41）用 percent-encoding（`.` 也转义）做**单射**段落编码——`/` 被编码掉所以一个 bank 不可能嵌进另一个的前缀被连带清扫。调用方在 `memory_engine.py`（导出/导入 key 拼装 :7980、:8705，前缀清扫 :11762）与 admin CLI（`admin/cli.py:1107-1108`，rename 时要同时拼新旧两个前缀）。

### 与 store-owned 模式的关系

同一套"可插拔后端 + 扩展槽"的模式在**两个存储面**上各有一个实例：本节的 `FileStorage` 管文件/附件；`engine/memories/` 的 `MemoriesExtension`（`HINDSIGHT_API_MEMORIES_EXTENSION`）管记忆行本身——bank 的记忆由外部 store 接管即"store-owned"模式。0.10.2 对 store-owned 的两处配套都落在连接池与索引这两个共享资源上：

- **读路径不占池**（#4620）：十余条引擎路径（HEAD 现状是 10 个函数里的 10 处调用点；#4620 落地时为 7 处，同窗口的 #4979/#5036 又有追加）此前只为把连接递给一个"对 store-owned bank 根本不碰 SQL"的 store 读而开了池连接、且整个远程调用期间握着槽位。现在统一经 `_store_read_conn`（`memory_engine.py:6224`，调用点如 `:10246, :10364, :11969, :17888`）——store-owned bank 时 yield `None`，否则给池连接；自己跑 SQL 或访问仍走 SQL 的 store 读（entity 名、graph view）的路径保持 `acquire_with_retry`。
- **不建 per-bank 向量索引**（#4659）：store-owned bank 不写 `memory_units` 行，它的三个 partial HNSW 索引永远是空的——而空不是免费的：Postgres 对关系上的每个索引都做规划，某租户 27,315 个 store-owned bank 背着 82,795 个空索引，为 0 行查询付 975 ms 规划（#4615）。建 bank 向量索引的路径现在跳过 store-owned bank（守卫放在被调方，import 恢复也受益；只影响创建、不删已有索引）。同一参数化也体现在 `ensure_embedding_dimension(store_owned_memories=...)`：跳过 mental_models 的维度对齐与索引校验（`migrations.py:763-800`）。

## 3.11 后台写任务的公共簿记：PendingWrites（0.10.3 新增）

`engine/background_writes.py`（70 行，#5092）是 0.10.3 从 `audit.py` 与 `llm_trace.py` 中提出的共享组件：两者都把"尽力而为"的 DB 写排成 fire-and-forget 任务，也都需要把这些任务记在某个地方。`PendingWrites`（`:17`）就是这个"某个地方"——按 key 分桶持有飞行中写任务的**强引用**，并可按需排空：

- **为什么必须持强引用**：事件循环对裸 task 只保弱引用，一个没有其他引用的写任务可能在飞行中被 GC 回收——写无声消失。audit 原来的 `asyncio.create_task(self._safe_log(entry))` 就只兜了"没有运行中事件循环"的 RuntimeError，任务本身不持有引用；llm_trace 原来自己手写了一份 `_pending: dict[str | None, set[asyncio.Task]]` + done 回调清理。现在两边都换成同一个类（`audit.py:149`、`llm_trace.py:440`）。
- **为什么必须能排空**：调用方在拆连接池（或要对这些行发 UPDATE）之前，得让写先落地。
- `schedule(coro, key)`（`:33-44`）：`create_task` 并登记进 key 桶，无事件循环（关停中）时 `coro.close()` 并返回 False；完成回调把任务摘出桶，空桶删除。
- `drain(key)`（`:57-61`）：等**单个 key** 的在飞写，无超时——调用方在操作中途，llm_trace 的 `attach_memory_ids` 用它先排空自己 trace 的写再 UPDATE（否则 UPDATE 可能跑到它要修补的 INSERT 前面；该任务刻意**不**登记进同 key 桶——桶里的任务会永远等自己，`llm_trace.py:660-663` 的注释明说）。
- `drain_all(timeout)`（`:63-70`）：等**全部**在飞写，有界——卡死的库不能挂死关停，超时仍在飞的记 warning 并放弃。audit 的 `drain()` 用它（`_DRAIN_TIMEOUT_SECONDS = 5.0`，`audit.py:29, 203`），`MemoryEngine.close` 在关停任务后端之后、关池之前 `await self._audit_logger.drain()`（`memory_engine.py:6335`）。

# 必答问题速查

1. **LLM 抽象核心接口**：`LLMInterface.call(...) -> LLMCallResult` 与 `call_with_tools(...) -> LLMToolCallResult`（`llm_interface.py:156, 205`）；返回值是 pydantic 模型 `content + TokenUsage`。structured output 三条路：软模式（schema 入 prompt + 可选 json_object——`_supports_json_mode()` 按 `HINDSIGHT_API_LLM_OPENAI_COMPATIBLE_JSON_MODE` 三态决定，#5261/#4935）、strict（OpenAI `json_schema strict` / Anthropic forced tool_use / Gemini 原生 response_schema）、解析兜底 `parse_llm_json`（围栏→控制字符→json_repair）。schema 序列化统一剥离数值边界关键字（`minimum`/`maximum` 等 5 个，Bedrock/OpenAI 白名单校验会 400，#5401/#5275）。prompt 缓存两级：接口层 `cached_prefix`（句柄）、编排层 `prompt_cache`（`PromptCachePrefix`，由实际服务的链成员自己解析句柄，#5245）。
2. **provider 清单**：32 个 LLM provider 名 / 17 个实现类（1.0.0 新增 `chatgpt` 一名一类；去重计数：`providers/__init__.py` 的 `_MODULES` 表登记 14 个类（PEP 562 惰性加载）+ 分支内惰性 import NousLLM `llm_wrapper.py:732`、XaiOAuthLLM :752、ChatGPTLLM :766；分派 `llm_wrapper.py:458-827` + `valid_providers :976-1012`）；embedding 13 分支（`embeddings.py:2363-2549`，1.0.0 新增 nvidia/NIM）；reranker 15 分支（`cross_encoder.py:2434-2583`，1.0.0 新增 nvidia/NIM）。本地/远程无单一标志，由 `hindsight_api/provider_auth.py` 的免 key 集合（+ anthropic WIF 的 env 条件分支）、子进程/远程实现之分（唯一的本地自管是 llamacpp 的 llama-cpp-python 子进程）、`_V1_PATH_LOCAL_PROVIDERS` 端点归一化三处共同刻画。
3. **mock / none**：`MockLLM` 是测试假人（记录调用、可编程响应、supports_vision=True）；`NoneLLM` 是 `provider=none` 的 chunk-only 模式安全网，任何调用抛 `LLMNotAvailableError`。
4. **配置三级层次**：全局 env → 租户（TenantExtension 钩子）→ bank（banks.config JSONB），后写者覆盖前者；**只有 `_CONFIGURABLE_FIELDS` 白名单内的 55 个行为字段能被 bank/租户覆盖**（1.0.0 新进了 decision model 的三个 `*_use_decision_model` 开关），provider/model/api_key 明确不行（credential 拒写、其余 static 拒写）；进程内另有"全局 → per-op（retain_/reflect_/consolidation_/mental_model_refresh_）"的第二维覆盖，仍属服务器级。1.0.0 另有两个不进三级层次的旁路：decision model 的 provider/key 侧设置（服务器级 static + credential 字段，按 recall/reflect/consolidation 逐操作可覆盖 env）与 LLM request extension（扩展代码逐调用决定，见 3.7）。
5. **embedding 维度**：初始化时自检（SentenceTransformers `get_embedding_dimension()`（5.4+，5.0-5.3 回落旧名 `get_sentence_embedding_dimension`，#5660）、TEI 试嵌入、OpenAI 查 `MODEL_DIMENSIONS` 表或试嵌入、ONNX 显式配置比对）。换模型维度不一致的防护有两层：启动/迁移期 `ensure_embedding_dimension`——空表直接 `ALTER COLUMN embedding TYPE vector(n)`，有数据则报错给迁移指引（`migrations.py:763-800`，ALTER 语句 :707）；运行期 `generate_embeddings_batch` 逐向量校验长度等于 `backend.dimension`，数量必须 1:1（`embedding_utils.py:95-153`）。
6. **重试/限流/超时**：LLM 自带每 provider 重试循环 + 双层 `CrossLoopSemaphore`（全局 32 + per-op）+ 分相位超时（connect 10s 封顶）+ SDK 调用外的 `asyncio.wait_for` 墙钟上限（#4763）；embedding/reranker 用 provider 无关的 `RetryPolicy`（attempts + budget_seconds 双界）+ 每后端实例 per-loop 信号量 fan-out；TEI 自带重试且被豁免外层重试；in-process 本地重排另有单次 recall 的 300s 墙钟（#4696，超时降级为部分分数 + RRF 序尾部）。
7. **cache_affinity.py 是干嘛的？embedding 有没有缓存？**：`cache_affinity` 是 OpenAI 兼容系 provider 的服务端 prompt-cache **亲和提示**（xAI 发 `x-grok-conv-id` 头、OpenAI 发 `prompt_cache_key` 字段；`auto` 按 base_url host 白名单解析），让同一操作的调用粘到同一后端缓存副本——它不缓存任何向量；embedding 侧没有 query→vector 的 memoization 缓存，向量落库随行读出（详见 3.6）。
